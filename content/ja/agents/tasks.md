# タスクの順序管理（DAG）

タスクを登録して依存関係をつなぐと、先に完了する必要がある段階に合わせて実行できます。`task-run`、`task-create`、`task-await` でタスクを 1 つ実行してから、順序と失敗の処理をつないでください。

タスクは `tasty` CLI で作成し、管理します。初めての場合は、[ランナーを起動する](#ランナーを起動する) → [タスクを作成する](#タスクを作成する) → [結果を確認する](#結果を確認する) の 3 節に沿って、タスクを 1 つ `task-run`・`task-create`・`task-await` で最後まで実行してみてください。その後の順序の接続・結果の受け渡し・分岐・同期は、必要なときに読んでください。実行状況を画面で確認するには、[進行状況を見る](#進行状況を見る) を参照してください。

各コマンドには、タスクが属するワークスペースを `--workspace` で指定します（以前の表記 `--workspace-id` も受け付けます）。別のワークスペースを表示していても、指定した場所で処理します。

## ランナーを起動する

タスクを作成しても、ランナーが停止していると何も実行されません。ワークスペースごとに一度起動してください。

```sh
tasty agent task-run --workspace 2 --action start
tasty agent task-run --workspace 2 --action status
tasty agent task-run --workspace 2 --action stop
```

tasty を再起動しても、ランナーは自動では起動しません。タスク自体は残っているので、再び `start` すると続きから進みます。再起動前に外部の完了シグナルを待っていたタスクは、再起動後にそのシグナルでは完了せず、設定した待機時間が過ぎると、実行中のランナーがタイムアウトによる失敗として終了させます。ランナーが停止している場合は、DAG 画面のランナー表示にもその状態が示され、表示にマウスを重ねると、再び起動するコマンドがそのまま表示されます。DAG タブでは、そのコマンドがヘッダーにも 1 行で表示されます。

## タスクを作成する

```sh
BUILD=$(tasty agent task-create --workspace 2 --name build \
  --command '{"kind":"run","command":["cargo","build"]}' | jq -r .id)
```

作成するとタスク ID が返されます。この ID で依存関係を設定し、状態を照会します。

| コマンドの種類 | 動作 |
|---|---|
| `run` | 指定したコマンドを実行します。ターミナルを占有しないバックグラウンドプロセスで、標準出力と標準エラーをそれぞれ末尾から最大 64KiB まで結果に含めます。対話型プログラムには適していません。環境変数は Tasty を起動した環境を引き継ぎますが、表の後に記載した例外があります |
| `custom` | tasty 自体の動作をタスクにします。子エージェントの起動など、ターミナルを作成する処理が該当します。完了を別途待つ動作の場合、グラフとして送信したタスクは、最初に受け取った受付応答を最終応答とは別に結果の `raw.accepted` に残します |
| `reduce` | 複数のタスクの結果を 1 つにまとめます |
| `wait_barrier` | バリアにシグナルがすべて集まるまで待機します |
| `agent` | Claude や Codex などのエージェントセッションに指示を 1 つ送り、その回答を結果として受け取ります。後述の [エージェントに仕事を任せて回答を結果として受け取る](#エージェントに仕事を任せて回答を結果として受け取る) で説明します |

コマンドの JSON はファイルに分けて、`--command @build.json` のように渡すこともできます。

`custom` タスクの完了を定期的に照会する場合は、`poll.interval_ms` で照会間隔を指定します（既定は 500ms）。最初の照会は直ちに行い、その後は前の照会が終わってから指定した時間だけ待機します。同じ対象を待つタスクも、それぞれ照会します。ランナーが混み合っていると確認が遅れることがありますが、遅れた照会をまとめて送信することはありません。`poll.timeout_ms` を設定した場合は、次の照会時刻に達していなくても期限を確認します。再起動後にランナーを再び起動すると、保存された間隔と期限で照会を再開し、元の実行要求は再送しません。0ms は、ランナーが進行するたびに一度照会することを意味します。

タスク 1 つの定義（コマンド、メタデータ、結果の型など）は、JSON に変換したときに最大 768 KiB です（メモリ項目のサイズ上限を 1 MiB 未満に設定すると、それに合わせて小さくなります）。超過するとタスクを作成せず、エラーで通知します。大きなデータはファイルに保存し、そのパスを渡してください。実行直前に前のタスクの結果を挿入してこのサイズを超えた場合、そのタスクは実行せず、失敗として終了します。

`run` コマンド、後述の後処理コマンド、シェルコマンドで結果をまとめるリデューサーは、Tasty を起動した環境をそのまま引き継ぎます。ただし、Tasty を Claude Code 内で起動した場合、そのセッションを指す変数は渡しません（ターミナルと同じです）。別の Tasty のターミナルから起動した場合は、その Tasty を指す `TASTY_SESSION_TOKEN`・`TASTY_SURFACE_ID`・`TASTY_PARENT_HOME`・`TASTY_AGENT_ID` も渡しません。そのため、コマンド内で `tasty` を呼び出すと、この Tasty に接続します。

## 結果を確認する

```sh
tasty agent task-await --workspace 2 --id "$BUILD"   # 完了するまで待機（既定で最大 10 分）
tasty agent task-get --workspace 2 --id "$BUILD"     # 状態と結果を再確認
```

`task-await` 応答の `outcome` が `terminal` ならタスクは完了しており、`state` が `succeeded` か `failed` かで成功したかどうかを判断します。`timed_out`（待機時間超過）と `not_found`（存在しないタスク）も終了コード 0 で返されるので、終了コードだけで判断しないでください。`run` タスクの終了コードと出力は、応答の `result` にあります。待機時間のオプションは、[タスクの待機と管理](#タスクの待機と管理) に記載しています。

ここまでが、タスクを 1 つ実行して結果を確認する基本的な流れです。以降の節では、複数のタスクを順につなぎ、結果を渡し、分岐させる高度な手順を説明します。

## 順序と失敗の処理

```sh
TEST=$(tasty agent task-create --workspace 2 --name test \
  --command '{"kind":"run","command":["cargo","test"]}' \
  --depends-on "$BUILD" --on-failure abort | jq -r .id)
```

`--depends-on` に記載したタスクがすべて完了すると、このタスクは準備状態になります。循環が生じるグラフは、作成時に拒否されます。

| 失敗ポリシー | 意味 | 設定する側 |
|---|---|---|
| `abort`（既定） | 依存先のタスクが失敗すると、このタスクをスキップします。その下流も続けてスキップします | 依存する側 |
| `continue_downstream` | 依存先のタスクが失敗しても、このタスクを進めます | 依存する側 |
| `fallback:<タスク ID>` | このタスクが失敗すると、代わりに指定したタスクを起動します | 失敗する可能性がある側 |

設定する位置は間違えやすい点です。`abort` と `continue_downstream` は、**後続の**タスクに設定すると、そのタスクの準備判定に反映されます。一方、`fallback` は、**失敗する可能性がある**タスク自身に設定する必要があります。別の位置に指定すると、意図した失敗の処理が適用されません。

Tasty が混み合って `custom` タスクの要求に時間内に応答できなくても、タスクをすぐに失敗として終了させることはありません。状態確認が遅れた場合は次の確認で再び問い合わせ、実行されないまま期限切れになった要求は再送します。すでに実行が始まった要求（子エージェントの起動など）は、二重に実行されないよう再送せず、遅れた応答を待ちます。その応答を最終的に受け取れなかった場合（その間にアプリを再起動した場合など）、タスクは失敗ではなく `unknown` になります。要求が実際に反映されたか（子が起動したかなど）を確認してから、再実行またはキャンセルしてください。

フォールバックに使うタスクは、本来のタスクより先に作成する必要があります。その間にランナーが先に実行してしまうのを防ぐには、フォールバック側を `--reserved-for-fallback` で作成してください。予約すると、本来のタスクを作成する前でも実行されません。本来のタスクを接続した後は、そのタスクが失敗してフォールバックを有効にするまで待機します。

## 前のタスクの結果を渡す

`--depends-on` は順序だけを結び付けます。前のタスクの結果を後のタスクの**入力**として渡すには、プレースホルダーを使います。

```
${task.<タスク ID>.output}          結果全体
${task.<タスク ID>.output/stdout/text}   結果内の 1 つの値
```

タスクを送信するときに、その位置に実際の値が入ります。子エージェントを起動し、その子に話しかける流れのように、作成時には分からず、実行して初めて決まる値を渡す場合に使います。参照するタスクは必ず `--depends-on` に記載する必要があり、記載がない場合は作成時に拒否されます。値の形式は維持されます。プレースホルダーが 1 つだけの文字列は、値が数値なら数値に変わります。

## 型を指定したタスクのまとまりを一度に送る

結果の型まで指定しておきたい場合は、タスクを 1 つのグラフにまとめて送信します。グラフ全体を先に検査するため、1 つでも不正なものがあるとタスクは一切作成されず、どのタスクのどの箇所が誤っているかがエラーに表示されます。すべてのタスクが作成されるまで、どのタスクも実行されません。1 つのグラフには最大 1000 個のタスクを含めることができ、それを超える場合は複数のグラフに分けて送信します。

```sh
tasty agent task-graph-submit --workspace 2 --graph @graph.json --dry-run   # 検査のみ
tasty agent task-graph-submit --workspace 2 --graph @graph.json
```

```json
{"contract_version": 2,
 "tasks": [
   {"id": "build", "command": {"kind": "run", "command": ["cargo", "build"]}},
   {"id": "report", "command": {"kind": "run", "command": ["notify"]},
    "input_schema": {"type": "object", "fields": {"code": {"type": "int64"}}},
    "bindings": {"code": {"from_task": "build"}},
    "input_mapping": {"args": ["/code"]}}]}
```

各タスクの `id` は自分で決めます。`bindings` は入力の取得元を指定します。固定値（`literal`）、前のタスクの結果内の値（`from_task` と `pointer`）、本来のタスクとフォールバックのうち実行された側（`one_of`）を使うことができ、型が合わない場合は送信時に拒否されます。受け取った値は `input_mapping` に記載した位置にだけ入ります。`args` はコマンドの後に引数として 1 つずつ追加し、`stdin: true` は入力全体を JSON として標準入力に書き込みます。`wait_barrier` タスクは、`"barrier": "/<フィールド>"` で待機するバリア名を入力から受け取ることができ、この場合はコマンドに `name` を記載しません。値の中の `$(...)` や空白は再解釈されません。実際に渡した値は、タスクの `input_snapshot` で確認できます。このグラフのタスクには、前述のプレースホルダーを使いません。

`run` タスクに既存のファイルを渡すには、`args` に `{"file": "/<フィールド>"}` を指定します。そのフィールドの文字列がファイルパスで、コマンドの後にパスが引数として追加されます。タスクの実行直前にそのファイルを読み取れるか確認し、存在しない場合や読み取れない場合は、コマンドを実行せず入力段階で失敗します。相対パスは、コマンドに `cwd` がある場合にだけ、それを基準として受け付けます。Tasty はファイルを作成したり削除したりしないので、ファイルの準備と後片付けは前後のタスクやスクリプトが担当します。以下のスクリプトは diff をファイルに書き出して検査コマンドに渡し、検査が失敗しても最後に削除します。

```sh
#!/bin/sh
# lint-diff.sh <workspace id>
set -eu
diff_file=$(mktemp)
git diff > "$diff_file"
tasty agent task-graph-submit --workspace "$1" --graph "$(cat <<JSON
{"contract_version": 2, "tasks": [
  {"id": "lint", "command": {"kind": "run", "command": ["my-lint", "--diff"]},
   "input_schema": {"type": "object", "fields": {"diff": {"type": "string"}}},
   "bindings": {"diff": {"literal": "$diff_file"}},
   "input_mapping": {"args": [{"file": "/diff"}]},
   "on_failure": {"kind": "continue_downstream"}},
  {"id": "cleanup", "command": {"kind": "run", "command": ["rm", "-f", "$diff_file"]},
   "depends_on": ["lint"]}]}
JSON
)"
```

タスクの結果を別のコマンド（判定・要約ツールなど）でもう一度処理し、その出力を結果にするには、`postprocess` を追加します。本来のタスクが成功するとそのコマンドを実行し、標準出力をタスクの結果として受け取ります。

```json
{"id": "judge",
 "command": {"kind": "run", "command": ["make-draft"]},
 "output_schema": {"type": "enum", "values": ["pass", "revise"]},
 "postprocess": {"command": ["judge-cli", "--json"],
                 "stdin": {"draft": {"from": "raw", "pointer": "/execution/stdout/text"}},
                 "stdout": {"pointer": "/verdict"},
                 "timeout_ms": 120000,
                 "retry": {"max_retries": 1}}}
```

- コマンドはシェルを使わず、そのまま実行されます。シェルが必要な場合は、`["sh", "-c", "..."]` のように明示してください。ログイン情報は Tasty を起動した環境をそのまま使います。ただし、Tasty を Claude Code 内で起動した場合、そのセッションを指す変数は渡しません（ターミナルと同じです）。Tasty を別の Tasty のターミナルから起動した場合は、その Tasty のターミナルを指す `TASTY_SURFACE_ID` などの変数も渡しません。
- `stdin` は、標準入力に書き込む JSON のフィールドを指定します。`from` は `input`（タスクの入力）または `raw`（本来のタスクの結果）で、`pointer` でその中の値を選びます。
- 標準出力は、既定では JSON 値 1 つである必要があります。`"stdout": {"format": "text"}` を使うと、文字列をそのまま受け取ります。進行ログを標準エラーに出力すれば、結果に混ざりません。
- `cwd` で後処理コマンドの作業フォルダーを指定します。省略した場合は本来のタスクの `cwd`、それもなければ Tasty を起動したフォルダーになります。
- `timeout_ms` は必須です。時間が過ぎるかタスクをキャンセルすると、そのコマンドと、そのコマンドが起動したプロセスを終了させます。
- `retry` を指定すると、失敗した場合に本来のタスクは再実行せず、後処理だけを指定回数だけ再実行します。`max_retries` は 1～10 で、`delay_ms` で再実行前の待機時間を指定します（既定は 0、最大 3600000）。回数を使い切るとタスクは失敗として終了し、後続のタスクは通常の失敗と同様に失敗ポリシーに従います。後処理だけを別途再実行する方法はありません。やり直すには、`task-retry` で本来のタスクから再実行してください。
- 型を指定したタスクの実行中は、`task-list` の行末と `task-get` の `phase:` 行に段階が表示されます。本来のタスクを実行中なら `executing` です。
- 後処理は `run`・`custom` タスクに追加します。`reduce`・`wait_barrier` タスクには追加できません。
- 段階が変わってもイベントは送信されません。特定の時点で通知が必要な場合は、そのタスクの後に `["tasty", "notify", "build finished"]` や webhook を呼び出す `curl` などの `run` タスクを挿入してください。
- 後処理が完了するまで、タスクは実行中と表示され、次のタスクは待機します。`task-get` は `state: running` の次の行に `phase: postprocessing (run 1)`（再試行を待機中なら `phase: retry_wait (run 2)`）を表示します。
- 後処理が失敗すると、`task-get` の `state` 行に理由が表示され、その下に `postprocess: run 2 failed (nonzero_exit), exit_code 3` のように、最後の実行の原因と終了コード、再試行に移った実行の原因（`postprocess retried after: ...`）が表示されます。後処理の結果が大きすぎて保存できない場合、成功した後処理は、`task-get` の元の結果から本来のタスクの応答を除き、成功として残します。それでも超過する場合や失敗した実行の場合、原因は `result_too_large` となり、再試行が残っていても再実行しません。
- 後処理の実行中に Tasty を終了すると、その後処理コマンドと、そのコマンドが起動したプロセスを終了させます。再起動後にその後処理は再実行されず、タスクは失敗として終了します。ランナーを停止するとき（`task-run --action stop`）も同じ方法で後処理を終了させ、ランナーを再び起動するまでタスクは実行中と表示されます。やり直すには、`task-retry` でタスクを再実行してください。
- Tasty が強制終了した場合（`kill` など）は、OS ごとに異なります。Windows では後処理コマンドとそのコマンドが起動したプロセスが一緒に終了し、macOS ではすべて残ります。
- 再起動後も後処理コマンドがまだ実行中の場合（macOS で強制終了した場合）、そのコマンドが終了するまでタスクは実行中のままで、セマフォ・lease も保持し続けます。コマンドが終了すると、結果を受け取れないため失敗として終了し、その時点でリソースを解放します。コマンドが起動した別のプロセスだけが残っている場合は待機しません。後処理を待っていたタスク（再試行待機を含む）は、リソースを保持したまま予定どおり後処理を実行します。

Tasty がメモリファイルを開けず、[一時メモリ](cli-reference.md#エージェントが共有するメモリ) で動作している間は、グラフが再起動後に残らないため、そのまま送信すると拒否されます。再起動で消えても構わないグラフは、`"durability": "best_effort"` を追加して送信してください。

### 結果に応じて次のタスクを選ぶ

タスクに `transitions` を記載すると、そのタスクの結果を見て次に実行するタスクを選びます。以下の例では、`review` の判定が `pass` なら `ship`、`revise` なら `fix`、それ以外なら `human` だけを実行します。

```json
{"id": "review", "command": {"kind": "run", "command": ["review-tool"]},
 "output_schema": {"type": "object", "fields": {
   "verdict": {"type": "enum", "values": ["pass", "revise", "review"]}}},
 "transitions": {
   "cases": [
     {"when": {"compare": {"path": "/verdict", "op": "eq", "value": "pass"}}, "to": ["ship"]},
     {"when": {"in": {"path": "/verdict", "values": ["revise"]}}, "to": ["fix"]}],
   "otherwise": ["human"]}}
```

- 条件は、結果内の 1 箇所（`path`）を値と比較するか（`compare`: `eq`・`ne`・`lt`・`le`・`gt`・`ge`）、値のリストに含まれるかを調べます（`in`）。`all`・`any`・`not` でまとめることができます。結果の型に合わない条件は、送信時に拒否されます。小数は範囲でのみ比較します。
- 結果を集める `reduce` タスク（戦略 `all`）では、条件に `"input": "<入力タスク id>"` を追加すると、集めた結果の代わりに、その入力タスクの結果をそのタスクの結果の型で読み取れます。
- 既定では、一致する条件が 1 つである必要があります。2 つ以上一致すると、そのタスクは失敗として終了します。一致したものをすべて実行するには、`"mode": "all_matches"` を追加してください。
- どの条件にも一致しないときに実行するタスク（`otherwise`）、または何も実行しない指定（`"no_match": "finish"`）を必ず記載してください。
- 選ばれなかったタスクと、そのタスクからだけつながる後続のタスクは、失敗ではなく「未選択」として終了します。分岐が再び合流するタスクは、実際に実行された分岐だけを待ちます。実行された分岐が失敗すると、その失敗はそのまま伝わります。
- 実行されない可能性がある分岐の結果を必須入力として受け取る場合は、送信時に拒否されます。分岐ごとに別のタスクが値を返す場合は `one_of` で受け取り、なくてもよい値なら入力フィールドを optional にするか、既定値を指定してください。
- タスクの `route` に選んだタスクが、選ばれなかったタスクの `skip` にその理由が残ります。すべてのタスクが成功または未選択なら、DAG は成功と表示されます。失敗したタスクも、フォールバックが代わりに成功していれば DAG を失敗にはしません。
- ある分岐が失敗しても、別の分岐が進行できる間は、DAG は進行中の状態（実行中・準備・待機）で表示されます。結果が分からなくなった（`unknown`）タスクは、再実行またはキャンセルしないと進まないため、進行中には数えません。すべてが終了したとき、最後まで成功した分岐があれば DAG の状態は `partially_failed`（一部失敗）、なければ `failed` です。前のタスクだけが成功し、最後のタスクが失敗またはスキップされた一直線の流れは `failed` です。失敗してもフォールバックが代わりに成功した最後のタスクは、成功と数えます。`agent dag-list` の `rollup_state` に表示され、タスク DAG の一覧と DAG タブには `◒` マークと **一部失敗** <!-- en: Partially failed --> ラベルで表示されます。

### エージェントに仕事を任せて回答を結果として受け取る

`agent` タスクは、Claude や Codex などのエージェントセッションに指示を 1 つ送り、その回答をタスクの結果として受け取ります。結果は、次のタスクの入力や前述の分岐条件にそのまま使えます。

```json
{"id": "review",
 "command": {"kind": "agent", "provider": "claude", "workspace_id": 2,
             "session": {"kind": "existing", "surface_id": 12},
             "instruction": "このブランチの変更をレビューしてください",
             "timeout_ms": 1800000},
 "output_schema": {"type": "enum", "values": ["approve", "revise"]}}
```

- `provider` はセッションを担当するプラグインの名前です。Claude プラグインは `claude`、Codex プラグインは `codex` で、エージェントタスクをサポートするほかのプラグインも自身の名前を使えます。そのプラグインがインストールされていない場合、無効になっている場合、ターン報告権限がない場合は、タスクの作成時に理由とともに拒否されます。作成後にプラグインを無効にすると、そのタスクは実行時に失敗します。
- `command` の `workspace_id` は、新しいセッションを起動するワークスペースです。値を提出する `task-submit` はタスクがあるワークスペースに送り、指示文の末尾に付く案内にその番号が含まれます。
- `session` が `{"kind": "new", "parent_surface": <サーフェス>}` なら、そのサーフェスの下に新しいセッションを起動して指示します。ここに `"cwd": "<パス>"` を追加すると、新しいセッションの作業フォルダーになります。`{"kind": "existing", "surface_id": <サーフェス>}` なら、すでに開いているセッションに送ります。
- すでに開いているセッションは、アイドル状態のときだけ指示を受け取ります。直接会話している場合は終わるまで待機するため、会話が混ざりません。指示の末尾には、その実行を識別するマーカーが 1 行追加され、そのマーカーで始まったターンだけをタスクのターンと見なします。同じセッションを使うタスクは順番に実行されます。
- 結果の型を記載しない場合、そのターンの最後の回答が文字列の結果になります。
- Claude セッションに Stop ゲートを設定している場合、ゲートが応答を継続させている間はターンが終了しません。ゲートが応答の終了を許可した後の最後の回答で、タスクが完了します。指示に対する最初の回答が必要な場合は、結果の型を指定し、`task-submit` で提出させてください。
- 上の例のように結果の型を指定すると、エージェントは `tasty agent task-submit` で値を提出する必要があります。指示文の末尾に、提出方法と型、その実行だけで使うトークンが自動で追加されます。トークンが異なる値は受け付けないため、別のタスクや過去の実行に誤って提出した値が混ざることはありません。提出された値は直ちに検査され、ターンが終了したときに結果になります。`revise` のような判定も、成功した結果です。
- 入力を受け取るタスクには、`"input_mapping": {"input_block": true}` を記載します。入力が指示文の後に JSON として追加されます。
- 回答を提出せずにターンが終了した場合、ターンがエラーで終了した場合、セッションが終了した場合、`timeout_ms` が経過した場合は、タスクが失敗します。失敗理由は `task-get` の結果に区別して表示されます。値を提出せずにターンが終了した場合は、そのターンの最後の回答が先頭 2000 文字まで失敗記録に残ります。
- エージェントが権限承認などの入力を待っている場合、タスクは実行中のままで、`task-get` は `phase: awaiting_input` 行と `agent session: claude surface 12, awaiting input since …` 行を表示します。
- Tasty が混み合って、すでに開いているセッションに指示を送ったという応答が遅れても、指示は再送しません。同じ指示が二重に届かないよう遅れた応答を待ち、まだ送っていないことが確実な場合だけ再送します。送信したかどうか分からなくなると、タスクは失敗ではなく `unknown` になります。セッションが指示を受け取ったか確認してから、再実行またはキャンセルしてください。
- タスクが完了またはキャンセルされても、セッションは閉じません。Tasty を再起動すると、実行中だった agent タスクは失敗として終了します。指示を送ったという応答を待っていたタスクは `unknown` になります。
- 新しいセッションの起動を待っている間も、ほかのタスクは進行します。新しいセッションが 30 秒以内に起動しない場合、タスクは失敗します。その後に遅れて起動したセッションは、タスクが閉じます。待機中にタスクをキャンセルした場合も、遅れて起動したセッションを閉じます。すでに開いていたセッションは閉じません。待機中に Tasty を再起動すると、タスクは `unknown` になります。
- Codex をネットワークが遮断されたサンドボックスで実行すると、`task-submit` が Tasty に接続できず、結果の型を指定したタスクは失敗します。結果の型を指定していないタスク（最後の回答が結果）には影響しません。
- 既存のタスクの結果を Codex の親に自動的に届けるには、[Codex の親に自動的に届ける](claude-codex.md#codex-の親に自動的に届ける) を参照してください。

### 例: 実装とレビューの後、判定に応じて分岐して再び合流する

前述の機能を 1 つにつないだグラフです。`implement` が変更内容を文章として返すと、`review` がその文章を入力として受け取り、判定と確信度を返します。確信度が 0.9 以上の `pass` なら `ship`、確信度が 0.9 以上の `revise` なら `fix`、それ以外なら `human_review` に進み、3 つの分岐は `report` で再び合流します。`make-change`・`review-tool` は、それぞれのツールに置き換えてください。エージェントに任せるには、前述の `agent` タスクに置き換えてください。

```json
{"contract_version": 2,
 "types": {"ReviewResult": {"type": "object", "fields": {
   "verdict": {"type": "enum", "values": ["pass", "revise", "review"]},
   "confidence": {"type": "float64", "min": 0, "max": 1}}}},
 "tasks": [
  {"id": "implement", "command": {"kind": "run", "command": ["make-change"]},
   "output_schema": {"type": "string"},
   "postprocess": {"command": ["summarize-tool"], "timeout_ms": 10000,
                   "stdin": {"text": {"from": "raw", "pointer": "/execution/stdout/text"}}}},
  {"id": "review", "command": {"kind": "run", "command": ["review-tool"]},
   "input_schema": {"type": "object", "fields": {"summary": {"type": "string"}}},
   "bindings": {"summary": {"from_task": "implement"}},
   "input_mapping": {"args": ["/summary"]},
   "output_schema": {"ref": "ReviewResult"},
   "transitions": {"cases": [
     {"when": {"all": [{"compare": {"path": "/verdict", "op": "eq", "value": "pass"}},
                       {"compare": {"path": "/confidence", "op": "ge", "value": 0.9}}]}, "to": ["ship"]},
     {"when": {"all": [{"compare": {"path": "/verdict", "op": "eq", "value": "revise"}},
                       {"compare": {"path": "/confidence", "op": "ge", "value": 0.9}}]}, "to": ["fix"]}],
     "otherwise": ["human_review"]}},
  {"id": "ship", "command": {"kind": "run", "command": ["ship-tool"]}},
  {"id": "fix", "command": {"kind": "run", "command": ["fix-tool"]}},
  {"id": "human_review", "command": {"kind": "run", "command": ["notify-reviewer"]}},
  {"id": "report", "command": {"kind": "run", "command": ["report-tool"]},
   "depends_on": ["ship", "fix", "human_review"]}]}
```

`review` が確信度 0.95 で `pass` を返すと、`task-get` は次のように表示します。

```text
state: succeeded
route: ship
attempt: review#1
revision: 7
input: summary <- implement (attempt implement#1)
output: {"confidence":0.95,"verdict":"pass"} (from postprocess.stdout.json)
```

- `input:` 行はどのタスクの何回目の実行結果を受け取ったかを、`output:` 行は結果の取得元を示します。結果なしで終了したタスクは、`output: none` とともに、失敗した段階と理由が `error:` 行に表示されます。
- `fix`・`human_review` は `skip: branch_not_selected` で終了し、`report` は実行された `ship` だけを待って成功します。
- `review` が失敗すると、3 つの分岐と `report` はすべてスキップされ、`skip: upstream_unavailable (review failed)` のように原因となったタスクが表示されます。
- `revision` は、タスクの記録が保存されるたびに増加します。同じタスクの 2 つの照会結果のうち、どちらが新しいかを判別するために使います。
- `confidence` は、タスクが結果の型に宣言した値なので、分岐条件に使えます。ターミナルの状態照会が返す `confidence` はセッション状態の判断の確かさであり、この値とは異なります。

型を指定していないタスクも、同じワークスペースで併用できます。`task-create --depends-on report` で作成したタスクは、`report` が完了すると実行されます。ただし、`${task.review.output}` のようなプレースホルダーで型を指定したタスクの結果を読み取ろうとすると、作成時に拒否されます。結果を渡すには、受け取るタスクもグラフに含め、`bindings` で受け取ってください。

## 実行記録を残して見る

型を指定したタスクのまとまりは、人が後から読める実行記録（report）を残します。タスクごとに Tasty が自動で記入する部分と、タスクが実行中に直接書き込むメモがあります。

- 自動記入部分: 終了時の状態、開始・終了時刻、実際に受け取った入力と提出した結果、失敗した場合は段階と理由、スキップした場合は理由です。シェルコマンドには終了コード、エージェントタスクにはどのセッションだったか、結果の集約には方法と入力数も表示されます。
- メモ: シェルコマンドのタスク、その結果を整える後処理コマンド、自分で書いた結果集約用のシェルは、環境変数 `TASTY_TASK_REPORT` を受け取ります。その中で `tasty agent report append 'テストを 3 件スキップ'` のように記載してください。このコマンドは成功時には何も出力せず、タスクの結果に影響を与えません。失敗時だけ標準エラーに理由を書き込みます。シェルコマンドは、標準エラーに `::tasty-report::<メモ>` で始まる行を書き込むこともできます（その行は標準エラーにもそのまま残ります）。エージェントタスクには、指示文の末尾にメモの書き方を読むコマンド（`tasty agent report usage`）とアドレスが追加されます。

```sh
#!/bin/sh
# シェルコマンドのタスク内で
tasty agent report append "検査したファイル $(ls src | wc -l) 件"
echo "::tasty-report::キャッシュを再作成しました" >&2
```

メモはタスクの実行中だけ受け付けます。終了後に書き込むと拒否されます。メモ 1 件が上限（既定は 1 KiB）を超えると切り詰められ、その旨の表示が付きます。1 回の実行のメモの合計が上限（既定は 16 KiB）を超えると、それ以降のメモは保存せず、件数だけを数えます。どちらの場合もコマンドは失敗しません。両方の上限は、**設定** › **その他** › **タスクパイプライン** <!-- en: Task pipeline --> で変更します。再実行（`task-retry`）すると、メモは実行ごとに別々に集められます。メモは記録にすぎないため、後続のタスクの入力（`bindings`）として受け取ることはできません。

```sh
tasty agent dag-report d:review-loop                       # まとまり全体
tasty agent dag-report d:review-loop --task build --attempt 2   # タスク 1 つの 2 回目の実行
tasty agent dag-report d:review-loop --include-raw         # 標準出力・エラーも含める
```

DAG id は `tasty agent dag-list` で確認します。再実行（retry）したタスクの過去の実行についても、終了時の状態・メモとともに、再実行の開始時に保存した自動記入部分が表示されます。

## 進行状況を見る

タスクグラフは、進行状況を確認する画面です。タスクの作成と変更は CLI で行います。ノードの実行状態と、タスクが残した結果を合わせて確認してください。

タスクの流れを見る画面は 2 つあります。どちらも同じデータを表示します。

- **タスク DAG** <!-- en: Task DAGs --> ウィンドウ — `Ctrl+Shift+G`（Mac プリセットでは `Cmd+Shift+G`）、またはサイドバーの **ツール** <!-- en: Tools --> メニューから開きます。一覧から 1 つ選んで短時間確認し、閉じる用途です。検索と状態フィルターがあります。1 つ選ぶと同じ場所がグラフに切り替わり、最上段の戻る矢印の横に拡大・縮小・全体表示・方向切り替えとランナー表示が並びます。
- **DAG タブ** — タブを 1 つ使い、開いたままにするグラフです。`tasty new tab --pane <ID> --type dag_graph` で開くか、既存のサーフェスで `Alt+'` を押して **DAG** に切り替えてください。拡大と縮小、全体表示、方向切り替えがあり、ノードを押すとコマンド・依存関係・所要時間・終了コード・出力が表示されます。

グラフの線は、関係ごとに形が異なります。順序だけを結び付ける依存関係は実線、入力を受け取る接続（`bindings`）は青緑の一点鎖線、結果に応じた分岐（`transitions`）は紫の破線です。選ばれた分岐は太く描画します。選ばれなかった経路や実行されない経路は、不透明度を下げずに中立色で描画し、関係に応じた実線・一点鎖線・破線の形は維持します。2 つのタスク間に順序の依存関係と入力接続が両方ある場合は、入力接続だけを描画します。選ばれずにスキップされたタスクには **未選択** <!-- en: Not selected --> が付きます。ノードにマウスを重ねるとタスク名と状態が表示され、スキップされたタスク、結果が不明なタスク、入力を待っているタスクには、その理由がもう 1 行表示されます。`task-graph --format dot` も同じ区別で描画します。

ノードの左上にある小さなアイコンは、タスクの種類を表します。シェルコマンドはターミナル、内部呼び出しはプラグ、結果の集約は重なったレイヤー、待機は南京錠、Claude や Codex に任せた 1 ターンは吹き出しです。Claude と Codex は同じ吹き出しを使い、どちらなのかはノードを押して詳細で確認します。

実行中のタスクは、処理内容によって表示が変わります。Claude や Codex のセッションが人の回答を待っていると、ノード全体が黄色に変わり、`!` マークと **入力待ち** <!-- en: Needs input --> ラベル、待機時間が表示されます。そのノードを押すと、詳細に **セッションを開く** <!-- en: Open session --> ボタンがあり、押すとそのセッションのタブに移動してすぐに回答できます。タスク DAG の一覧から押した場合は、一覧が閉じます。一覧でも、入力を待っているタスクがある DAG の行に `! 1 needs input` が付きます。結果を整える後処理中や、再試行を待っているタスクは、実行中の色のまま **後処理 · 1 回目** <!-- en: Postprocess · run 1 --> ・ **再試行待機 · 2 回目** <!-- en: Retry wait · run 2 --> のように、何回目の実行かが付きます。

一覧の各行と DAG タブの最上段には、終了したタスク数/全体数が表示されます。スキップされたタスクがある場合は、その後に `· 2 skipped (1 not selected)` のようにスキップ数が付き、そのうち分岐が選ばれなかったためにスキップされたタスクがあれば、括弧内にその数が付きます。

1 つのワークスペースで、互いに無関係なグラフを複数実行しても構いません。一覧は、依存関係でつながったまとまりを 1 つの DAG として表示します。タスクに `--metadata '{"dag":"名前"}'` を追加すると、接続の有無にかかわらず、同じ名前のタスクがまとめられます。

| 状態 | 意味 |
|---|---|
| **待機** <!-- en: Waiting --> | 依存先のタスクがまだ完了していません |
| **準備** <!-- en: Ready --> | 実行条件を満たしており、ランナーを待っています |
| **実行** <!-- en: Running --> | 実行中です |
| **成功** <!-- en: Succeeded --> · **失敗** <!-- en: Failed --> | 終了しました |
| **取消** <!-- en: Cancelled --> · **スキップ** <!-- en: Skipped --> | 人がキャンセルしたか、前のタスクが失敗したためスキップしました |
| **未選択** <!-- en: Not selected --> | 分岐で別の側が選ばれたため、実行しませんでした。失敗ではありません |
| **入力待ち** <!-- en: Needs input --> | 実行中の Claude・Codex セッションが人の回答を待っています。DAG の状態は実行中のままです |
| **不明** <!-- en: Unknown --> | 結果が分かりません。ノードを押すと、詳細にその理由が表示されます。Tasty の再起動中にコマンドが終了した場合や、再起動後も引き続き監視していたコマンドが後から終了し、終了コードを受け取れなかった場合です（再起動した Tasty は、そのコマンドの終了コードを受け取れません）。後続のタスクは待機し、再実行（`task-retry`）またはキャンセルしないと進みません。セマフォ・lease を保持するタスクも同じです。コマンドがまだ実行中なら、終了するまでリソースを保持し、終了後に解放します |

ターミナルで見るには:

```sh
tasty agent dag-list                                   # すべてのワークスペースの DAG
tasty agent task-list --workspace 2 --state waiting,ready,running
tasty agent task-get --workspace 2 --id "$BUILD"
tasty agent task-graph --workspace 2 --format dot   # Graphviz で描画
```

`--format dot` は、Graphviz にそのまま渡せるグラフだけを標準出力に書き込みます（例: `... --format dot | dot -Tsvg > graph.svg`）。循環があるという案内とランナーの状態は、標準エラーに出力されます。`dag-get --format dot` も同じです。

`task-list` と `task-get` は、人が読むための行を出力します。スクリプトで使う場合や、タスクが受け取った入力（`input_snapshot`）と元の結果（`typed_result.raw`）まで確認するには、`--json` を追加してください。Tasty が返した応答が、そのまま JSON として出力されます。

## タスクの待機と管理

```sh
tasty agent task-await --workspace 2 --id "$TEST"             # 完了するまで待機
tasty agent task-retry --workspace 2 --id "$TEST"             # 失敗・取消・スキップ・不明のタスクを再試行
tasty agent task-cancel --workspace 2 --id "$TEST"
tasty agent task-set-result --workspace 2 --id "$MANUAL" --state succeeded
tasty agent task-purge --workspace 2 --states succeeded
```

保存応答が失われても、完了記録を再確認すると、保留中の完了通知を復元します。無期限の待機も、確認済みの完了を受け取ります。保存結果が不明な要求を成功に変更することはなく、確認のためにコマンドを再実行することもありません。再起動をまたいで同じ完了イベントが再配信されることがあるため、イベントを処理するツールは `terminal_id` で重複を判別してください。完了記録を読み取れない場合は保持し、次のタスク変更時または再起動時に再確認します。

ランナーが停止している間にキャンセルしたタスクは、完了通知をすでに受け取っていても実行の後片付けを続けます。ほかのタスクの応答が先に処理されても、キャンセルしたコマンドと下流タスクの後片付けを省略しません。占有しているリソースは、終了を確認した後にだけ返却します。

- `task-await` は既定で最大 10 分待機し、その間に完了しない場合はタイムアウトとして返ります。`--timeout-ms 0` なら無期限に待機します。
- `task-await` 応答の `outcome` は、`terminal`（終了、`state` に succeeded・failed など）、`timed_out`（タイムアウト）、`not_found`（存在しないタスク）のいずれかです。3 つとも終了コード 0 なので、終了コードで成功を判断せず、`outcome` と `state` を読んでください。ルートオプション `--response-timeout-ms` は応答を待つ時間であり、タスクの待機時間ではありません。
- バリアの状態は `tasty agent barrier-state` で確認します。即座に返り、閉じるまで待機しません。以前の名前 `barrier-await` も同じ結果を返します。
- 型を指定したタスクは、フォールバックがすでに実行されていると `task-retry` が拒否されます。本来のタスクが再び成功すると、どちらか一方を受け取る次のタスクに値が 2 つ見えるためです。再実行するには、新しいタスクとして送信してください。
- 経路が選ばれずにスキップされたタスク（**未選択**）は、`task-retry` が拒否されます。再実行しても同じ理由ですぐにスキップされるためです。
- 型を指定したタスクには `--reset-downstream` を使えません。後続のタスクは、すでに前の実行の失敗や選ばれた経路に従って終了しているためです。`task-retry` はそのタスクだけを再実行します。後続のタスクまで再実行するには、新しいグラフとして送信してください。
- `task-set-result` は、ランナーが実行していない処理、たとえば人が手作業で行う確認手順を、完了したと報告するときに使います。
  - 型を指定したタスクは、実行のたびに実行回 ID（`<タスク ID>#<番号>`）を受け取ります。`--attempt-id` でどの実行回の結果かを明示すると、その間にタスクが再実行された場合、古い報告が新しい実行を終了させることなく拒否されます。
  - 同じ報告を再送すると、最初と同じ応答が返ります。すでに終了した実行回に別の結果を送信すると拒否されます。
- `task-cancel` で実行中のコマンドタスクをキャンセルすると、そのコマンドと、コマンドが起動したプロセスを終了させます。コマンドは終了していても、コマンドが起動したプロセスがまだ出力を保持していて、タスクが実行中と表示される場合も、そのプロセスを終了させます。出力を閉じて残ったデーモンは、タスクが終了するとタスクの一部と見なしません。終了を確認してからセマフォ・lease を解放するため、同じリソースを待っていたタスクは、前のコマンドが実際に終了した後で開始します。ランナーが停止していても、キャンセルすると終了処理を開始します。この場合、キャンセルコマンドは終了を待たずに即座に返り、セマフォ・lease は終了を確認してから解放します。その前に `task-retry` で再実行すると、前の実行回のプロセスがすべて終了したことをランナーが確認するまで、タスクは準備状態で待機します。このとき、`task-list` は行末に `(waiting_previous_attempt)` を、`task-get` は `phase: waiting_previous_attempt` 行を表示します。以前のキャンセルの後片付けが遅れて届いても、再実行中の新しい実行回とそのリソースの占有には影響しません。
- `task-delete` は、ほかのタスクから参照されている場合は拒否し、参照元の ID を通知します。実行中のタスクは先にキャンセルする必要があります。キャンセルしたタスクのプロセスが終了したことをまだ確認できていない場合も拒否します。終了を確認してセマフォ・lease を解放した後に削除できます。`task-purge` はこのようなタスクをスキップし、応答の `skipped`・`skipped_count` で通知します。

## 完了をイベントとして受け取る

タスクが完了したか繰り返し問い合わせる代わりに、完了するたびに受け取ることができます。

```sh
tasty events follow --filter 'agent.*'
```

1 行に 1 つのイベントが JSON として出力されるので、シェルでそのまま受け取って使います。

```sh
tasty events follow --filter 'agent.*' | while read -r line; do
  echo "イベント: $line"
done
```

- **読み取り位置は受信側で保存します。** 応答に含まれる `next_offset` を次回の `--offset` に渡すと、切断された位置から続行できます。一度だけ読み取る場合は、`tasty events fetch --offset <番号>` を使ってください。
- イベントはメモリにだけ残り、最近のものだけを保持します。長時間切断されていて、その間のイベントが保持範囲から外れた場合は、**何も知らせず最初から渡すのではなく**、何件渡せなかったかを通知します。その通知はイベント一覧と混ざらないよう別に出力されるため、上の `while read` は妨げられません。
- Tasty を再び起動すると、イベントは消え、位置も最初から振り直されます。応答に含まれる `epoch` が前回と異なる場合、保存した位置は再起動前の実行の値です。
- 接続が切れると、`follow` は再接続時に渡す `--offset` と `--epoch` を通知して終了します。そのまま指定して再実行すると、その間に Tasty が再起動されていた場合はその旨を通知し、新しく始まったイベントの先頭から受け取ります。`--reconnect` を指定すると、終了せずに 1 秒ごとに再接続して続行します。
- 現在出力されるのは、**タスクが終了したとき**と**バリアが閉じたとき**の 2 つです。タスクのイベントには、状態とともに実行回（`attempt_id`）、記録バージョン（`revision`）、スキップした理由（`skip`、前のタスクが原因ならそのタスクと状態）が含まれます。失敗理由はイベントに含まれないため、その場合は `tasty agent task-get` で確認してください。
- 読み取りが遅い受信側のために、別のキューを増やし続けることはありません。最近のイベントの共通保持範囲から外れた場合は、欠落を確認する必要があります。

## 同時実行の制限とシグナル

複数のタスクを実行するときに使う調整の仕組みも用意されています。

| 仕組み | 用途 |
|---|---|
| セマフォ | 同じ名前が付いたタスクを同時にいくつまで実行できるかを指定します。タスク作成時の `--concurrency-limit <名前>` が短い表記です。タスクに設定したセマフォの有効期限は、リースと同様に、ランナーがタスクを監視している間は延長し続けます |
| バリア | 指定した数のシグナルが集まるまで処理を止めます。`wait_barrier` タスクとしてグラフに挿入します |
| リース | ファイルなどのリソースを一度に 1 つの保持者だけが確保できるようにします。有効期限があり、競合すると失敗するか、取得できなかったという応答を即座に返します — 待機はしません。タスクに設定したリース（`metadata.lease`）の有効期限は、ランナーがタスクを監視している間は延長し続けるため、時間のかかるタスクも途中でリースを奪われません。ランナーが停止している間は延長しません。タスクに設定する有効期限は 1 秒以上である必要があります。それでも延長前に期限切れとなり、別の側がリースを取得した場合は、`task-get` に `warning:` 行が表示されます。この行は現在の実行回の内容だけを表示するため、再実行すると前の実行回の警告は表示されません |
| リデューサー | 複数のタスクの結果を 1 つにまとめます。最初の成功だけ、すべて、JSON マージ、テキスト連結から選ぶか、`custom:<シェルコマンド>` で自分でまとめます。このコマンドは入力結果を JSON 配列として標準入力から受け取り、標準出力が JSON ならその値を、そうでなければ文字列をそのまま結果に使います |
| リクエスト数制限 | エージェントごと・指標ごとに、指定した時間内に何回まで許可するかを指定します |

```sh
tasty agent semaphore-create --workspace 2 --name build --permits 2
tasty agent barrier-create --workspace 2 --name ready --count-required 3
tasty agent lease-acquire --workspace 2 --resource file:/tmp/db --holder agent-a --ttl-ms 60000
tasty agent task-reduce --workspace 2 --inputs "$A,$B" --strategy all --extract-path /stdout/text
```

セマフォ・バリアの名前には、英小文字・数字・`.`・`_`・`-` だけを使います。ほかの文字が含まれると、コマンドはどの文字に問題があるかを通知して拒否します。リースのリソース名には、この制限はありません。

一覧は `tasty agent --help` にあります。
