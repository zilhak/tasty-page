# フック・通知・ウェブフック

フックは Tasty のイベントに合わせて動作を実行し、通知は確認すべきことをアプリ内に表示します。ウェブフックは外部サービスの HTTP リクエストを受け取ります。必要な経路を選んで設定してください。

- イベントに反応するにはフックを設定してください。
- 通知は通知パネルとサーフェスの表示で確認します。
- 外部リクエストはウェブフックで受け取ります。受付の応答は実行完了を意味しません。
- 判断と応答を待つ必要がある場合は承認リクエストを使います。

## サーフェスフック

ヘッドレスインスタンスでもシェル終了フックが実行されます。サーフェスを閉じると、`--once` のないフックを含め、そのサーフェスに残っているフック登録も削除されます。

特定のサーフェス（ターミナル）でイベントが発生すると、シェルコマンドを実行します。

```sh
tasty set hook --surface 42 --event process-exit --command "tasty notify 'シェルが終了しました'"
tasty set hook --surface 42 --event 'output-match:error\[E\d+\]' --command 'tasty notify "$TASTY_HOOK_MATCHED_TEXT"'
tasty set hook --surface 42 --event idle-timeout:30 --command "tasty notify '30 秒間出力なし'" --once
tasty list hooks [--surface 42]
tasty unset hook --hook <HOOK_ID>
```

| イベント | タイミング |
|---|---|
| `process-exit` | シェルプロセスが終了したとき |
| `bell` | ベル（`\a`）を受け取ったとき |
| `notification` | ターミナル通知シーケンス（OSC 9/99/777）を受け取ったとき |
| `output-match:<正規表現>` | 出力の**完成した 1 行**が正規表現に一致したとき |
| `idle-timeout:<秒>` | N 秒間出力がないとき（1 秒単位、新しい出力が来ると再び待機します） |
| `command-completed` | シェル内でコマンドが 1 つ終了したとき（bash/zsh シェル統合が必要です） |
| `command-completed:<コード>` | その終了コードで終了したコマンドのみ（例: `command-completed:1` = 失敗したコマンド） |
| `claude-idle` / `needs-input` / `codex-idle` | Claude Code / Codex プラグインが送るイベント（[Claude・Codex](claude-codex.md)） |
| `claude-stop-failure` | Claude Code のターンが API エラー（サーバー過負荷・リクエスト上限・認証失敗など）で終了したとき。通常は `claude-idle` と一緒に届き、バックグラウンドタスクが残っている場合はこれだけが届きます |
| `claude-error` | Claude Code の画面出力に既知のエラーメッセージが表示されたとき |
| `claude-error-stalled` | Claude Code の出力がデフォルトで 10 分間（設定可能）変わらないとき。ターン中の最後の出力にエラーがある場合は 30 秒固定で、Monitor だけが残っている待機は除外します（[待機ごとの基準と受信条件](claude-codex.md#4-完了通知を受け取る)） |

- `--once` を付けると、1 回実行した後に自動で削除されます。デフォルトでは維持されます。
- フックコマンドはバックグラウンドで実行され、ターミナル入力を妨げません。
- `command-completed` はシェル統合なしでは一切発生しません。シェル統合のないローカルサーフェスには案内バナーが 1 回表示され、10 秒後に自動で閉じます。

コマンドにはイベント情報が環境変数として渡されます。

| 変数 | 値 |
|---|---|
| `TASTY_HOOK_EVENT` | 登録したイベント文字列（`bell`、`output-match:…` など） |
| `TASTY_HOOK_SURFACE_ID` | イベントが発生したサーフェスの ID |
| `TASTY_HOOK_MATCHED_TEXT` | `output-match` で実際に一致した行全体 |
| `TASTY_HOOK_EXIT_CODE` | `command-completed` の終了コード |
| `TASTY_HOOK_IDLE_ELAPSED_SECS` | `idle-timeout` で最後の出力から経過した秒数 |
| `TASTY_HOOK_CUSTOM_EVENT` | プラグインイベント（`claude-idle` など）の名前 |
| `TASTY_HOOK_SOURCE` | フックが実行した場合は `hook`、`tasty hook-handler dispatch` で直接実行した場合は `dispatch` |

`TASTY_HOOK_EVENT`・`TASTY_HOOK_SOURCE`・`TASTY_HOOK_SURFACE_ID` 以外の変数は、イベント情報のキー名から作られます。キーの英字・数字は大文字に、それ以外の文字は `_` に変換して `TASTY_HOOK_` の後ろに付けます（`matched_text` → `TASTY_HOOK_MATCHED_TEXT`）。シェルコマンドで動作するフックハンドラを `tasty hook-handler dispatch --body '{"build-id":7}'` で実行すると、`--body` オブジェクトの最上位キーも同じ規則で渡されます（`TASTY_HOOK_BUILD_ID=7`）。文字列はそのまま、それ以外の値は JSON テキストとして渡され、値ごとに 4096 バイトで切り詰められます。同じ名前が生成された場合は、先に作られた値を使います。

## グローバルフック

サーフェスとは関係なく、時間条件に従って実行します。

```sh
tasty set global-hook --condition interval:60 --command "df -h > ~/disk.log" --label "ディスク記録"
tasty set global-hook --condition once:300 --command "tasty notify '5 分経過'"
tasty list global-hooks
tasty unset global-hook --hook <HOOK_ID>
```

| 条件 | 意味 |
|---|---|
| `interval:<秒>` | N 秒ごとに繰り返します |
| `once:<秒>` | N 秒後に 1 回実行して削除します |

## フックハンドラ（再利用可能な動作）

`--command` の代わりに、あらかじめ登録した**フックハンドラ**を名前で関連付けられます。同じハンドラを複数のフックとウェブフックで共有します。

```sh
tasty hook-handler list                                     # 登録済みハンドラ (host / plugin / user)
tasty set hook --surface 42 --event bell --handler user/my-handler
tasty hook-handler get --id user/my-handler                 # 1 件の詳細 (実行する動作も含む)
tasty hook-handler dispatch --id user/my-handler            # 直接実行してテスト
tasty hook-handler reload                                   # ~/.tasty/hook-handlers.toml を再読み込み
```

`dispatch` は受け付けたことを示す行（`run` 番号を含む）を先に出力し、終了するまで待ってから結果の行を出力します。結果の `state` は、すべて成功すると `succeeded`、一部だけ成功すると `partial`、すべて失敗すると `failed`、応答を受け取れず結果がわからない場合は `unknown` となり、`result` と `steps` にどの段階がなぜ失敗したかが表示されます。シェルコマンドハンドラはプロセスが開始すれば成功とみなし、終了時の終了コードは参考としてのみ表示します。結果が `succeeded` でない場合、コマンドは終了コード 1 で終了します。待たない場合は `--no-wait` を付け、後で `tasty hook-handler result --run <番号>` で結果を確認してください。

ハンドラの**変更や新規作成**もコマンドで行えます。指定しなかった項目はそのままなので、
名前を維持したまま動作だけを変更できます（そのハンドラを参照するフックは変更に追従します）。

```sh
# 動作だけを変更 — まず get で現在の動作を確認し、その形式のまま返します
tasty hook-handler upsert --id user/my-handler \
  --calls '[{"method":"notification.create","params":{"body":"ビルド終了"}}]'

# 一時的に無効化 / 再び有効化
tasty hook-handler upsert --id user/my-handler --disabled true

# 自分で作った項目を削除
tasty hook-handler remove --id user/my-handler
```

変更内容はまず現在の実行に適用され、コマンドは `~/.tasty/hook-handlers.toml` の保存結果を受け取ってから終了します。保存の失敗はエラーとして表示され、現在の実行に適用された変更は維持されます。ただし、**作成済みのウェブフック URL は変更に追従しません** — ウェブフックは登録時点の動作をそのまま保持するため、新しい動作を使うにはそのウェブフックを再登録してください。

ユーザーハンドラは**設定** <!-- en: Settings --> › **ハンドラ** <!-- en: Handler --> › **フックハンドラー** <!-- en: Hook Handlers --> タブで追加・編集します。保存するとまず現在の実行に適用し、`~/.tasty/hook-handlers.toml` への書き込みはバックグラウンドで行います。保存できなかった場合はトーストと通知に表示され、次回起動時に変更が残らないことがあります。ファイルを直接編集することもできます（`tasty hook-handler reload` で反映します）。保存中は reload を拒否するため、完了後に再実行してください。ファイルの読み込みや形式にエラーがある場合は以前の設定を維持します。起動時に設定を読み込めなかった場合は、ログにファイル名と問題の種類を残し、ファイルの内容は記録しません。

一覧の各行にはハンドラを登録した側が表示されます — Tasty 自身は `host`、プラグインはそのプラグイン名、自分で作ったものは `you` です。削除できる行にだけゴミ箱が付き、それ以外の行には鍵が表示されます（Tasty とプラグインが起動するたびに自分のハンドラを再登録するためです）。複数の内部動作をつなぐハンドラは、その順序が 1 行で表示され、行末の**編集** <!-- en: Edit --> を押すとその場でテキストとして編集できます。1 行につき動作を 1 つ、メソッド名の後に必要に応じて JSON パラメータを記述します（`#` で始まる行はスキップされ、保存されません）。記述に誤りがある行があると、最初の問題とその行番号が入力欄の下に表示され、修正するまで**適用** <!-- en: Apply --> を押せません。適用した内容は、設定ウィンドウ下部の**保存** <!-- en: Save --> を押すとファイルに書き込まれます。入力欄内では Ctrl+Enter（macOS は Cmd+Enter）で適用、Esc でキャンセルします — この 2 つのキーは[キーバインド](../customize/keybindings.md)設定の**コード入力欄で適用**・**コード入力欄でキャンセル**で変更できます。Tasty やプラグインが登録したハンドラを編集すると、同じ名前の自分の設定として保存されます。このように保存したハンドラは、後で Tasty やプラグインがデフォルトの動作を変更しても**追従しません**。このような行には登録元の横に**編集済み** <!-- en: edited --> が表示され、2 行目の**元に戻す** <!-- en: Revert --> を押すとデフォルトに戻ります。元に戻す操作は**保存**を押すと適用され、それまでは**保存時に元に戻す** <!-- en: reverts on save --> の表示とともに、同じ位置の**取り消す** <!-- en: Undo --> でキャンセルできます。待機中はオン・オフのスイッチがデフォルト値でロックされ、**編集**も押せません — 変更するには先に**取り消す**を押してください。ターミナルでは `tasty hook-handler remove --id <id>` が同じ操作になります（自分の設定だけが削除され、元のハンドラが再び適用されます）。テキストに変換できない名前の動作が含まれる場合は、編集の代わりに **CLI で編集** <!-- en: Edit with CLI --> とコピーボタンが表示されます — コピーされる `tasty hook-handler get --id <id>` で内容を確認し、上記の `tasty hook-handler upsert` で変更してください。

```toml
[[handler]]
id = "user/notify-fail"
source = "hook"          # hook | webhook | any — どのトリガーがこのハンドラを使えるか
[handler.action]
kind = "shell_command"
command = "tasty"
args = ["notify", "コマンド失敗", "--title", "hook"]
```

`kind = "ipc_sequence"` にすると、シェルの代わりに Tasty 内部の動作一覧（`calls = [{ method = "...", params = {} }]`）を実行します。TOML には null がないため、params 内に null 値が必要な場合は、`params` の代わりに JSON 文字列で `params_json = '{"a":null}'` のように記述します。`tasty hook-handler upsert` で保存すると、この形式で自動的に記録されます。

フックが自動実行時に失敗すると、通知一覧に残ります。ハンドラがなくなった、またはコマンドを起動できなかったために実行自体が行われなかった場合は**エラー**、動作一覧の一部の段階だけが失敗した、または時間内に応答がなく結果がわからない場合は**警告**です。サーフェスフックの通知は、そのフックが設定されたサーフェスに関連付けられます。シェルコマンドが 0 以外の終了コードで終了した場合は失敗とみなしません。同じ失敗が短い間隔で繰り返される場合は、10 秒に 1 回だけ記録されます。

## 通知

### 送信

```sh
tasty notify "ビルド完了"                    # タイトルのデフォルトは "通知"
tasty notify "テストが 3 件失敗" --title "cargo test" --level error --surface 42
tasty list notifications
```

`list notifications` は、すべてのウィンドウの通知から、新しく作成された順に直近の 50 件を返します。通知 ID は同じ実行中であればウィンドウ間でも重複しません。短い間隔の通知が既存の項目に統合された場合、その項目の順序は維持されます。画面の通知パネルには、そのウィンドウの通知が表示されます。集計と明示的な既読コマンドは、すべてのウィンドウを対象にできます。


ターミナルプログラムが送る通知シーケンス（OSC 9 / 99 / 777）とベルも、同じ通知としてまとめられます。

重大な失敗は `--level error`、致命的でない問題は `--level warning`、情報は `--level info` で送ります。省略すると `info` になります。異なるレベルは統合されず、既読の項目に新しい内容が統合されると再び未確認の状態になります。

```sh
tasty notification counts
tasty notification counts --workspace 12
tasty notification read 7
tasty notification read --all --workspace 12
```

集計は、一覧の直近 50 件という制限に関係なく、保持されているすべての未確認通知を数えます。個別の既読処理には、`list notifications` に表示された通知 ID を使います。ワークスペースのフィルターなしで `read --all` を実行すると、すべてのウィンドウが対象になります。同じサーフェスの最後の未確認通知を既読にすると、その注意表示も解除されますが、ハード占有中は維持されます。通知数とサーフェス数は別々に集計します。

サーフェスと無関係な通知は `notify --workspace 12` で送ります。この呼び出しではサーフェスの注意表示を追加しません。ワークスペースを明示すると、環境のサーフェス ID は自動追加されません。

### 表示される場所

- **サイドバーの通知サマリー** — ツールボタンのすぐ上に、未確認のエラー（赤）・警告（黄）・情報（青）の件数が表示されます。0 件のレベルは非表示になり、99 件を超えると `99+` と表示されます。サイドバーを展開すると、最新の未確認タイトルも表示されます。サマリーを押すと通知パネルが開きます。ライトテーマの警告バッジは、明るい黄色の背景と暗い色の数字で表示されます。一覧の警告アイコンも背景と区別できる暗い色で、既読にした後も同じ色を維持します。
- **通知パネル** — サマリーのクリックまたは `Ctrl+Shift+I` で開きます。レベル・タイトル・本文・登録元・経過時間が新しい順に表示され、開閉するだけでは既読になりません。行または**もっと見る** <!-- en: More --> を押すと全文を展開し、その通知を既読にします。チェックボタンで 1 件を、**すべて既読** <!-- en: Mark all read --> でそのウィンドウの通知を既読にできます。**移動** <!-- en: Jump --> は通知を送ったサーフェスまたはワークスペースへ移動します。登録元が閉じられても記録は残り、移動ボタンは無効になります。タイトルバーから全画面に切り替えられます。新しい通知が届いても、パネルが自動で開いたり、見ていた一覧が先頭に移動したりすることはありません。既存の通知に内容が統合されて本文が長くなっても、読んでいた位置を維持します。
- **サーフェスの枠線** — 通知が発生したサーフェスに青い枠線が表示されます。Tasty ウィンドウがアクティブな状態でそのサーフェスにフォーカスすると消えます。別のアプリを見ている間は残り、ウィンドウに戻ると消えます。
- **サイドバーのバッジ** — 注意が必要なサーフェスがあるワークスペースの行に件数バッジが表示されます。
- **サウンド** — 設定で有効にすると、通知ごとにシステムのビープ音が 1 回鳴ります。

OS の通知センター（システム通知）には送りません。別のアプリを使っている間も気付けるようにするには、サウンドを有効にしてください。

### 設定

**設定** › **一般** › **通知** <!-- en: Notifications --> タブ、または `~/.tasty/config.toml`:

```toml
[notification]
enabled = true        # 通知を有効化
sound = false         # サウンド
coalesce_ms = 500     # 通知の統合間隔 (ms) — 同じ登録元からの連続した通知を 1 つに統合

[general]
bell_notification = true   # ベル通知を表示 (無効にするとベルのトーストだけを抑制し、bell フックは引き続き発火)
```

### 人の判断を待つ（承認）

タスクを進める前にユーザーの判断が必要な場合は、承認リクエストを送ってください。エージェントはリクエストを送った後、応答を待てます。

```sh
ID=$(tasty approval request --title "prod DB マイグレーションを実行しますか?" --severity danger \
      --choices "approve:実行,deny:中止:1" --timeout-ms 600000 | jq -r .id)
tasty approval await --id "$ID"            # 応答が届くまで待機し、結果を JSON で出力
```

- ポップアップが表示され、通知も送られます。ユーザーはポップアップのボタンをクリックするか、ポップアップ内で数字キー `1`~`9`（選択肢の順序）を押すか、`tasty approval respond --id <ID> --choice approve` で回答します。
- ポップアップはキーボードフォーカスを奪いません。ターミナルや文書に入力していた文字は、そのままそこに入力されます。数字キーで選ぶには、先にポップアップのタイトルまたは空白部分を押してください。ボタンはそのまま押せます。Markdown・HTML 文書に入力している場合は、その文書がポップアップと重なる部分を覆うことがあります。一緒に送られる通知でもリクエストを確認できます。
- コメント欄への入力中に押した数字はコメントの文字として入力され、選択肢は選ばれません。コメントを書いた後に数字キーで選ぶには、Tab でコメント欄から移動するか、ポップアップの空白部分を押してください。
- `--severity info` はポップアップなしで通知のみ、`warn`/`danger` はポップアップと通知を表示します。`danger` はユーザーが直接回答する必要があります。
- ポップアップは Esc では閉じません（回避防止のため）。`tasty approval list` / `get` / `history` で照会します。
- `approval await` はユーザー専用です。セッショントークン（`TASTY_SESSION_TOKEN`）で接続したエージェントは呼び出せないため、`tasty approval get --id "$ID"` で状態を確認してください（`approval` 権限が必要です）。
- `--metadata` の `kind` に `capability_elevation` は使えません。エージェントの権限リクエスト専用の値なので、リクエストが拒否されます。エージェントの権限は `tasty plugin request-permission` でリクエストしてください。
- リクエストはワークスペースに関連付けられます。`--workspace` を指定するとそのワークスペース、`--surface` だけを指定するとそのターミナルがあるワークスペース、どちらもない場合は現在表示しているワークスペースです（以前の表記 `--workspace-id`・`--surface-id` も受け付けます）。エージェントがリクエストする場合は、自分のターミナルを `--surface "$TASTY_SURFACE_ID"` で指定するのが安全です — ユーザーが別のワークスペースを見ていても、同じ場所に関連付けられます。

## ウェブフック（外部 → Tasty）

CI や他のサービスが HTTP リクエストを送り、Tasty 内の動作を起こせるようにします。Tasty はウェブフック用のポートを 1 つ開き、ウェブフックごとに推測しにくい URL を発行します。

ウェブフックは推測しにくい URL と、任意で設定する固定トークン（`--auth-*`）を使います。**HMAC 署名検証には対応していないため**、外部サービスが送った署名ヘッダーは検査しません。**認証を設定しなければ、URL にアクセスできる誰もが動作をリクエストできます。**必要な認証オプションを登録時に一緒に指定してください。

### ポートと外部からの受信

```sh
tasty webhook port                  # 実行中のリスナーのアドレス・ポートと決定方法
tasty webhook port 28500            # 次回起動からこのポートを使用
tasty webhook port --unset          # 保存したポートを削除し、次回起動から空きポートを自動選択
tasty webhook allow-external on     # 次回起動から他のコンピューターの呼び出しも受信 (off で元に戻す)
tasty webhook allow-external        # 保存値と実行中のリスナーが実際に開いたアドレスを表示
tasty --webhook-port 28500          # 今回の実行だけこのポートで起動
```

- **ポートを指定しない場合**は `28429` から 1 つずつ増やし、空いているポートを使います（最大 64 個、`28492` まで）。別の Tasty がすでに `28429` を使っていてもウェブフックは動作します。すべて使用中の場合は通知一覧に警告を残し、ウェブフックなしで実行します。
- **ポートを指定した場合**（`--webhook-port` または `tasty webhook port <N>`、両方ある場合は `--webhook-port` が優先）は、そのポートだけを使います。他のプログラムが使用中の場合は別のポートに移らず、**ウェブフックなしで起動します**。ターミナルは通常どおり使え、通知一覧にはポートと原因、修正方法を含む警告が 1 件残ります。このときウェブフック URL（保存した `--persistent` ウェブフックを含む）は応答しませんが、登録はそのまま残るため、ポートを修正して再起動すると同じ登録で再び受信します。URL のポートはその実行で開いたポートに変わるため、実際の URL は `tasty webhook list` で確認してください。`tasty webhook port` は `bound: false` と、`unavailable` に開けなかったポートと原因を表示します。別のポートで起動するか、保存したポートであれば `tasty webhook port --unset`（削除）または `tasty webhook port <空きポート>`（変更）を実行してから再起動してください。この 2 つのコマンドは、Tasty が実行中でなくても `~/.tasty/webhooks.toml` を直接変更し、その旨を知らせます。Tasty が実行中の場合は次回起動から適用されます。
- `tasty webhook config --port <N>` は以前の名前で、現在は推奨されていません（deprecated）。今も `tasty webhook port <N>` と同じように動作します。
- ポートが `28429` からずれ、`--persistent` で保存したウェブフックがある場合は、通知一覧に警告を残します。保存したウェブフックの URL のポートも変わるため、`tasty webhook list` で新しい URL を確認してください。URL が変わってはいけない場合は、ポートを指定してください。
- Tasty がすでに実行中のときに別の `--webhook-port` で再び起動すると、実行中の Tasty に引き継がず、案内を表示して終了します。同じポートであれば、通常どおり実行中の Tasty に新しいウィンドウを開きます。
- 以前のバージョンが自動的に書き込んだ `port = 28429` は初回起動時に削除され、自動選択に変わります。直接指定した他のポートはそのまま維持されます。
- **デフォルトでは、ウェブフックサーバーはこのコンピューター（`127.0.0.1`）からの呼び出しだけを受け付けます。**他のコンピューターや CI から直接呼び出す必要がある場合は、**設定 → 一般 → 他のコンピューターからのウェブフック呼び出しを受け付ける**を有効にするか、`tasty webhook allow-external on` を実行してから Tasty を再起動してください。`~/.tasty/config.toml` の `[webhook]` の下に `allow_external = true` と記述しても同じです。有効にすると、すべての IPv4 ネットワークインターフェース（`0.0.0.0`）で受信するため、ホストのファイアウォールが許可していれば、ルーターの転送設定なしでも同じネットワーク（社内ネットワーク・公衆 Wi-Fi など）からアクセスできます。ファイアウォールと認証設定を確認してください。HTTPS は手前のリバースプロキシで処理します。

### 登録

```sh
# 登録済みハンドラに関連付ける
tasty webhook register --method POST --handler host/webhook-notify --persistent

# インラインで動作を定義 — 本文の値を ${body.x} で取り込む
tasty webhook register --method POST \
  --sequence '[{"method":"notification.create","params":{"title":"CI","body":"${body.status}"}}]' \
  --ttl-secs 3600 \
  --auth-location header --auth-key X-Token --auth-token s3cret
```

登録すると、`http://127.0.0.1:<ポート>/<16 文字の id>` 形式の URL が出力されます。ポートは今回の実行で実際に開いたポートです。外部からの受信を有効にした場合は、外部から呼び出すときにホスト部分を実際のアドレスに置き換えます — その場ですぐに `curl` しやすいように入れてある表記です。返されたパスをそのまま使ってください。`/webhook/` プレフィックスは付けません。

| オプション | 意味 |
|---|---|
| `--method <M>` | 許可する HTTP メソッド（繰り返し指定可能、デフォルトは POST） |
| `--handler <id>` または `--sequence <json>` | どちらか一方が必須です |
| `--persistent` | 再起動後も維持します（デフォルトでは再起動時に消えます）。`--auth-token` も設定すると、そのトークンも `~/.tasty/webhooks.toml` に平文で保存されます |
| `--ttl-secs <秒>` / `--count <N>` | 時間制限 / **受け付けた**呼び出し回数の制限（どちらか一方）。認証で拒否されたリクエスト（`401`）と許可されていないメソッド（`405`）は回数を消費しません |
| `--auth-location query\|bearer\|body\|header` + `--auth-token` (+ `--auth-key`) | 任意の認証です。設定しなければ認証なしになります |

実行中にポートを照会または変更すると、ファイル処理が完了してから結果を受け取ります。保存できない場合は元の内容を維持してエラーを返し、実行中のリスナーのアドレスは変わりません。

永続ウェブフックの登録・解除は、ファイルの保存が完了してから結果を受け取ります。保存できない場合は以前の登録を維持します。保存を待っている間も、他の Tasty のタスクは続けられます。

ポート設定と永続登録は同じファイルに保存しますが、互いの内容を消しません。ファイルを読み込めない、または解析できない場合は、元の内容をそのままにして保存を拒否します。直接編集した場合、コメントと空白は次回の保存で変わることがあります。

`--ttl-secs` と `--count` を両方省略すると、呼び出し制限はありません。`--persistent` は各種の制限と併用でき、再起動時に期限や回数が残っている登録を復元します。

使用できるハンドラ id は `tasty hook-handler list` で確認します。`--sequence` は、Tasty 内部の動作（通知の送信、テキストの送信など）を順番に記述した JSON の一覧です。正しい JSON でなければ何も登録せず、原因を記したエラーで終了します（終了コード 1）。

### 応答と管理

呼び出したサービスには、ステータスコードと固定の応答メッセージが返されます。実際の動作の結果は応答に含まれません。

**`200` は「実行した」ではなく「受け付けた」という意味です。**応答は動作が始まる前に決まるため、動作がすべて失敗しても呼び出し側は `200` を受け取ります。複数段階の `--sequence` は、ある段階が失敗しても次の段階が続けて実行されるため、一部だけが適用された状態で終わることがあります。何が失敗したかは Tasty の通知一覧に残ります（どの段階も成功しなかった場合はエラー、一部だけ失敗した場合は警告）。ステータスコードで再試行を判断する CI では、`200` を「成功」と数えないよう注意してください。

| コード | 意味 |
|---|---|
| 200 `received` | 受付済み（動作はバックグラウンドで実行します） |
| 401 `unauthorized` | 認証失敗（繰り返すと 429 でブロックされます） |
| 404 | 存在しない URL |
| 405 | 許可されていないメソッド |
| 410 | 期限・回数の上限に到達 |
| 413 | 本文がリクエストごとのサイズ上限（デフォルトは 1 MiB）を超えています |
| 429 | 同じ送信元が 10 秒間に 20 回以上失敗（`401`・`404`・`405`・`413`）し、60 秒間ブロックされています |
| 503 `unavailable` | リクエストを受け付けられなかったか、保存結果を確定できませんでした。動作は実行しません |

本文のサイズ制限は認証より先に適用されます。チャンクで送信した本文に不正な UTF-8 バイトがあっても、同じサイズ制限が適用されます。トークンがなくても本文が上限を超えると `413 payload too large` を受け取り、動作は実行されません。この上限は処理する本文のサイズを制限します。413 の応答には `Connection: close` が付き、サーバーは残りの本文を受け取らずに接続を閉じます。ブロック中（`429`）のリクエストも同様です。同じ接続で次のリクエストを送れないため、新しい接続を開いてください。本文を送信している途中だった場合は、接続がリセット（reset）で切断されることがあります。総メモリ量や同時接続数を制限する機能ではありません。

回数・期限の変更を保存できなかったことが確認された場合は、警告を残し、それまでどおり受付と動作を続けます。この場合、再起動後に保存できなかった変更が元に戻ることがあります。受付を拒否した場合や保存結果がわからない場合は、`503` を返し、動作を実行しません。結果が不明確になった後は、Tasty を再起動して保存済みの登録を復元するまで、新しい変更を拒否します。

ブロック状態はメモリ内にしかありません — Tasty を再起動すると残りのブロック時間が消え、その送信元は再び最初から始まります。

```sh
tasty webhook list
tasty webhook info --id <ID>
tasty webhook unregister --id <ID>
tasty webhook sweep                 # 期限切れのウェブフックを一括削除
```

ウェブフックはシェルコマンドを直接実行できません（Tasty 内部の動作のみ）。シェルが必要な場合は、ウェブフック → 通知 → サーフェスフックのようにつないでください。

## 組み合わせの例: 長時間のビルドが終わったら通知する

```sh
tasty set hook --surface 42 --event command-completed --once \
  --command 'if [ "$TASTY_HOOK_EXIT_CODE" = 0 ]; then tasty notify "ビルド成功" --title build; else tasty notify "ビルド失敗 ($TASTY_HOOK_EXIT_CODE)" --title build; fi'
tasty send text "cargo build --release\r" --surface 42
```

`command-completed` はすべての終了コードに反応し、`command-completed:0` のように整数を 1 つ付けると、そのコードの場合だけ反応します。実際の終了コードは、フックコマンドに `TASTY_HOOK_EXIT_CODE` 環境変数として渡されます。
