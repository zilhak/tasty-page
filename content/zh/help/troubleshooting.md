# 故障排除

本页按症状列出 Tasty 安装、输入、显示、恢复和通知问题的原因及解决方法。如果 CLI 无法连接或响应缓慢，也可查看连接诊断。问题仍未解决时，可附上运行环境和日志报告问题。

## 安装和首次启动

- **Windows：出现“Windows 已保护你的电脑”警告** — 原因是没有代码签名。点击**更多信息 → 仍要运行**。
- **macOS：提示“身份不明的开发者”，无法打开** — 这是 Gatekeeper。在**系统设置 > 隐私与安全性**中允许，或在终端运行 `xattr -dr com.apple.quarantine /Applications/Tasty.app`。
- **Linux：AppImage 无法运行** — 缺少执行权限或 FUSE。先运行 `chmod +x Tasty-*.AppImage`，仍无法运行时，使用 `./Tasty-*.AppImage --appimage-extract-and-run` 启动。
- **Linux：提示 `GLIBC_2.39 not found`，无法运行** — 发行版比构建基准（Ubuntu 24.04）更旧，例如 Ubuntu 20.04 · Debian 11。不提供适用于旧发行版的构建。
- **Linux `.tar.gz`：提示缺少库后退出** — `tasty` 会列出缺失的共享库文件名后退出。使用同时显示的搜索命令（从 `apt-file search` · `dnf provides` · `zypper what-provides` · `pacman -F` 中选择适合发行版的命令），查找并安装提供该库的软件包。要自动安装所需的库，使用 `.deb` / `.rpm`。
- **窗口未显示便立即退出，日志中留下“找不到 GPU 适配器”** — 未找到可用的 GPU 适配器（Vulkan / DirectX 12 / Metal）。此错误不会单独显示在界面中，只记录在 `~/.tasty/debug.log` 和终端输出中（从终端启动时）。安装或更新驱动程序。Linux 上存在 `libvulkan1` / `vulkan-loader` 时使用 Vulkan，否则使用 OpenGL，再失败则使用软件渲染。要在没有图形界面的服务器 · VM 上运行，使用[无界面构建](../getting-started/install.md#无界面构建)。
- **Windows：启动时显示 Shell 选择界面，或无法打开新终端** — Tasty 在 Windows 上仅运行 Git Bash。Shell 设置不是 Git Bash（包括文件夹路径）、配置的路径下没有文件，或设置为空且默认安装位置也未找到 Git Bash 时，会出现此问题。启动时会显示**选择 Shell** <!-- en: Choose a shell --> 界面；运行期间，**设置** <!-- en: Settings --> > **终端** <!-- en: Terminal --> 标签页会显示原因，且无法打开新终端。安装 Git for Windows，或在其位于其他位置时输入对应的 `bash.exe` 路径。在 Shell 选择界面输入路径并点击**使用此 Shell** <!-- en: Use this shell -->。运行期间，在**设置** > **终端** > **Shell** <!-- en: Shell --> 中修正路径。Git for Windows 的 `usr\bin\bash.exe` 也可使用，但如果 Git 不在 Windows 的 `PATH` 中，该 Shell 将找不到 `git` 命令；改为输入 `bin\bash.exe`。
- **打开的 Shell 与配置的 Shell 不同** — 在 macOS · Linux 上，如果配置的 Shell 路径下没有文件，Tasty 会使用找到的其他 Shell（登录 Shell 或 `$SHELL`）打开终端。配置文件中的 Shell 值不会更改，因此修正路径或重新安装该 Shell 后，新终端便会恢复使用原来的 Shell。替代使用的 Shell 会记录在 `~/.tasty/debug.log` 中，**设置** <!-- en: Settings --> > **终端** <!-- en: Terminal --> 标签页也会显示说明。在 Windows 上，Tasty 不会换用其他 Shell；参见上方的 Windows 条目。
- **macOS · Linux：启动时立即显示 Shell 选择界面，或设置中显示 Shell 错误** — 配置的 Shell 路径是文件夹，或是没有执行权限的文件。此时 Tasty 不会换用其他 Shell，而是显示原因。首次启动时，**选择 Shell** <!-- en: Choose a shell --> 界面的检查结果行会显示“此路径是文件夹”或“此文件没有执行权限”。运行期间，**设置** <!-- en: Settings --> > **终端** <!-- en: Terminal --> 标签页会显示相同原因，且无法打开新终端。将路径改为 Shell 可执行文件路径，或使用 `chmod +x` 赋予执行权限。
- **启动后立即显示“无法启动终端”界面** — 无法打开首个终端。正文的“详细信息”中会显示原因。解决原因后重新运行。如果在运行期间打开新窗口时因相同原因失败，**无法打开新窗口** <!-- en: Could not open a new window --> 提示中会显示原因，已打开的窗口仍正常运行。
- **通知中出现“最近列表和教程进度未保存”** — 无法打开保存最近文件列表和教程进度的 `~/.tasty/state.db`。Tasty 仍可使用，终端和布局恢复不受影响，但无法加载之前保存的最近列表和教程进度，本次运行中的更改也不会保存。本次运行中通过文件浏览器访问的文件夹，可能仍会显示在该窗口运行期间的最近列表中，但下次运行时不会保留。通知正文会显示原因。“数据库已锁定”表示另一个 Tasty 已在运行。如果显示“已损坏”/“架构版本不匹配”，关闭 Tasty，备份并删除 `~/.tasty/state.db`，下次运行便会重新开始。解决原因后必须重新运行 Tasty，才会恢复保存。
- **显示“无法启动 Tasty”界面，终端未打开** — 准备首个窗口时，Tasty 的内部步骤失败。“详细信息”中会显示原因。点击**退出** <!-- en: Quit --> 或按 Esc · Enter 关闭后，Tasty 会退出。重新运行；如果持续重复，检查数据文件夹（`TASTY_HOME`，默认 `~/.tasty`）是否可用，并查看 `~/.tasty/debug.log`。无法显示界面的环境中，相同内容会通过消息框显示（Linux 上没有 zenity 时，使用桌面通知）。
- **在 Tasty 终端中输入 `tasty`，但没有打开新窗口** — 在 Tasty 内不带参数运行时，会显示帮助，而非打开新窗口。使用 `tasty new window` 打开新窗口（当前查看窗口的焦点保持不变）。

安装步骤见[安装](../getting-started/install.md)。

## Linux 上无法查看文档或与外部应用复制和粘贴时

Tasty 使用原生 Wayland 运行时，无法查看 HTML、Markdown、远程 HTML 文件和网址。无法通过终端的复制和粘贴或文件浏览器的文件复制、剪切和粘贴，与外部应用交换剪贴板内容。原生右键菜单也尚未显示。

设置输入框、工作区重命名、地址栏等处可与其他应用相互复制和粘贴文本。

根据原因，按以下方式处理。

- 未设置 `DISPLAY` 时，由于没有 XWayland，Tasty 使用原生 Wayland 运行。在 Tasty 外部启用 XWayland 后重启 Tasty。
- 设有 `DISPLAY`，但无法连接其 X 服务器，且设有 `WAYLAND_DISPLAY` 时，会记录警告并使用原生 Wayland 运行。在 Tasty 外部检查 `DISPLAY` 的 X 服务器或 XWayland 连接后重启 Tasty。

HTML、Markdown 和远程 HTML 文件 Surface 的页面区域以标题显示原因，下方一行显示解决方法。远程 HTML 文件在接收期间显示接收状态，接收完成后显示此说明。在终端复制和粘贴，或在文件浏览器复制、剪切和粘贴文件时，会显示包含原因和解决方法的警告短暂提示。短暂提示的显示时长遵循全局设置。

<a id="linux-gdk-backend"></a>

## Linux 上无法查看文档或使用托盘图标时

即使设有 `DISPLAY` 且 Tasty 窗口使用 X11 运行，若 Tasty 启动环境中的 `GDK_BACKEND` 不允许 x11，GTK 初始化也会失败。此时无法使用托盘图标，也无法查看 HTML、Markdown、远程 HTML 文件和网址。右键菜单也尚未显示。窗口使用 X11 运行，因此剪贴板正常工作。

在 Tasty 外部从 Tasty 启动环境中移除 `GDK_BACKEND` 后重启 Tasty。Tasty 不会删除或覆盖此值，终端内的 Shell 也会原样接收用户设置的值。

页面区域显示原因和解决方法，标题也会说明托盘图标不可用。托盘本身没有单独的说明。

### `GDK_BACKEND` 并非原因但 GTK 初始化失败时

未设置 `GDK_BACKEND` 或其允许 x11 时，GTK 初始化仍可能失败。此时同样无法使用托盘图标或查看 HTML、Markdown、远程 HTML 文件和网址，右键菜单也尚未显示。窗口使用 X11 运行，因此剪贴板正常工作。

应用仅显示 GTK 初始化失败的说明，没有解决方法一行。此时 Tasty 无法确定原因。查看[日志和配置文件位置](#日志和配置文件位置)中的警告日志，并附上[报告问题](#报告问题)中列出的信息。

## macOS 权限提示

**症状** — 工作期间弹出权限提示，导致正在进行的工作停下。终端中的命令（及其中的智能体）首次访问新文件夹时都会出现。

**原因** — 终端中运行的命令读取文件时，macOS 将该访问视为 Tasty 的访问（Terminal.app · iTerm2 也一样）。macOS 只在实际访问时询问，因此如果没有提前授予权限，提示便会在工作期间出现。

**解决方法 — 提前一次性授予权限。** 在**设置** > **常规** <!-- en: General --> > **权限** <!-- en: Permissions --> 中点击**请求所有权限** <!-- en: Request all permissions -->，会依次询问下载 · 文稿 · 桌面文件夹 →（已连接时）外置 · 网络宗卷 → 屏幕录制权限。回答前一个提示后才会出现下一个，提示显示期间窗口仍正常运行。已经允许或拒绝的项目不会再次询问，因此可以多次点击。连接新宗卷后再次点击，只会额外询问该宗卷的权限。

Tasty 启动时**不会自动弹出提示。** 这是为了避免首次打开应用时出现一连串原因不明的提示。如果仍有未授予的权限，启动时会显示说明，引导至此界面。

**如何选择**

| 权限 | 不允许时 | 之后如何更改 |
|---|---|---|
| 文件夹访问（下载 · 文稿 · 桌面 · 宗卷） | 读取或写入该文件夹的命令可能失败 | 系统设置 > 隐私与安全性 > 文件与文件夹 |
| 屏幕录制 | `Ctrl+Alt+S` 截图 → 剪贴板功能只会显示“需要屏幕录制权限”提示。拒绝一次后不会再次询问 | 系统设置 > 隐私与安全性 > 屏幕与系统音频录制 |

也可在同一标签页查看当前状态（仅在 macOS 上显示）。应用无法请求完全磁盘访问权限，因此此按钮不包含该权限。使用完全磁盘访问权限行的**打开系统设置** <!-- en: Open System Settings --> 打开系统设置，手动添加。文件夹权限无法自动检查，因此显示为“无法自动检查” <!-- en: Cannot check automatically -->。

- **出现“部分权限尚未授予”提示** — 只要看起来缺少完全磁盘访问权限或屏幕录制权限，每次启动都会显示。可在**设置** > **常规** > **权限**标签页查看各项权限及其状态。点击**打开权限设置** <!-- en: Open permission settings --> 会打开 Tasty 的权限界面。应用无法直接请求完全磁盘访问权限，必须使用该界面完全磁盘访问权限行中的**打开系统设置** <!-- en: Open System Settings --> 打开系统设置，并手动将 Tasty 加入列表。授予此权限后，文件访问提示（其他应用的数据 · 下载 · 文稿 · 桌面 · 宗卷）会消失。不过，控制其他应用（Automation）· 屏幕录制是独立权限，仍会保留。授予权限后，下次启动起便不会显示该提示。没有关闭此提示的设置，因为如果记录了关闭状态，以后权限被重置时便无法告知。
- **已授予所有权限，但仍出现文件夹访问提示** — 启动提示只检查能够确认的权限。下载 · 文稿 · 桌面 · 宗卷等文件夹权限不参与提示判定，因为为检查权限而访问文件夹时，可能弹出权限请求对话框。授予完全磁盘访问权限后，也能访问这些文件夹。
- **已授予权限，但提示再次出现** — 下载的发行版和自行构建的 Tasty 均使用 ad-hoc 签名，因此更新或重新构建后，macOS 会将其视为另一个应用。此时，即使系统设置的完全磁盘访问权限列表中 Tasty 仍处于开启状态，该条目也可能已不再生效。如果曾在具有该权限的状态下启动过 Tasty，提示会识别此情况，并要求从列表中移除 Tasty 后重新添加。如果应用未变但权限已关闭，会提示重新开启；如果通过 `tccutil reset` 等操作使 Tasty 从列表中消失，会提示重新添加。**设置** > **常规** > **权限**中的完全磁盘访问权限行也会将状态保持为“未允许”，并在下方一行显示相同的处理方法（即使显示已开启也不生效，需移除后重新添加；或重新开启；从列表消失时，通过 + 重新添加）。自行构建时，使用 `./scripts/macos-codesign-identity.sh --create` 创建一次“Tasty Dev”证书，之后的构建使用同一证书。使用证书也不能保证权限保留，因此还需在系统设置中检查状态。刚换用证书后，也需从列表中移除原有 Tasty 并重新添加。
- **完全磁盘访问权限状态显示“未知”** <!-- en: The Full Disk Access status shows "Unknown" --> — macOS 没有可查询此状态的 API，因此通过推断获取。如果当前 macOS 版本中不存在用于推断的文件，便没有判断是否允许的依据，会显示未知，也不会因该权限而显示启动提示（屏幕录制未获批准时，仍会因此显示）。此值不会阻止任何功能。
- **每个应用文件夹都不断弹出“Tasty 想要访问其他应用的数据”** — `~/Library/Application Support/<应用>` 等路径会按应用分别询问，因此即使使用**请求所有权限**也无法提前授予。授予上述完全磁盘访问权限后便会消失。
- **使用 `osascript` 时出现“想要控制其他应用”** — Automation 权限必须按目标应用分别批准，完全磁盘访问权限也不涵盖。Tasty 无法提前处理。

## 在 Linux X11 上重启输入法后无法输入韩文时

Tasty 检测到 XIM 输入法服务器退出或被替换后，会停止向旧服务器发送请求，并重新连接
新服务器。连接恢复前可能改用本地输入，因此可能暂时无法组合输入韩文。
检查 ibus 是否已重新运行，并已选中韩文引擎。

服务器在连接协商期间或存活检查刚结束时退出，或服务器仍在运行但不响应时，
仍可能发生无响应。如果整个窗口持续无响应，报告问题时保留下文所述的无响应记录。
此说明适用于 X11，不适用于 Wayland · macOS · Windows 的输入方式。

## `tasty` 命令无法连接时

- **`No running tasty instance found (port file not found at …)`** — CLI 检查的路径中没有端口文件。如果消息中的路径不是 `~/.tasty/tasty.port`，则正在查看其他主目录（`TASTY_HOME`）。此消息遵循配置语言（`general.language`，默认为英语），因此设为韩语时，会显示“找不到正在运行的 tasty 实例”。参数错误时（JSON 损坏、`--cwd` 文件夹不存在等），会先显示该参数的错误，再显示此消息，因此看到此消息意味着已通过连接前的参数检查。
- **端口文件存在，但无法连接** — 可能是上次运行留下的文件，或正在查看其他实例的路径。检查错误中的路径和 `TASTY_HOME`，确认使用该文件的 Tasty 实例是否已退出。只有文件属于已退出实例的残留文件时，才手动删除并重新启动。不要仅凭进程名称搜索结果删除文件。如果文件在启动后被替换，或其他进程正在保存，Tasty 退出时可能会保留该文件。
- **启动时出现端口文件保存错误** — 检查当前账户是否能读写该文件及其父文件夹。无法读取的原文件不会被覆盖。由于必须能够替换整个文件，父文件夹也需要写入权限。
- **可以连接，但响应缓慢，或以 `Error (-32061)` · `Error (-32065)` 等行结束** — 没有响应时，不要使用 Shell 的 `timeout` 中断 `tasty` 后重复相同请求。关闭连接不会取消已发送的请求。Tasty 忙碌期间积累的请求可能稍后集中执行；如果是发送输入的命令，相同输入便会重复。

  如果需要限制响应等待时间，对单次请求即可完成的命令使用 `--response-timeout-ms`，并将标志放在命令前。未能在期限内开始处理的请求会以 `Error (-32067)` 结束，之后也不会执行。开始处理后超过期限时，会以 `Error (-32061)` 结束，结果未知，任务可能继续。反复查询或保持连接的命令收到此标志时，不会发送请求，而是以退出码 2 拒绝。可以重新发送的情况和需先检查状态的情况见[设置响应等待上限](cli-diagnostics.md#设置响应等待上限)。其他错误码的处理方法及 `tasty list pressure` 的解读方式见 [CLI 响应延迟与连接诊断](cli-diagnostics.md)。


- **`tasty: command not found`** — Tasty 打开的终端会自动将其加入 PATH；通过 `.deb` · `.rpm` · `.msi` 安装时，在其他终端应用中也可找到。其他安装方式需手动添加。各安装方式的路径见[安装位置](../getting-started/install.md#安装位置)。

## 点击按钮或按下快捷键后提示无法完成操作时

更改布局、移动分隔线、重置类别、启动远程连接等用户操作失败时，界面会显示一次失败提示。如果无法确认分隔线位置，会恢复到原来的位置。类别重置失败意味着设置未更改。检查界面当前状态后重试。如果持续失败，报告问题时附上 `~/.tasty/debug.log` 中同一时刻的记录。智能体命令的失败会通过命令响应或日志传达，而非界面上的短暂提示。

## 出现无法打开链接或文件夹的通知时

终端链接、通过系统默认应用打开的文件，以及插件窗口中的主页和安装文件夹，都会交给操作系统的默认程序打开。如果无法启动该程序，便会显示通知。

- **Linux** — 检查是否已安装 `xdg-open`，或 `BROWSER` 环境变量是否指向可执行的浏览器。会在启动 Tasty 时所用环境的 `PATH` 中查找。
- **macOS · Windows** — 在系统设置中检查是否有与该地址或文件类型关联的默认应用。

如果没有通知，也没有任何反应，说明默认程序已启动，但该程序无法打开。检查该程序。

## 无法通过命令打开文件选择弹窗时

- **脚本或智能体尝试通过 IPC 打开文件选择弹窗时，出现 `-32016` 错误** — 这是正常行为。文件选择弹窗由用户通过侧边栏的**工具** <!-- en: Tools --> > **打开文件…** <!-- en: Open File… --> 打开，或由插件打开（例如在 Markdown 的打开文件中点击**浏览…** <!-- en: Browse… --> 时）。因为命令弹出弹窗会夺走正在输入位置的焦点，所选路径也不会返回给该命令。脚本和智能体应直接指定文件路径。

<a id="不知道开发服务器使用哪个端口时"></a>

## 查找开发服务器端口时

在侧边栏的**工具** <!-- en: Tools --> 菜单中打开**监听端口…** <!-- en: Listening ports… -->。会显示 Tasty 终端所启动进程打开的 TCP 端口，以及端口 · 进程 · 工作区 · 标签页。

- 默认仅显示 LISTEN 状态。如果列表为空并显示“没有符合状态筛选条件的端口”，可能仍有其他状态的端口 — 使用筛选行右侧的**状态** <!-- en: State --> 按钮启用其他状态，再点击**应用** <!-- en: Apply -->。
- 要查看 Tasty 外部的进程，开启**显示全部（整个系统）** <!-- en: Show all (system-wide) -->。
- 点击选中一行，使用**复制地址** <!-- en: Copy address --> 将 `host:port` 放入剪贴板。
- 使用星形图标加入收藏后，会始终显示在顶部，重启后也会保留（`~/.tasty/port-favorites.toml`）。其他窗口中更改的收藏也会立即显示。

<a id="窗口无响应或崩溃时"></a>

## 窗口无响应或意外退出时

- **窗口对点击 · 按键输入 · CLI 完全无响应** — 无响应超过 5 秒时，会自动生成 `~/.tasty/crash-reports/hang-*.log`。文件中的 `Render phase` 为 `acquire` / `submit` / `present` 时，表示停在对应渲染阶段。可能是 GPU 驱动程序问题，因此也需检查驱动程序更新。Tasty 不会自行恢复，需强制退出后重新启动。
- **突然退出** — 查看 `~/.tasty/crash-reports/crash-*.log`。报告问题时附上此文件。

### 运行期间提示已停止保存时

如果窗口右上角出现 **Tasty 已停止，需要重新启动** <!-- en: Tasty stopped and needs a restart --> 提示，且通知中留有一条错误，说明将工作区 · 窗格 · 标签页布局保存到 `~/.tasty/structure/journal.db` 时失败。为保护已保存的布局，Tasty 不会应用后续更改。

- 此状态下，按键输入和点击不会传递给终端或其他界面，`tasty` 命令也会被拒绝。提示中的**继续** <!-- en: Continue --> 或 × 只会关闭提示。
- 使用窗口关闭按钮退出 Tasty，然后重新运行。此状态下会直接退出，不会再次询问。
- 原因显示在提示下方，也会记录在 `~/.tasty/debug.log` 中。如果重新运行后仍显示相同提示，检查存储所在磁盘的剩余空间和权限，报告问题时附上日志。

## 设置或窗口布局看似被重置时

布局未恢复时，先检查**启动时恢复布局** <!-- en: Restore layout on startup --> 设置和通知。如果提示无法打开存储，检查提示中的位置和原因。原始存储无法读取时启动的临时布局，不会保留至下次运行。此限制不适用于在终端中编辑的项目文件。

- **设置恢复为默认值** — 如果 `~/.tasty/config.toml` 无法解析为 TOML，会以默认值启动。原文件不会被删除。文件会先保留原处，直到保存设置、重新写入文件时，才移至同一文件夹下的 `config.toml.bak`。打开该文件修正后，改回 `config.toml` 即可恢复设置。有问题的行会记录在 `~/.tasty/debug.log` 中。
- **提示无法恢复已保存的工作区** — 不会仅因记录累计大小而阻止终端启动。如果无法继续恢复，会保留原始数据，并使用仅限本次运行的空工作区继续。仍可输入终端和新建标签页，但本次布局不会保存至下次运行。检查磁盘剩余空间和数据文件夹权限后重新启动。磁盘写入失败不会被视为保存成功，原因会显示在通知中。
- **已保存的窗口布局未恢复** — 先检查**设置** > **常规** > **启动时恢复布局** <!-- en: Restore layout on startup --> 是否开启。工作区 · 窗格 · 标签页布局保存在 `~/.tasty/structure/journal.db` 中。旧版本使用的 `~/.tasty/layouts/` 下的 `01.json` 等文件，仅在首次迁移至新存储时读取一次，因此之后修改或删除这些文件都不会改变恢复的布局。如果无法打开存储，Tasty 会以新的默认工作区启动，并在显示错误通知的同时，在窗口右上角显示**无法恢复上次会话** <!-- en: Couldn't restore your last session --> 提示。提示中会显示原因和存储位置，通知条目中包含详细错误，相同内容也会记录在 `~/.tasty/debug.log` 中。不会更改、移动或删除存储文件。本次运行的布局记录（工作区 · 标签页及恢复它们所需的记录）会在 Tasty 退出后消失（不影响在终端中更改的文件），下次运行会重新读取存储。恢复读取权限后，原布局便会恢复。使用**继续** <!-- en: Continue --> 或 × 关闭提示；提示显示期间仍可正常输入终端。另一个 Tasty 正在使用同一数据文件夹时，不会启动，而会显示原因界面。报告问题时附上日志。 <!-- TODO verify: 是否有供用户从损坏的 journal.db 中恢复布局的步骤 -->
- **出现“无法导入旧布局文件”通知** <!-- en: "An old layout file could not be imported" --> — 无法将旧版本使用的 `~/.tasty/layouts/01.json` 等文件作为布局读取。该窗口会以新的默认工作区启动，文件保持原样。没有文件读取权限时，会显示错误通知，并在窗口右上角显示提示。以新布局启动一次后，即使修正文件也不会再次导入。
- **出现“部分终端内容未恢复”通知** <!-- en: "Some terminal contents were not restored" --> — 导入旧版本文件时，部分终端保存的内容文件不存在或无法读取。布局会正常恢复，仅这些终端不带之前的输出启动。
- **出现“无法恢复所选标签页”通知** <!-- en: "Selected tabs could not be restored" --> — 工作区和标签页布局已恢复，但无法读取最后选中的工作区 · 标签页记录。启动时会选中第一个工作区和标签页。无法读取的记录会保留在通知所示位置（通常为 `~/.tasty/structure/damaged/`），不会自动删除。
- **出现“无法恢复部分已保存的布局”通知** <!-- en: "Part of the saved layout could not be restored" --> — 无法读取某个窗口的保存记录。仅该窗口不恢复，而是以新布局启动，其他窗口正常恢复。无法读取的记录会保留，不会删除。通知中会显示布局编号和原因。
- **出现“已从较早的保存点恢复”通知** <!-- en: "Restored from an earlier save point" --> — 无法读取最新保存点，因此使用较早的保存点和之后的记录重建布局。之后的记录都会重新应用，因此布局保持不变。
- **某个标签页打开为空终端，并出现“无法恢复某个标签页”通知** <!-- en: A tab opened as an empty terminal with "A tab could not be restored" --> — 无法读取该标签页保存的内容（工作文件夹 · 之前的输出 · 恢复命令）。其他标签页和工作区正常恢复，该标签页会按当前 Shell 设置重新启动。无法读取的原始数据仍保留在存储中，不会删除。通知中会显示所属工作区、标签页及原因。
- **出现“布局已停止保存”通知** <!-- en: "Layout is no longer being saved" --> — 为保存运行中的布局和终端内容而一次性汇集的 Surface 捕获请求超过了 64 MiB 上限。此上限适用于一次保存同一运行引擎所属全部 Surface 的请求，并非整个存储或单个工作区的磁盘容量限制。会跳过整个请求，不会仅保存其中一部分。最后保存的状态会保留，但之后的更改不会在下次运行时恢复。清除输出积累较多的终端的回滚缓冲区。布局更改或记录减少时会重试，请求大小回到上限以内后会恢复保存。相同原因只会通知一次，直到再次保存成功。
- **出现“保存持续失败”通知** <!-- en: "Saving keeps failing" --> — 布局或所选标签页连续 3 次保存失败，中间没有成功。一两次临时失败会在下次保存时重试，因此不会通知。Tasty 会继续重试，但在保存成功前，最后一次保存后的更改不会在下次运行时恢复。解决通知中的原因（磁盘空间不足、权限等）后，下次保存便会恢复正常。完整原因也会记录在 `~/.tasty/debug.log` 中。
- **出现“无法保存，请移动或删除 `.bak` 文件”通知** — 尝试将配置文件（`config.toml`）的原文件移到一旁时，`.bak` 到 `.bak.9` 的九个位置已全部占用，没有位置可放。为避免删除原文件，已停止保存，该会话期间会一直无法保存。移动或删除积累的 `.bak` 文件中不需要的文件，然后重新启动即可恢复正常。
- **出现“无法读取配置文件”通知** — 文件存在，但**无法读取**（权限问题或磁盘错误）。此时 Tasty 不会修改该文件，也不会保存 — 保持原样时，当前界面中的默认值不会覆盖原设置。修正权限或将文件改名移开后重新启动。

  ```sh
  ls -l ~/.tasty/config.toml
  ```

## 重新运行 Tasty 时

- **从应用菜单 · 启动器重新运行后，已有窗口置于前台，而未打开新窗口** — 使用同一数据文件夹（`~/.tasty/`，或通过 `TASTY_HOME` 指定的文件夹）的 Tasty 只能运行一个。再次运行时，不会创建新进程，而是交给正在运行的 Tasty。隐藏到托盘或最小化的窗口也会重新显示，最后使用的窗口会置于前台。实际是否置于前台由 OS 决定，因此某些环境中只会闪烁任务栏。Wayland 上，如果桌面环境不支持窗口激活请求，会打开新窗口，而非激活已有窗口。
- **在终端运行 `tasty` 后，只打开一个新窗口** — 从 Tasty 外部的终端 · 脚本 · 智能体不带参数运行时，结果与 `tasty new window` 相同。在 Tasty 打开的终端内，会显示帮助，而非打开新窗口。当前查看窗口的焦点和隐藏的窗口保持不变。在 Windows 上，从当前使用的（前台）终端运行时，OS 会传递置于前台的权限，因此可能与从应用菜单启动时一样，将已有窗口置于前台。
- **出现“已有 Tasty 正在运行。”消息框** — 无法将请求交给正在运行的 Tasty，且正在运行的 Tasty 没有响应。如果请求已传达但处理缓慢，不会显示消息框，稍后会打开窗口。消息框多数出现在正在运行的 Tasty 尚在启动，或 Linux 上无法连接会话总线时。原因会记录在数据文件夹中的 `launch.log`（`~/.tasty/launch.log`）。每次重新运行都会按进度阶段记录多行。Linux 上没有 `zenity` 时，会以桌面通知代替消息框。
- **刚强制退出 Tasty 后重新运行，显示稍慢** — 会等待残留锁释放，最多 2 秒，然后启动。
- **需要分别运行两个 Tasty** — 使用不同的 `TASTY_HOME` 启动其中一个。

  ```sh
  TASTY_HOME=~/tasty-second tasty
  ```

## 收不到通知或通知过多时

- **OS 通知中心收不到通知** — Tasty 目前不向 OS 通知中心发送通知。即使窗口位于后台，通知仍会显示在应用内的**通知** <!-- en: Notifications --> 面板、Surface 边框和侧边栏徽标中。使用 `Ctrl+Shift+I` 打开面板。如果应用内也看不到通知，检查**设置** > **常规** > **通知** <!-- en: Notifications --> 中的**启用通知** <!-- en: Notifications enabled --> 是否开启。
- **每次响铃（`\a`）都出现通知，干扰过多** — 关闭**设置** > **终端** > **显示响铃通知** <!-- en: Show bell notification -->。在 `config.toml` 中，对应 `[general]` 下的 `bell_notification = false`。响铃钩子仍会触发。
- **没有声音** — **设置** > **常规** > **通知** > **声音** <!-- en: Sound --> 默认关闭。即使开启，合并间隔内来自同一来源的连续通知也会合并为一条，只播放一次声音。

完整设置项见[钩子 · 通知 · Webhook](../agents/hooks-notifications.md#设置)。

## Claude 和 Codex 钩子不工作时

**症状** — 收不到子智能体的完成通知。智能体结束响应后，Surface 边框 · 侧边栏徽标也不亮起。恢复标签页或重启 Tasty 后，无法继续同一会话。`tasty claude reboot` 以 `claude-session-id meta not set`（设置为韩语时为“claude-session-id 메타데이터 미설정”）失败。`tasty claude children` 显示的状态与实际不同。

**原因** — 未安装钩子，或更新 Tasty 后，旧钩子命令仍留在配置文件中。

**解决方法** — 重新安装钩子。多次运行也不会重复安装。

```sh
tasty claude install    # ~/.claude/settings.json
tasty codex install     # ~/.codex/config.toml
```

仍无效时，查看 `~/.tasty/hook-failures.log` 和 `tasty plugin logs com.tasty.claude --follow`。详细内容见[配合 Claude 和 Codex 使用](../agents/claude-codex.md#故障排除)。

### 父智能体未收到子智能体的结果

子智能体的边框 · 徽标状态与父智能体接收结果是独立的。如果父智能体是 Claude Code，重新运行 install 后，在新会话中检查完成通知的 mod 标记及接收情况。仅在没有 mod 时检查 Monitor 订阅，不要同时启用两者。按照[连接与恢复说明](../agents/claude-codex.md)操作。

### 创建信号量或屏障时因“invalid char”被拒绝

名称中含有大写字母或空格等不允许的字符。消息指向的位置按输入的名称计数（首字符为 0）。改用小写英文字母 · 数字 · `.` · `_` · `-` 后重新创建。[并发限制和信号](../agents/tasks.md#并发限制和信号)

## 插件停止运行时

- **`tasty plugin list` 中为 enabled，但不是 running** — 10 秒内 3 次运行失败后，会自动停止。使用 `tasty plugin logs <id>` 查看原因，再使用 `tasty plugin enable <id>` 重新启动。
- **刚运行 `plugin enable` 时为 running，稍后便不再是 running** — `plugin enable` 不会等待插件连接 Tasty，而是立即返回。因此刚启用的插件在连接前也会显示为 running，其间发送的请求会在连接后传达。如果 10 秒内未能连接，会计为运行失败，并不再显示为 running。使用 `tasty plugin logs <id>` 查看原因。
- **随附插件损坏** — 使用 `tasty plugin upgrade-builtins --force` 从随附文件中重新复制。插件数据（书签 · 配置档等）会保留。
- **macOS：内置插件无法运行** — 应用上残留的 Gatekeeper 隔离标记（quarantine）可能也被带到插件副本上，阻止运行。Tasty 不会自行删除此标记。使用 `tasty plugin logs <id>` 确认原因；要手动删除，在终端运行 `xattr -dr com.apple.quarantine /Applications/Tasty.app ~/.tasty/plugins`，然后重启 Tasty。

## 日志和配置文件位置

均位于 `~/.tasty/` 下（Windows 上为 `%USERPROFILE%\.tasty\`）。

| 文件 | 内容 |
|---|---|
| `config.toml` | 设置。设置窗口中保存的值会写入此处 |
| `tasty.port` | 正在运行的 Tasty 的 IPC 端口号。Tasty 启动时创建 |
| `debug.log` | 上次运行的警告及以上级别日志。重新启动 Tasty 时清空 |
| `crash-reports/crash-*.log` | 崩溃报告 — 版本 · OS · 位置 · 消息 · 回溯 |
| `crash-reports/hang-*.log` | 窗口无响应超过 5 秒时自动留下的记录 |
| `launch.log` | 已有 Tasty 运行时再次启动的记录和结果 |
| `hook-failures.log` | Claude / Codex 钩子未能连接 Tasty 的记录 |
| `plugins-logs/<插件 id>.log` | 各插件的日志。也可使用 `tasty plugin logs <id>` 查看 |
| `state.db` | 最近文件等由应用自动管理的数据 |

需要更详细的日志时，在终端中提高日志级别后运行。使用的是 `TASTY_LOG`，而非 `RUST_LOG`。

```sh
TASTY_LOG=debug tasty 2> tasty.log
```

## 报告问题

在 [GitHub Issues](https://github.com/zilhak/tasty/issues) 中填写复现问题的步骤、Tasty 版本、OS 和架构，以及相关错误消息。附上日志前，检查路径和输出中是否包含个人信息。

- `tasty --version` 的输出和 OS · 版本
- 复现步骤
- `~/.tasty/crash-reports/` 中对应的 `crash-*.log` / `hang-*.log`
- 症状出现后的 `~/.tasty/debug.log`（重新启动会清空，因此先复制保留）
