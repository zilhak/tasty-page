# トラブルシューティング

このページでは、Tasty のインストール、入力、画面、復元、通知の問題について、症状別に原因と解決方法を紹介します。CLI が接続できない場合や応答が遅い場合は、接続診断も参照してください。解決しない場合は、使用環境とログを添付して問題を報告できます。

## インストール・初回起動

- **Windows: 「Windows によって PC が保護されました」という警告が表示されます** — コード署名がないためです。**詳細情報 → 実行** を押してください。
- **macOS: 「未確認の開発元」と表示されて開けません** — Gatekeeper によるものです。**システム設定 > プライバシーとセキュリティ** で許可するか、ターミナルで `xattr -dr com.apple.quarantine /Applications/Tasty.app` を実行してください。
- **Linux: AppImage が実行されません** — 実行権限がないか、FUSE がありません。まず `chmod +x Tasty-*.AppImage` を実行し、それでも動作しない場合は `./Tasty-*.AppImage --appimage-extract-and-run` で起動してください。
- **Linux: `GLIBC_2.39 not found` と表示されて起動しません** — Ubuntu 20.04・Debian 11 のように、ビルドの基準（Ubuntu 24.04）より古いディストリビューションです。古いディストリビューション向けのビルドはありません。
- **Linux `.tar.gz`: ライブラリがないと表示されて終了します** — `tasty` は不足している共有ライブラリのファイル名を列挙して終了します。一緒に表示される検索コマンド（`apt-file search`・`dnf provides`・`zypper what-provides`・`pacman -F` のうち、ディストリビューションに合うもの）で、そのライブラリを提供するパッケージを探してインストールしてください。必要なライブラリを自動でインストールするには、`.deb` / `.rpm` を使用してください。
- **ウィンドウが表示されずにすぐ終了し、ログに「GPU アダプターが見つかりません」と残ります** — 使用可能な GPU アダプター（Vulkan / DirectX 12 / Metal）が見つかりませんでした。このエラーは画面には表示されず、`~/.tasty/debug.log` とターミナル出力（ターミナルから起動した場合）にのみ残ります。ドライバーをインストール・更新してください。Linux では `libvulkan1` / `vulkan-loader` があれば Vulkan で、なければ OpenGL で、それも使えなければソフトウェアレンダリングで起動します。グラフィカルな画面なしでサーバー・VM 上で実行するには、[ヘッドレスビルド](../getting-started/install.md#ヘッドレスビルド)を使用してください。
- **Windows: 起動時にシェル選択画面が表示されるか、新しいターミナルを開けません** — Tasty は Windows では Git Bash のみを実行します。シェル設定が Git Bash ではない値（フォルダーのパスを含みます）、設定したパスにファイルがない、または設定が空で既定のインストール先にも Git Bash が見つからない場合です。起動時は **シェルを選択** <!-- en: Choose a shell --> 画面が表示され、実行中は **設定** <!-- en: Settings --> > **ターミナル** <!-- en: Terminal --> タブに原因が表示されて、新しいターミナルを開けません。Git for Windows をインストールするか、別の場所にある場合はその `bash.exe` のパスを入力してください。シェル選択画面ではパスを入力して **このシェルを使用** <!-- en: Use this shell --> を押してください。実行中は **設定** > **ターミナル** > **シェル** <!-- en: Shell --> でパスを修正してください。Git for Windows の `usr\bin\bash.exe` も使用できますが、Git が Windows の `PATH` にない場合はそのシェルで `git` コマンドが見つからないため、代わりに `bin\bash.exe` を入力してください。
- **設定したシェルとは別のシェルが開きます** — macOS・Linux で設定のシェルパスにファイルがない場合、Tasty は見つかった別のシェル（ログインシェルまたは `$SHELL`）でターミナルを開きます。設定ファイルのシェルの値は変更しないため、パスを修正するか、そのシェルを再インストールすると、新しいターミナルから元のシェルに戻ります。どのシェルで代替したかは `~/.tasty/debug.log` に残り、**設定** <!-- en: Settings --> > **ターミナル** <!-- en: Terminal --> タブにも案内が表示されます。Windows では別のシェルで代替しません。上の Windows の項目を参照してください。
- **macOS・Linux: 起動直後にシェル選択画面が表示されるか、設定にシェルエラーが表示されます** — 設定したシェルパスがフォルダーか、実行権限のないファイルです。この場合、Tasty は別のシェルで代替せず、原因を表示します。初回起動時は **シェルを選択** <!-- en: Choose a shell --> 画面の判定行に「このパスはフォルダーです」または「このファイルには実行権限がありません」と表示されます。実行中の場合は **設定** <!-- en: Settings --> > **ターミナル** <!-- en: Terminal --> タブに同じ原因が表示され、新しいターミナルを開けません。シェルの実行ファイルのパスに修正するか、`chmod +x` で実行権限を付与してください。
- **起動直後に「ターミナルを起動できません」という画面が表示されます** — 最初のターミナルを開けませんでした。本文の「詳細」に原因が表示されます。原因を修正してから再び起動してください。すでに実行中に新しいウィンドウを開こうとして同じ原因で失敗した場合は、**新しいウィンドウを開けません** <!-- en: Could not open a new window --> という案内に原因が表示され、開いていたウィンドウはそのまま動作します。
- **通知に「最近の一覧とチュートリアルの進行状況が保存されません」と表示されています** — 最近使ったファイルの一覧とチュートリアルの進行状況を格納する `~/.tasty/state.db` を開けませんでした。Tasty はそのまま使用でき、ターミナルとレイアウトの復元にも影響しませんが、以前保存した最近の一覧とチュートリアルの進行状況を読み込めず、今回の実行中に変更した内容も保存されません。今回の実行中にエクスプローラーで移動したフォルダーは、実行中、そのウィンドウの最近の一覧に表示されることがありますが、次回の起動には残りません。通知本文に原因が表示されます。「DB がロックされています」の場合は、別の Tasty がすでに起動しています。「破損しています」/「スキーマのバージョンが一致しません」の場合は、Tasty を終了し、`~/.tasty/state.db` をバックアップしてから削除すると、次回の起動から新しく開始されます。原因を解消した後、Tasty を再び起動すると保存が再開されます。
- **「Tasty を起動できませんでした」という画面が表示され、ターミナルが開きません** — 最初のウィンドウを準備する途中で、Tasty 内部の処理が失敗しました。「詳細」に原因が表示されます。**終了** <!-- en: Quit --> を押すか、Esc・Enter で閉じると Tasty が終了します。再び起動し、繰り返し発生する場合は、データフォルダー（`TASTY_HOME`、既定値は `~/.tasty`）を使用できるかどうかと、`~/.tasty/debug.log` を確認してください。画面を表示できない環境では、同じ内容がメッセージボックス（Linux で zenity がない場合はデスクトップ通知）に表示されます。
- **Tasty のターミナル内で `tasty` と入力しても新しいウィンドウが表示されません** — Tasty 内で引数なしで実行すると、新しいウィンドウの代わりにヘルプを表示します。新しいウィンドウは `tasty new window` で開いてください（見ていたウィンドウのフォーカスはそのままです）。

インストール手順自体は[インストール](../getting-started/install.md)にあります。

## Linux でドキュメント表示と外部アプリとのコピー・貼り付けができない場合

Tasty がネイティブ Wayland で実行されると、HTML・マークダウン表示、リモート HTML ファイル・Web アドレス表示、外部アプリとのテキスト・ファイルのクリップボードのやり取りはできません。ネイティブの右クリックメニューもまだ表示されません。

外部アプリからのファイルのドラッグ取り込みは動作しません。

原因に応じて次の対処を行ってください。

- `DISPLAY` がない場合は、XWayland がないためネイティブ Wayland で実行されます。Tasty の外部で XWayland を有効にしてから、Tasty を再起動してください。
- `DISPLAY` があってもその X サーバーに接続できず、`WAYLAND_DISPLAY` がある場合は、警告を記録してネイティブ Wayland で実行されます。Tasty の外部で `DISPLAY` の X サーバーまたは XWayland の接続を確認してから、Tasty を再起動してください。

HTML・マークダウン・リモート HTML ファイルのサーフェスでは、ページ領域に原因が見出しとして、その下の行に対処方法が表示されます。リモート HTML ファイルでは受信中は受信状況を表示し、受信完了後にこの案内を表示します。コピー・貼り付け時には、原因と対処方法を含む警告トーストが表示されます。トーストの表示時間は全体の設定に従います。

<a id="linux-gdk-backend"></a>

## Linux でドキュメント表示とトレイアイコンを使えない場合

`DISPLAY` があり、Tasty のウィンドウが X11 で実行されていても、Tasty の起動環境の `GDK_BACKEND` が x11 を許可しない場合は GTK の初期化に失敗します。この場合、トレイアイコン、HTML・マークダウン表示、リモート HTML ファイル・Web アドレス表示は使えません。右クリックメニューもまだ表示されません。ウィンドウは X11 で実行されるため、クリップボードは正常に動作します。

Tasty の外部で Tasty の起動環境から `GDK_BACKEND` を削除してから、Tasty を再起動してください。Tasty はこの値を削除したり上書きしたりせず、ターミナル内のシェルにもユーザーが設定した値がそのまま渡されます。

ページ領域に原因と対処方法が表示され、見出しにはトレイアイコンも使えないことが示されます。トレイ自体の個別の案内はありません。

### `GDK_BACKEND` が原因でなくても GTK の初期化に失敗する場合

`GDK_BACKEND` がない場合や x11 を許可している場合でも、GTK の初期化に失敗することがあります。この場合もトレイアイコン、HTML・マークダウン表示、リモート HTML ファイル・Web アドレス表示は使えず、右クリックメニューはまだ表示されません。ウィンドウは X11 で実行されるため、クリップボードは正常に動作します。

アプリには GTK の初期化失敗の案内だけが表示され、対処方法の行は表示されません。Tasty が原因を特定できない場合なので、[ログと設定ファイルの場所](#ログと設定ファイルの場所)で警告ログを確認し、[問題の報告](#問題の報告)に記載された情報を添えて報告してください。

## macOS の権限プロンプト

**症状** — タスクの途中で権限プロンプトが表示され、作業が止まります。ターミナル内のコマンド（およびその中のエージェント）が、新しいフォルダーに初めてアクセスするたびに発生します。

**原因** — ターミナル内で実行したコマンドがファイルを読み取ると、macOS はそのアクセスを Tasty によるものと見なします（Terminal.app・iTerm2 も同様です）。macOS は実際にアクセスする瞬間にしか確認しないため、事前に権限を取得していないと、作業の途中でプロンプトが表示されます。

**解決方法 — 事前にまとめて取得してください。** **設定** > **一般** <!-- en: General --> > **アクセス権** <!-- en: Permissions --> で **すべての権限を要求** <!-- en: Request all permissions --> を押すと、ダウンロード・書類・デスクトップフォルダー →（接続されている場合）外部・ネットワークボリューム → 画面収録の順に、1 つずつ確認されます。前のものに回答すると次が表示され、プロンプトの表示中もウィンドウは正常に動作します。すでに許可または拒否した項目は再び表示されないため、何度押しても問題ありません。ボリュームを新しく接続した後に再び押すと、そのボリュームについてのみ追加で確認されます。

Tasty は起動時にプロンプトを **自動では表示しません。** 初めてアプリを起動した人に、理由のわからないプロンプトが次々と表示されるのを避けるためです。代わりに、許可されていない権限が残っている場合は、起動時に案内が表示され、この画面に誘導します。

**回答方法**

| 権限 | 許可しない場合 | 後で変更するには |
|---|---|---|
| フォルダーへのアクセス（ダウンロード・書類・デスクトップ・ボリューム） | そのフォルダーを読み書きするコマンドが失敗することがあります | システム設定 > プライバシーとセキュリティ > ファイルとフォルダ |
| 画面収録 | `Ctrl+Alt+S` のスクリーンショット → クリップボード機能では、「画面収録の権限が必要です」という案内だけが表示されます。一度拒否すると再び確認されません | システム設定 > プライバシーとセキュリティ > 画面収録とシステムオーディオ録音 |

現在の状態も同じタブで確認できます（macOS でのみ表示されます）。フルディスクアクセスはアプリから要求できないため、このボタンには含まれません。フルディスクアクセスの行の **システム設定を開く** <!-- en: Open System Settings --> でシステム設定を開き、直接追加してください。フォルダーの権限は自動で確認できないため、「自動確認不可」<!-- en: Cannot check automatically --> と表示されます。

- **「許可されていない権限があります」という案内が表示されました** — フルディスクアクセスまたは画面収録の権限がないと判断されている間、起動するたびに表示されます。どの権限がどの状態かは、**設定** > **一般** > **アクセス権** タブで確認してください。**権限設定を開く** <!-- en: Open permission settings --> を押すと、Tasty の権限画面が開きます。フルディスクアクセスはアプリから直接要求できないため、その画面のフルディスクアクセスの行にある **システム設定を開く** <!-- en: Open System Settings --> でシステム設定を開き、Tasty を一覧に直接追加する必要があります。この権限を付与すると、ファイルアクセスのプロンプト（ほかのアプリのデータ・ダウンロード・書類・デスクトップ・ボリューム）が表示されなくなります。ただし、ほかのアプリの制御（Automation）・画面収録は別の権限なので、そのまま残ります。権限を付与すると、次回の起動から案内は表示されません。案内を無効にする設定はありません。無効にした記録を残すと、後で権限がリセットされたときに知らせる方法がなくなるためです。
- **すべての権限を付与したのに、フォルダーアクセスのプロンプトがまだ表示されます** — 起動時の案内では、確認できる権限のみを参照します。ダウンロード・書類・デスクトップ・ボリュームなどのフォルダーの権限は、確認のためにフォルダーにアクセスすると権限要求ダイアログが表示されることがあるため、案内の判定には含めません。フルディスクアクセスを付与すると、これらのフォルダーにもアクセスできます。
- **権限を付与したのに、案内が再び表示されます** — ダウンロードした配布版と自分でビルドした Tasty は、どちらも ad-hoc 署名のため、更新または再ビルドすると macOS が別のアプリと見なします。そのため、システム設定のフルディスクアクセス一覧で Tasty が有効のまま残っていても、その項目は適用されなくなっていることがあります。権限を付与した状態で Tasty を起動したことがあれば、案内がこのケースを検出し、一覧から Tasty を削除して追加し直すように知らせます。アプリは同じで権限が無効になっている場合は、有効に戻すように知らせ、`tccutil reset` などで一覧から Tasty が消えた場合は、追加し直すように知らせます。**設定** > **一般** > **アクセス権** のフルディスクアクセスの行も、状態を「未許可」のままにし、その下の 1 行に同じ対処方法（有効に見えても適用されていないため削除して追加し直す、または有効に戻す、一覧から消えていたら + で追加し直す）を表示します。自分でビルドする場合は、`./scripts/macos-codesign-identity.sh --create` で「Tasty Dev」証明書を一度作成し、以降のビルドに同じ証明書を使用してください。証明書を使用しても権限の維持は保証されないため、システム設定でも状態を確認してください。証明書に切り替えた直後も、一覧から既存の Tasty を削除して追加し直してください。
- **フルディスクアクセスの状態が「確認不可」と表示されます** <!-- en: The Full Disk Access status shows "Unknown" --> — この状態は macOS に問い合わせる API がないため、推定で求めます。推定に使用するファイルがその macOS バージョンに存在しない場合は、許可の有無を判断する根拠がないため確認不可と表示し、この権限を理由とした起動時の案内も表示しません（画面収録が未承認の場合は、その理由で表示されます）。この値によって使えなくなる機能はありません。
- **「Tasty がほかのアプリのデータにアクセスしようとしています」と、アプリのフォルダーごとに繰り返し表示されます** — `~/Library/Application Support/<アプリ>` のようなパスはアプリごとに個別に確認されるため、**すべての権限を要求** でも事前に取得できません。上記のフルディスクアクセスを付与すると、表示されなくなります。
- **`osascript` を使用すると「ほかのアプリを制御しようとしています」と表示されます** — Automation の権限は対象アプリごとに承認する必要があり、フルディスクアクセスでもカバーされません。Tasty が事前にできることはありません。

## Linux X11 で入力メソッドを再起動した後に韓国語を入力できない場合

Tasty は XIM 入力メソッドサーバーの終了・置き換えを検出すると、以前のサーバーへの要求を停止し、新しいサーバーに
再接続します。接続が復旧するまではローカル入力で代替することがあり、韓国語の文字の組み立てが一時的に
できなくなることがあります。ibus が再び実行され、韓国語エンジンが選択されていることを確認してください。

接続のネゴシエーション中や生存確認の直後にサーバーが終了した場合や、サーバーが生きていても応答しない
場合までフリーズを防げるわけではありません。ウィンドウ全体がフリーズしたままの場合は、以下のフリーズ記録を保存して報告してください。
この説明は X11 向けであり、Wayland・macOS・Windows の入力方式には適用されません。

## `tasty` コマンドが接続できない場合

- **`No running tasty instance found (port file not found at …)`** — CLI が確認したパスにポートファイルがありません。メッセージに記載されたパスが `~/.tasty/tasty.port` でなければ、別のホームディレクトリ（`TASTY_HOME`）を参照しています。このメッセージは設定言語（`general.language`、既定値は英語）に従うため、韓国語に設定している場合は「実行中の tasty インスタンスが見つかりません」と表示されます。引数が不正な場合（壊れた JSON、存在しない `--cwd` フォルダーなど）は、このメッセージより先にその引数のエラーが表示されるため、このメッセージが表示された場合は、接続前に行う引数の検査を通過しています。
- **ポートファイルはあるのに接続できません** — 前回の実行時のファイルが残っているか、別のインスタンスのパスを参照している可能性があります。エラーに表示されたパスと `TASTY_HOME` を確認し、そのファイルを使用する Tasty インスタンスが終了しているか確認してください。終了したインスタンスの残存ファイルである場合にのみ、直接削除して再起動してください。プロセス名の検索結果だけでファイルを削除しないでください。起動後にファイルが置き換えられた場合や、別のプロセスが保存中の場合、Tasty は終了時にそのファイルを残すことがあります。
- **起動時にポートファイルの保存エラーが発生します** — 現在のアカウントでファイルと親フォルダーを読み書きできるか確認してください。読み取れない元のファイルは上書きしません。ファイル全体を置き換えられる必要があるため、親フォルダーにも書き込み権限が必要です。
- **接続はできるものの応答が遅いか、`Error (-32061)`・`Error (-32065)` のような行で終わります** — 応答がないときに、シェルの `timeout` で `tasty` を停止して同じ要求を繰り返さないでください。接続を閉じても、送信済みの要求は取り消されません。Tasty がビジーの間に蓄積された要求は、後でまとめて実行されることがあり、入力を送信するコマンドであれば同じ入力が繰り返されます。

  応答待ちに期限が必要な場合は、1 つの要求で完結するコマンドに `--response-timeout-ms` を使用し、フラグはコマンドの前に記述してください。期限内に処理を開始できなかった要求は `Error (-32067)` で終了し、後からも実行されません。処理開始後に期限が過ぎると `Error (-32061)` で終了し、結果は不明で、タスクが続く可能性があります。繰り返し問い合わせるコマンドや接続を維持するコマンドは、このフラグを受け取ると要求を送信せず、終了コード 2 で拒否します。再送してもよい場合と、先に状態を確認する場合については、[応答待ちに上限を設ける](cli-diagnostics.md#応答待ちに上限を設ける)で説明しています。ほかのエラーコード別の対処方法と `tasty list pressure` の読み方は、[CLI の応答遅延と接続診断](cli-diagnostics.md)で確認できます。


- **`tasty: command not found`** — Tasty が開いたターミナル内では PATH に自動で追加され、`.deb`・`.rpm`・`.msi` でインストールした場合は、ほかのターミナルアプリでも見つかります。それ以外のインストール方法では、手動で登録する必要があります。インストール方法別のパスは[インストール先](../getting-started/install.md#インストール先)にあります。

## ボタンやショートカットを押すとタスクを完了できなかったという案内が表示される場合

レイアウトの変更・分割線の移動・カテゴリーの初期化・リモート接続の開始など、ユーザー操作が失敗すると、画面に失敗の案内が一度表示されます。分割線の位置を確定できなかった場合は、以前の位置に戻ります。カテゴリーの初期化の失敗は、設定が変更されなかったことを意味します。画面の現在の状態を確認してから、再試行してください。失敗が続く場合は、`~/.tasty/debug.log` の同時刻の記録とともに問題を報告してください。エージェントコマンドの失敗は、画面のトーストの代わりにコマンド応答やログで伝えます。

## リンクやフォルダーを開けなかったという通知が表示される場合

ターミナルのリンク、システムの既定のアプリで開くファイル、プラグインウィンドウのホームページ・インストールフォルダーは、オペレーティングシステムの既定のプログラムに渡して開きます。そのプログラムを起動できない場合は、通知が表示されます。

- **Linux** — `xdg-open` がインストールされているか、または `BROWSER` 環境変数が実行可能なブラウザーを指しているか確認してください。Tasty を起動した環境の `PATH` から探します。
- **macOS・Windows** — そのアドレスやファイル形式に関連付けられた既定のアプリがあるか、システム設定で確認してください。

通知なしで何も起きない場合は、既定のプログラムは起動したものの、そのプログラムが開けなかったケースです。そのプログラム側を確認してください。

## コマンドでファイル選択ポップアップを開けない場合

- **スクリプトやエージェントが IPC でファイル選択ポップアップを開こうとすると、`-32016` エラーが発生します** — 正常な動作です。ファイル選択ポップアップは、ユーザーがサイドバーの **ツール** <!-- en: Tools --> > **ファイルを開く…** <!-- en: Open File… --> から開くか、プラグインが開きます（Markdown のファイルを開く画面で **参照…** <!-- en: Browse… --> を押す場合など）。コマンドがポップアップを表示すると、ユーザーが入力していた場所からフォーカスを奪い、選択したパスもそのコマンドには返されないためです。スクリプト・エージェントはファイルパスを直接指定してください。

<a id="自分の-dev-サーバーが何番ポートで起動したかわからない場合"></a>

## 開発サーバーのポートを探したい場合

サイドバーの **ツール** <!-- en: Tools --> メニューから **受信ポート…** <!-- en: Listening ports… --> を開いてください。Tasty のターミナルから起動したプロセスが開いている TCP ポートを、ポート・プロセス・ワークスペース・タブとともに表示します。

- 既定では LISTEN 状態のみ表示されます。一覧が空で「状態フィルターに一致するポートがありません」と表示されている場合は、別の状態のポートがある可能性があります — フィルター行の右側にある **状態** <!-- en: State --> ボタンで別の状態を有効にし、**適用** <!-- en: Apply --> してください。
- Tasty 外のプロセスも表示するには、**全て表示** <!-- en: Show all (system-wide) --> を有効にしてください。
- 行をクリックして選択し、**アドレスをコピー** <!-- en: Copy address --> で `host:port` をクリップボードにコピーしてください。
- 星アイコンでお気に入りに追加すると、常に上部に表示され、再起動後も残ります（`~/.tasty/port-favorites.toml`）。別のウィンドウで変更したお気に入りもすぐに反映されます。

<a id="ウィンドウがフリーズしたりクラッシュしたりする場合"></a>

## ウィンドウがフリーズしたり突然終了したりする場合

- **ウィンドウがクリック・キー入力・CLI にまったく反応しません** — 5 秒を超えてフリーズすると、`~/.tasty/crash-reports/hang-*.log` が自動で残ります。ファイルの `Render phase` が `acquire` / `submit` / `present` の場合は、そのレンダリング段階で停止した記録です。GPU ドライバーの問題である可能性があるため、ドライバーの更新も確認してください。Tasty は自動では復旧しないため、強制終了して再び起動してください。
- **突然終了しました** — `~/.tasty/crash-reports/crash-*.log` を確認してください。問題を報告するときは、このファイルも添付してください。

### 実行中に保存が停止したという案内が表示された場合

ウィンドウの右上に **Tasty が停止したため再起動が必要です** <!-- en: Tasty stopped and needs a restart --> という案内が表示され、通知にエラーが 1 つ残っている場合は、ワークスペース・ペイン・タブの配置を `~/.tasty/structure/journal.db` に保存する際に失敗したケースです。保存済みの配置を保護するため、Tasty はそれ以降の変更を適用しません。

- この状態では、キー入力とクリックがターミナルやほかの画面に伝わらず、`tasty` コマンドも拒否されます。案内の **続行** <!-- en: Continue --> または × は、案内を閉じるだけです。
- ウィンドウの閉じるボタンで Tasty を終了し、再び起動してください。この状態では終了の再確認は行わず、すぐに終了します。
- 原因は案内の下部に表示され、`~/.tasty/debug.log` にも残ります。再び起動しても同じ案内が表示される場合は、保存先があるディスクの空き容量と権限を確認し、問題を報告するときはログも添付してください。

## 設定やウィンドウの構成が初期化されたように見える場合

配置が復元されない場合は、**起動時にレイアウトを復元** <!-- en: Restore layout on startup --> 設定と通知を先に確認してください。保存先を開けなかったという案内がある場合は、案内に記載された場所と原因を確認してください。元の保存先を読み取れない状態で起動した一時的な配置は、次回の起動には残りません。ターミナルで編集したプロジェクトファイルには、この制限は適用されません。

- **設定が既定値に戻りました** — `~/.tasty/config.toml` を TOML として解析できない場合は、既定値で起動します。元のファイルは削除されません。そのまま残され、設定を保存してファイルを書き直す時点で、同じフォルダーの `config.toml.bak` に移動されます。そのファイルを開いて修正し、`config.toml` に戻すと設定が復元されます。どの行に問題があるかは、`~/.tasty/debug.log` に記録されます。
- **保存済みのワークスペースを復旧できなかったという案内が表示されます** — 記録の累積サイズだけを理由に、ターミナルの起動を妨げることはありません。復元を進められない場合は、元のデータを保全し、今回の実行中だけ使用する空のワークスペースで続行します。ターミナル入力と新しいタブは使用できますが、今回の配置は次回の起動用には保存されません。ディスクの空き容量とデータフォルダーの権限を確認してから、再起動してください。ディスクへの書き込み失敗は保存成功として扱わず、原因は通知に表示します。
- **保存しておいたウィンドウ構成が復元されませんでした** — まず **設定** > **一般** > **起動時にレイアウトを復元** <!-- en: Restore layout on startup --> が有効になっているか確認してください。ワークスペース・ペイン・タブの配置は `~/.tasty/structure/journal.db` に保存されます。以前のバージョンが使用していた `~/.tasty/layouts/` の `01.json` などのファイルは、新しい保存先に初めて移行するときに一度だけ読み取るため、その後にこのファイルを修正・削除しても、復元される配置は変わりません。保存先を開けない場合、Tasty は新しい既定のワークスペースで起動し、エラー通知とともにウィンドウの右上に **前回のセッションを復元できませんでした** <!-- en: Couldn't restore your last session --> という案内を表示します。案内には原因と保存先の場所が記載され、詳しいエラーは通知項目にあり、同じ内容が `~/.tasty/debug.log` に残ります。保存先のファイルは変更・移動・削除しません。今回の実行中のレイアウト記録（ワークスペース・タブと、その復元に必要な記録）は Tasty を終了すると消えますが（ターミナルで変更したファイルには影響しません）、次回の起動では保存先を再び読み取ります。読み取り権限を戻すと、元の配置が復元されます。案内は **続行** <!-- en: Continue --> または × で閉じることができ、表示中もターミナル入力はそのまま使用できます。別の Tasty が同じデータフォルダーを使用している場合は、起動せずに原因を示す画面を表示します。問題を報告するときは、ログも添付してください。 <!-- TODO verify: 破損した journal.db からユーザーが配置を復旧する手順があるか -->
- **「以前のレイアウトファイルを取り込めませんでした」という通知が表示されました** <!-- en: "An old layout file could not be imported" --> — 以前のバージョンが使用していた `~/.tasty/layouts/01.json` などのファイルを、レイアウトとして読み取れなかったケースです。そのウィンドウは新しい既定のワークスペースで起動し、ファイルはそのまま残ります。ファイルを読み取る権限がない場合は、エラー通知とともにウィンドウの右上に案内が表示されます。一度新しいレイアウトで起動した後は、ファイルを修正しても再び取り込みません。
- **「ターミナルの内容の一部を復元できませんでした」という通知が表示されました** <!-- en: "Some terminal contents were not restored" --> — 以前のバージョンのファイルを取り込む際に、一部のターミナルの保存済みの内容ファイルが存在しなかったか、読み取れなかったケースです。配置はそのまま復元され、そのターミナルだけが以前の出力なしで起動します。
- **「選択していたタブを復元できませんでした」という通知が表示されました** <!-- en: "Selected tabs could not be restored" --> — ワークスペースとタブの配置は復元できたものの、最後に選択していたワークスペース・タブの記録を読み取れなかったケースです。最初のワークスペースとタブを選択した状態で起動します。読み取れなかった記録は、通知に記載された場所（通常は `~/.tasty/structure/damaged/`）に残し、自動では削除しません。
- **「保存されたレイアウトの一部を復元できませんでした」という通知が表示されました** <!-- en: "Part of the saved layout could not be restored" --> — 1 つのウィンドウの保存記録を読み取れなかったケースです。そのウィンドウだけを復元せずに新しいレイアウトで起動し、ほかのウィンドウはそのまま復元されます。読み取れなかった記録は削除せずに残します。通知にレイアウト番号と原因が記載されます。
- **「以前の保存時点から復元しました」という通知が表示されました** <!-- en: "Restored from an earlier save point" --> — 最新の保存時点を読み取れなかったため、以前の保存時点とそれ以降の記録からレイアウトを再構築したケースです。それ以降の記録をすべて再適用するため、レイアウトは変わりません。
- **1 つのタブが空のターミナルで開き、「タブを復元できませんでした」という通知が表示されました** <!-- en: A tab opened as an empty terminal with "A tab could not be restored" --> — そのタブに保存された内容（作業フォルダー・以前の出力・復元コマンド）を読み取れなかったケースです。ほかのタブとワークスペースはそのまま復元され、そのタブは現在のシェル設定で新しく起動します。読み取れなかった元のデータは保存先にそのまま残し、削除しません。通知に、どのワークスペースのどのタブかと、原因が記載されます。
- **「レイアウトが保存されていません」という通知が表示されました** <!-- en: "Layout is no longer being saved" --> — 実行中の配置とターミナルの内容を保存するために一度にまとめたサーフェスキャプチャ要求が、64 MiB の上限を超えました。この上限は、同じ実行エンジンに属するすべてのサーフェスを一度に保存する要求に適用され、保存先全体や 1 つのワークスペースのディスク容量制限ではありません。その要求は一部だけを保存せず、全体をスキップします。最後に保存された状態は残りますが、それ以降の変更は次回の起動で復元されません。出力が多く蓄積されたターミナルのスクロールバックを消去してください。配置が変わるか記録が減ると再試行し、要求サイズが上限以内になると保存を再開します。同じ原因では、保存が再び成功するまで通知を一度だけ残します。
- **「保存が失敗し続けています」という通知が表示されました** <!-- en: "Saving keeps failing" --> — レイアウトまたは選択したタブの保存が、成功せずに 3 回連続で失敗したケースです。1、2 回の一時的な失敗は次の保存時に再試行するため、通知しません。Tasty は再試行を続けますが、保存に成功するまでは、最後の保存以降の変更は次回の起動で復元されません。通知にある原因（ディスク容量不足、権限など）を解消すると、次の保存時に正常に戻ります。原因の全体は `~/.tasty/debug.log` にも残ります。
- **「保存できません。`.bak` ファイルを移動または削除してください」という通知が表示されました** — 設定ファイル（`config.toml`）の元のファイルを退避しようとしたものの、`.bak` から `.bak.9` までの 9 か所がすでに埋まっており、置き場所がないケースです。元のファイルを削除しないために保存自体を停止した状態で、そのセッション中は保存されないままになります。蓄積した `.bak` ファイルのうち不要なものを移動または削除してから再び起動すると、正常に戻ります。
- **「設定ファイルを読み取れませんでした」という通知が表示されました** — ファイルは存在するものの、**読み取れなかった** ケースです（権限の問題やディスクエラー）。この場合、Tasty はそのファイルを変更せず、保存もしません — そのままにしておけば、現在画面に表示されている既定値で元の設定が上書きされることはありません。権限を修正するか、ファイルを別の名前に変更してから再び起動してください。

  ```sh
  ls -l ~/.tasty/config.toml
  ```

## Tasty を再び起動した場合

- **アプリメニュー・ランチャーから再び起動すると、新しいウィンドウの代わりに、すでに開いていたウィンドウが前面に表示されます** — 同じデータフォルダー（`~/.tasty/`、または `TASTY_HOME` で指定したフォルダー）を使用する Tasty は、1 つだけ実行されます。再び起動すると、新しいプロセスを作成せずに、実行中の Tasty に引き渡します。トレイに隠したウィンドウや最小化したウィンドウも再表示され、最後に使用していたウィンドウが前面に表示されます。実際に前面に表示するかは OS が決めるため、タスクバーが点滅するだけで終わる環境もあります。Wayland でデスクトップ環境がウィンドウのアクティブ化要求に対応していない場合は、開いていたウィンドウの代わりに新しいウィンドウが開きます。
- **ターミナルで `tasty` を実行すると、新しいウィンドウが 1 つだけ開きます** — Tasty 外のターミナル・スクリプト・エージェントから引数なしで実行すると、`tasty new window` と同じ結果になります。Tasty が開いたターミナル内では、新しいウィンドウの代わりにヘルプが表示されます。見ていたウィンドウのフォーカスと、隠したウィンドウはそのままです。Windows では、現在使用している（前面にある）ターミナルから実行すると、OS が前面に表示する権限を引き渡すため、アプリメニューから起動した場合と同じように、開いていたウィンドウが前面に表示されることがあります。
- **「すでに実行中の Tasty があります。」というボックスが表示されます** — 実行中の Tasty に要求を引き渡せず、実行中の Tasty が応答していません。要求は届いたものの処理が遅い場合は、ボックスは表示されず、しばらくするとウィンドウが開きます。ボックスが表示されるのは、実行中の Tasty がまだ起動途中だった場合や、Linux でセッションバスに接続できなかった場合が大半です。原因はデータフォルダーの `launch.log`（`~/.tasty/launch.log`）に残ります。再び起動するたびに、進行段階ごとに複数行が記録されます。Linux で `zenity` がない場合は、ボックスの代わりにデスクトップ通知で表示されます。
- **強制終了した直後に Tasty を再び起動すると、表示が少し遅くなります** — 残っているロックが解除されるまで最大 2 秒待ってから起動します。
- **Tasty を 2 つ別々に起動する必要があります** — 一方を別の `TASTY_HOME` で起動してください。

  ```sh
  TASTY_HOME=~/tasty-second tasty
  ```

## 通知が届かない、または多すぎる場合

- **OS の通知センターに通知が届きません** — 現在、Tasty は OS の通知センターに通知を送信しません。ウィンドウが背面にあっても、通知はアプリ内の **通知** <!-- en: Notifications --> パネル、サーフェスの枠線、サイドバーのバッジに表示されます。パネルは `Ctrl+Shift+I` で開いてください。アプリ内でも通知が表示されない場合は、**設定** > **一般** > **通知** <!-- en: Notifications --> の **通知を有効化** <!-- en: Notifications enabled --> が有効になっているか確認してください。
- **ベル音（`\a`）のたびに通知が表示され、うるさいです** — **設定** > **ターミナル** > **ベル通知を表示** <!-- en: Show bell notification --> を無効にしてください。`config.toml` では `[general]` の `bell_notification = false` です。ベルのフックは引き続き発生します。
- **音が鳴りません** — **設定** > **一般** > **通知** > **サウンド** <!-- en: Sound --> は、既定では無効です。有効にしても、マージ間隔内に同じ送信元から連続して届いた通知は 1 つにまとめられ、音は一度だけ鳴ります。

設定項目の全体は[フック・通知・webhook](../agents/hooks-notifications.md#設定)にあります。

## Claude・Codex のフックが動作しない場合

**症状** — 子エージェントの完了通知が届きません。エージェントが応答を終えても、サーフェスの枠線・サイドバーのバッジが点灯しません。タブを復元したり Tasty を再起動したりしても、同じセッションを再開できません。`tasty claude reboot` が `claude-session-id meta not set`（韓国語設定の場合は "claude-session-id 메타데이터 미설정"）で失敗します。`tasty claude children` が表示する状態が実際と異なります。

**原因** — フックがインストールされていないか、Tasty の更新後も古いフックコマンドが設定ファイルに残っています。

**解決方法** — フックを再インストールしてください。複数回実行しても重複しません。

```sh
tasty claude install    # ~/.claude/settings.json
tasty codex install     # ~/.codex/config.toml
```

それでも動作しない場合は、`~/.tasty/hook-failures.log` と `tasty plugin logs com.tasty.claude --follow` を確認してください。詳細は [Claude・Codex と一緒に使う](../agents/claude-codex.md#トラブルシューティング)にあります。

### 親エージェントが子の結果を受け取れません

子の枠線・バッジの状態と、親による結果の受信は別のものです。親が Claude Code の場合は、install を再実行した後、新しいセッションの完了通知の mod マーカーと受信を確認してください。mod がない場合にのみ Monitor の購読を確認し、両方を同時に有効にしないでください。[接続・復旧の案内](../agents/claude-codex.md)に従ってください。

### セマフォ・バリアの作成時に "invalid char" で拒否されます

名前に大文字や空白など、使用できない文字が含まれています。メッセージが示す位置は、入力した名前の中で数えた位置です（最初の文字は 0）。英小文字・数字・`.`・`_`・`-` に変更して、作成し直してください。[同時実行の制限とシグナル](../agents/tasks.md#同時実行の制限とシグナル)

## プラグインが停止した場合

- **`tasty plugin list` で enabled なのに running ではありません** — 10 秒以内に 3 回実行に失敗すると、自動で停止されます。`tasty plugin logs <id>` で原因を確認した後、`tasty plugin enable <id>` で再び起動してください。
- **`plugin enable` の直後は running なのに、しばらくすると running ではなくなります** — `plugin enable` は、プラグインが Tasty に接続するのを待たずにすぐ戻ります。そのため、有効にした直後のプラグインは接続前でも running と表示され、その間に送信された要求は接続後に届けられます。10 秒以内に接続できないと実行失敗として数えられ、running ではなくなります。原因は `tasty plugin logs <id>` で確認してください。
- **バンドルされたプラグインが壊れました** — `tasty plugin upgrade-builtins --force` でバンドルからコピーし直してください。プラグインのデータ（ブックマーク・プロファイルなど）は維持されます。
- **macOS: 組み込みプラグインが実行されません** — アプリに残っている Gatekeeper の隔離属性（quarantine）がプラグインのコピーにも付与され、実行が妨げられた可能性があります。Tasty はこの属性を自動では削除しません。`tasty plugin logs <id>` で原因を確認し、手動で削除する場合は、ターミナルで `xattr -dr com.apple.quarantine /Applications/Tasty.app ~/.tasty/plugins` を実行してから Tasty を再起動してください。

## ログと設定ファイルの場所

すべて `~/.tasty/` の下にあります（Windows では `%USERPROFILE%\.tasty\`）。

| ファイル | 内容 |
|---|---|
| `config.toml` | 設定です。設定ウィンドウで保存した値がここに入ります |
| `tasty.port` | 実行中の Tasty の IPC ポート番号です。Tasty の起動時に作成されます |
| `debug.log` | 直前の実行の警告以上のログです。Tasty を再び起動すると空になります |
| `crash-reports/crash-*.log` | クラッシュレポート — バージョン・OS・場所・メッセージ・backtrace |
| `crash-reports/hang-*.log` | ウィンドウが 5 秒を超えてフリーズしたときに自動で残る記録です |
| `launch.log` | すでに実行中の Tasty があるときに、再び起動した記録と結果です |
| `hook-failures.log` | Claude / Codex のフックが Tasty に届かなかった記録です |
| `plugins-logs/<プラグイン id>.log` | プラグインごとのログです。`tasty plugin logs <id>` でも確認できます |
| `state.db` | 最近使ったファイルなど、アプリが自動で管理するデータです |

さらに詳しいログが必要な場合は、ターミナルからログレベルを上げて起動してください。`RUST_LOG` ではなく `TASTY_LOG` です。

```sh
TASTY_LOG=debug tasty 2> tasty.log
```

## 問題の報告

問題を再現した手順、Tasty のバージョン、OS とアーキテクチャ、関連するエラーメッセージを [GitHub Issues](https://github.com/zilhak/tasty/issues) に記載してください。ログを添付するときは、パスと出力に個人情報が含まれていないか確認してください。

- `tasty --version` の出力と OS・バージョン
- 再現手順
- `~/.tasty/crash-reports/` 内の該当する `crash-*.log` / `hang-*.log`
- 症状発生直後の `~/.tasty/debug.log`（再び起動すると空になるため、先にコピーしてください）
