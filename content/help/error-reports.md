# 크래시·멈춤 리포트와 로그

Tasty가 갑자기 종료되거나 응답하지 않을 때, 리포트와 로그를 모아 문제를 신고할 수 있습니다.

1. 멈추거나 종료된 시각과 직전에 하던 작업을 적어 두세요. 아직 멈춰 있다면 종료하기 전에 아래 스택 표본도 모을 수 있습니다.
2. **Tasty를 다시 켜기 전에 데이터 폴더의 `debug.log`를 다른 폴더로 복사하세요. 새 인스턴스가 이 로그를 열면 이전 내용이 비워집니다.** 관련 플러그인의 로그도 플러그인을 다시 띄우기 전에 복사하세요.
3. 같은 시각의 `crash-*.log` 또는 `hang-*.log`와 아래 진단 정보를 모으세요. 리포트가 없으면 남아 있는 로그와 증상을 보내세요.
4. 첨부할 복사본에서 토큰과 개인 정보를 가린 뒤 [GitHub Issues](https://github.com/zilhak/tasty/issues)에 신고하세요.

## 데이터 폴더 찾기

`TASTY_HOME`을 지정했다면 그 폴더에서 찾으세요. 값의 앞뒤 공백을 뺀 결과가 비어 있으면 기본 폴더를 사용합니다.

| OS | 기본 데이터 폴더 |
|---|---|
| Windows | `%USERPROFILE%\.tasty\` |
| macOS · Linux | `~/.tasty/` |

아래 경로는 모두 이 데이터 폴더 기준입니다.

## 어떤 파일을 모으나요

| 파일 | 내용과 보관 시점 |
|---|---|
| `crash-reports/crash-*.log` | 크래시 시각, Tasty 버전, OS·아키텍처, 오류 위치·메시지와 backtrace를 담습니다. 문제 시각에 해당하는 파일을 첨부하세요 |
| `crash-reports/hang-*.log` | 화면이 있는 Tasty(GUI)에서 약 5초 넘게 진행이 멈춘 것으로 감지되면 기록을 남깁니다. 모든 멈춤에 기록이 생기는 것은 아닙니다. 문제 시각에 해당하는 파일을 첨부하세요 |
| `debug.log` | 기본은 경고 이상입니다. 실행 중인 Tasty의 로그는 종료 뒤에도 남습니다. 다음 인스턴스가 이 파일을 열 때 이전 내용이 비워집니다. **재실행 전에 복사하세요** |
| `plugins-logs/<id>.log` | 플러그인별 로그입니다. 관련 플러그인의 파일을 **플러그인 재실행 전에 복사하세요** |
| `hook-failures.log` · `hook-failures.log.1` | Claude Code·Codex CLI 훅이 Tasty에 닿지 못한 기록입니다. 훅 문제라면 함께 첨부하세요. 기록이 256 KiB를 넘으면 다음 기록 전에 이전 파일을 `.1`로 옮깁니다 |

크래시 리포트는 자동으로 삭제되지 않습니다. 신고할 때는 문제 시각에 해당하는 파일을 고르세요. `debug.log`에는 로그 파일을 열기 전의 초기 출력이 남지 않을 수 있습니다. `tasty --version` 같은 CLI 명령 실행만으로는 이 파일을 비우지 않습니다.

화면이 있는 Tasty(GUI)에서만 멈춤을 자동으로 감지하고 리포트를 남깁니다. 멈춤 리포트에는 멈춘 시간, 마지막으로 기록된 처리·화면 그리기 상태, 윈도우 포커스·가림 상태가 담깁니다. Linux에서는 시스템 부하, Tasty의 CPU 사용 시간과 실행·대기·스케줄 정보도 담깁니다. Linux의 부하·CPU·스케줄 정보 중 수집할 수 없는 항목은 이유와 함께 표시됩니다. 윈도우 포커스·가림 상태는 알 수 없음으로 표시될 수 있습니다. 마지막 화면 그리기 상태만으로 멈춤의 원인을 단정할 수는 없습니다.

Linux·Windows 배포본의 크래시 리포트에서는 backtrace에 Tasty 함수 이름이 표시됩니다. Tasty 함수의 줄 번호는 표시되지 않습니다. Windows ZIP·헤드리스 ZIP과 MSI 설치 폴더에는 `tasty.exe` 옆에 `tasty.pdb`가 함께 들어 있으며, 별도로 내려받을 필요가 없습니다. **`tasty.pdb`를 지우거나 `tasty.exe`만 다른 곳으로 옮기지 마세요.** `tasty.pdb`가 옆에 없으면 backtrace에 잘못된 함수 이름이 표시될 수 있습니다. `tasty.pdb`가 있어도 일부 프레임의 함수 이름은 정확하지 않을 수 있습니다.

## 더 자세한 로그 받기

기본 로그로 원인을 알기 어려우면 `TASTY_LOG`로 로그 수준을 높여 다시 재현할 수 있습니다. **먼저 이전 로그를 복사하세요.**

macOS·Linux에서는 Tasty 외부 터미널에서 다음과 같이 실행하면 표준 오류 출력(stderr)을 `tasty.log`에 저장합니다. 실행 중인 Tasty가 있다면 로그를 복사한 뒤 종료하고 실행하세요.

```sh
TASTY_LOG=debug tasty 2> tasty.log
```

표준 오류 출력에는 로그와 크래시 메시지, backtrace가 나옵니다. Windows GUI 빌드는 콘솔 출력이 보이지 않고, macOS 앱 번들로 실행할 때도 콘솔 출력을 보기 어렵습니다. 이 경우에도 데이터 폴더의 로그와 리포트를 모으세요.

## 진단 명령

버전은 다음 명령으로 확인합니다.

```sh
tasty --version
```

Tasty가 실행 중이고 응답한다면 다음 출력도 함께 모으세요.

```sh
tasty list info
tasty list pressure
```

`tasty list pressure`는 이번 실행의 연결·요청 처리 상태와 진단 누계입니다. 재시작하면 누계가 초기화됩니다. GPU나 반복되는 멈춤 문제라면 `tasty list gpu-stats`, `tasty list timers` 출력도 도움이 됩니다. 명령이 응답하지 않으면 반복 실행하지 말고 [CLI 응답 지연과 연결 진단](cli-diagnostics.md)을 참고하세요.

## 멈춘 상태의 스택 표본

아직 실행 중인 Tasty가 멈춰 있다면 OS 도구로 스택 표본을 수집할 수 있습니다. 종료한 뒤에는 그 상태의 표본을 얻을 수 없습니다.

Linux에서 GDB가 설치되어 있고 해당 프로세스에 연결할 권한이 있다면, Tasty 외부 터미널에서 `gdb -p <PID>`로 연결하세요. `<PID>`는 멈춘 Tasty 프로세스의 ID로 바꿉니다. GDB에서 다음을 실행하고 출력을 저장하세요.

```text
thread apply all bt
detach
quit
```

Linux 배포본의 GDB 스택 표본에도 Tasty 함수 이름이 표시되며, Tasty 함수의 줄 번호는 표시되지 않습니다.

macOS·Windows에서 이미 수집한 프로세스 표본이나 덤프가 있다면 사용한 도구와 수집 시각을 적어 함께 첨부하세요.

## OS 자체 크래시 기록

이미 수집한 OS 크래시 기록이 있다면 문제 발생 시각과 일치하는지 확인하고, 사용한 도구와 수집 시각을 적어 함께 첨부하세요.

## 첨부할 것과 가릴 것

신고에는 다음 정보를 포함하세요.

- 직전에 하던 작업, 재현 순서, 발생 시각, 반복 여부
- `tasty --version` 출력, OS 버전과 아키텍처
- 해당 시각의 크래시·멈춤 리포트, 재실행 전에 복사한 `debug.log`, 관련 플러그인 로그
- 수집할 수 있었던 진단 명령 출력, 스택 표본 또는 OS 크래시 기록

**첨부할 복사본과 스크린샷에서 다음 정보를 가리세요.**

- `TASTY_SESSION_TOKEN` 값: 64자리 16진수이며 터미널 화면, 환경 변수 덤프, `ps` 출력에 보일 수 있습니다.
- 홈 경로에 들어 있는 사용자 이름과 작업 폴더 경로
- 원격 attach 호스트 이름과 SSH 사용자 이름

첨부할 모든 파일은 로그를 포함해 토큰과 개인 정보가 들어 있는지 확인하고 가리세요. 플러그인 로그에는 파일 경로가 남을 수 있으므로 홈 경로도 가리세요. 덤프와 OS 기록도 같은 기준으로 확인하세요.
