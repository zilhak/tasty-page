# CLI の応答遅延と接続の診断

`tasty` コマンドの応答が遅い、接続できない、`Error (-32061)` のようなエラーで終了する場合に読むページです。応答待ちの上限とタスクの待機時間の違い、エラーコード別の対処、この Tasty が対応する機能の確認、`tasty list pressure` で見る接続数・リクエストキュー・データベースの状態を扱います。初めて CLI を使う場合は、[tasty CLI でターミナルを操作する](../agents/cli.md)から読んでください。

## 応答待ちとタスク待ちの区別

- `tasty --response-timeout-ms MS <コマンド>` は、CLI が Tasty の**応答**を待つ上限です。コマンドの前に記述してください。
- `tasty agent task-await --timeout-ms MS` は、**タスク**が終わるのを待つ時間です。省略すると 10 分、`0` なら無期限に待ちます。結果は応答の `outcome` で通知され、タイムアウトでも終了コードは 0 です（[タスクの待機と管理](../agents/tasks.md#タスクの待機と管理)）。
- `tasty pty state` と `tasty agent barrier-state` は待機せず、現在の状態をすぐに返します。待機するには再度呼び出してください。

両方の時間を指定したとき、応答待ちの上限がタスクの待機時間より短いと、タスクが終わる前に CLI が `Error (-32061)` で終了します。応答待ちの上限をタスクの待機時間より長く設定してください。

## 応答待ちに上限を設ける

```sh
tasty --response-timeout-ms 5000 read screen --surface 42
```

`--response-timeout-ms` はコマンドの**前**に記述してください。その時間内に応答がないと、コマンドは `Error (-32061): …` で終了します。このエラーは**結果が不明**であることを意味します — リクエストは Tasty 内で実行を続けている可能性があるため、何かを変更するコマンドだった場合は、再送する前に状態を確認してください。リクエストが Tasty 内で順番を待っている間に時間切れになった場合は、代わりに `Error (-32067): …` で終了します。この場合は**何も実行されていないため**、そのまま再送してください。フラグを指定しない場合や `0` を指定した場合は、上限なしで待ちます。

1 回のリクエストで完結するコマンドにのみ使用できます。`events follow` のように繰り返し問い合わせるコマンドや、リモートアタッチのように接続を開くコマンドは、このフラグを受け取ると何も送信せず、終了コード 2 で拒否します。

上限を認識できない旧バージョンの Tasty にはリクエストを送信しません。この場合、コマンドは stderr に `{"error":{"kind":"unsupported_capability",…,「sent」:false}}` ではなく `{"error":{"kind":"unsupported_capability",…,"sent":false}}` という 1 行を書き込み、終了コード 1 で終了します（[この Tasty が対応する機能の確認](#この-tasty-が対応する機能の確認)）。その確認も同じ時間に含まれます — Tasty が停止していて確認さえ時間内に終わらない場合は、リクエストを送信せず `Error (-32067): …` で終了するため、この場合もそのまま再送してください。

## この Tasty が対応する機能の確認

`list info` は、この Tasty が何に対応しているかも `capabilities` で返します。名前とバージョンが対になっており、バージョン文字列だけでは分からないことをここで確認できます — 同じバージョンでも、ビルド構成によってできることが異なります。知らない名前はそのまま無視してください。

コマンドが `"sent":false` を含むエラー 1 行で終了した場合、接続先の Tasty がその機能を認識しない旧バージョンのため、リクエストを送信していません。`capability` に記載された名前が、不足している機能を示します。

## エラー別の対処

- **`"sent":false` を含むエラーが 1 行表示されます** — 接続先の Tasty は、その機能（読み取り位置の指定、応答待ちの上限など）を認識しない旧バージョンです。リクエストは送信していません。`capability` に記載された名前が、不足している機能を示します。
- **`Error (…)` 行の下に `data: {…}` 行が付きます** — Tasty が失敗の分類を併せて送信しています（例: メモリ保存失敗の `storage_failure`、拒否理由の `reason`）。`data: ` の後は 1 行の JSON なので、スクリプトでは最初の行の代わりにこの値で分岐できます。最初の行の `Error (コード): メッセージ` は、この行の有無にかかわらず同じです。`tasty events follow` と `tasty plugin audit-follow` もこの行を付けます。この 2 つのコマンドの最初の行は、先頭に `Error: ` がもう 1 つ付いた `Error: Error (コード): メッセージ` という形式のままです。
- **`Error (-32603): memory writer queue is full …` で終了します** — メモリ保存リクエストが一度に集中し、Tasty がこのリクエストを受け付けませんでした（`data` の `storage_failure` が `busy`）。保存されていないため、少し待ってから再度呼び出してください。`memory writer is not accepting requests` は、Tasty が終了処理中であることを意味します。
- **セッショントークンを使うエージェントのリクエストが `Error (-32000): host is busy: the request gate could not reach the memory writer …` で終了します** — リクエストを受け付ける前に確認するセッション判定を、Tasty がストレージに入れられませんでした（`data` の `storage_failure` が `busy`）。リクエストは実行されていないため、少し待ってからそのまま再度呼び出してください。`Error (-32000): host is shutting down` は、Tasty が終了処理を開始し、リクエストを実行しなかったことを意味します。トークンなしで呼び出す CLI コマンドは、この確認を経ません。
- **メモリ・エージェント協調コマンドが `"outcome":"unknown"` を含むエラーで終了します** — 保存が完了したかを Tasty も確認できませんでした。同じリクエストを再送する前に、`tasty memory get` などで値を確認してください。応答を待っている間にコマンドを中断しても、すでに受け付けた保存リクエストはキャンセルされません。
- **`Error (-32065): …` で終了します** — Tasty が処理するリクエストが滞留しているため、このリクエストを受け付けませんでした。リクエストは実行されていないため、少し待ってからそのまま再度呼び出してください。
- **`Error (-32066): …` で終了します** — 接続後 20 秒以内にリクエストを送信しなかったため、Tasty が接続を閉じました。何も実行されていません。直接ソケットを開くツールの場合は、接続直後にリクエストを送信してください。一度リクエストを送信した接続は、リクエスト間で長く待機しても閉じられません。

## リクエストの処理規則

セッショントークンを使用するエージェントの呼び出し上限は、通常のコマンドだけでなく、プラグインコマンドと一覧全体の取得にも適用されます。許可されたリクエストは呼び出し量に 1 回記録され、上限を超えるとリクエストを実行せずにエラーを返します。トークンのないローカル CLI の既存の例外は維持されます。

プラグインの namespace 呼び出しは、有効な所有元プラグインと、該当する IPC フックに必要な有効な拡張だけを起動します。無効なプラグインを有効にしたり、無関係なプラグインを起動したりはしません。存在しない namespace は何も起動しません。既知の namespace 内のメソッド名の誤記は、所有元プラグインを起動した後にエラーを返す場合があります。

構造変更リクエストがキューまたは保存予算の上限を超えると、`-32065` エラーを受け取ります。他のリクエストが一時的に使用している保存予約枠が不足している場合は、上限内で待機します。同じ冪等キーで異なるリクエストを送信すると、`-32063` エラーを受け取ります。

あるウィンドウの構造変更が外部タスクの完了を待っている間も、対象を明示した別のウィンドウの独立した構造変更リクエストは進行できます。同じ対象範囲のリクエストの順序は維持されます。

## 応答の遅延と接続状態の確認

`tasty list pressure` は、リクエストの待機・処理時間、接続数、拒否理由を表示します。
項目ごとに測定対象が異なるため、リクエスト数同士を引いて拒否数を計算しないでください。
累計はインスタンスの起動後に蓄積され、測定したことのない平均は `null` です。
現在の使用量と設定値は、以下で別々に区別します。

| 時間の項目 | 測定対象 |
|---|---|
| `queue_before_gate` | キューで待機した時間。後で権限検査により拒否されたリクエストも含みます |
| `handler_after_gate` | 検査を通過して実際に処理したリクエストの時間 |
| `plugin_round_trip` | プラグインに送信したリクエストのうち、応答が届いたリクエストの待機時間 |
| `db` | データベースの commit と WAL checkpoint にかかった時間、1 回の commit で保存された書き込み数、別途集計した VACUUM |

キュー待ちが長い場合はリクエストが滞留していないか、処理時間が長い場合はどのコマンドに時間がかかっているかを確認してください。
プラグインの待機が長い場合は、該当するプラグインのログを調べてください。DB の時間は保存処理と競合を
調査する根拠ですが、この値だけでディスクの問題とは断定できません。commit 時間は処理時間にも
含まれるため、両方の時間を足すと重複します。`checkpoints_busy` は、他の接続が原因で checkpoint を
完了できなかった回数です。`writes_per_commit` は、1 回の commit で保存された書き込み数の分布です。
commit 数に含まれないデータベースの圧縮（VACUUM）は、`vacuums` で別途集計します。
`memory_writer` は、保存リクエストをまとめて処理するキューの受け付け・拒否・バッチの数です。
`state_writer` と `state_db` は、最近使ったファイルとチュートリアルの進行状況を保存するキューの同じ数と commit 時間です。
ヘッドレス実行や `state.db` を開けなかった実行では `null` です。

保存キューの `batch_wait` はバッチの実行前の待機、`batch_execution` は再試行の待機も含めたバッチ処理、`executor_execution` は実際の処理呼び出しの時間分布です。単位はマイクロ秒で、`samples` が 0 ならまだ観測していません。`queued_items`・`queued_bytes` は、まだ実行に渡していないキューだけを数えます。`pending_bytes` と `oldest_pending_age_us` は、未完了のリクエストの入力サイズと、最も古いリクエストの経過時間です。未完了のリクエストがない場合、経過時間は `null` です。すでに完了していても結果を読み取っていないリクエストは、`held_bytes` に残る場合があります。この経過時間はファイルの未保存の変更からの経過時間ではなく、完了数やバッチ数が実際のディスクへの commit 数を意味するわけでもありません。

`journal` は、GUI とヘッドレスの両方で、ジャーナル処理の受け付け・拒否・待機・実行中の数を表示します。
処理段階の数はユーザーコマンド数とは異なり、バイト数は入力サイズの推定値です。`store` 内の
`physical_commits` は実際の SQL commit 数、`structural_commits` は構造変更を含む commit 数、
`logical_requests` は確定した論理リクエスト数です。時間分布は固定区間に累積されます。
`dirty_age_us` が `null` なのは、この計測ではその時間を提供しないことを意味します。
`unpublished_age_us` は、保存後に画面への反映確認を待った時間で、取得しても値は消去されません。
実際の SQL commit が失敗し、確定状態を再確認する必要がある場合、`publication_known` は `false`、
`unpublished_age_us` は `null` です。この場合、ジャーナルを再度開いて検証するまで unknown のまま維持します。
ジャーナルのないテスト構成では `journal: null`、まだストレージが開かれていない場合は `store: null` です。

`file_snapshots.settings` は、GUI とヘッドレスの両方で、メモリに適用した設定と保存が確認された設定の差を表示します。`dirty` が true の場合、まだ保存が確認されておらず、`dirty_age_us` は最初の未保存の変更から経過したマイクロ秒です。新しい変更・失敗・結果不明・再試行・以前の変更の保存成功によって、この時間はリセットされません。最新の変更の保存成功が確認されると、`dirty` は false、経過時間は `null` になります。失敗後、`pending` が 0 でも未保存の変更が残る場合があります。この取得は保存完了処理を早めません。

`state_snapshots.recent_files` は、GUI の最近使ったファイル一覧に保存が確認されていない変更があるか（`dirty`）と、その状態が最初に始まってから経過したマイクロ秒（`dirty_age_us`）を表示します。別の種類の一覧を変更したり、保存が失敗・拒否・結果不明で終わったりしても、時間は継続します。すべての種類の最新の一覧が保存されたと確認されると、経過時間は `null` になります。種類ごとの経過時間を個別に表示する値ではなく、取得によって保存結果が回収されるわけでもありません。ヘッドレスや状態 DB を開けなかった実行では、この一覧の状態は `null` です。

権限・上限・頻度制限による拒否数は、以下の `gate_refusals` で確認してください。

### 接続数と上限（`connections`）

| フィールド | 意味 |
|---|---|
| `live` | 現在の接続数。接続が閉じると減少します |
| `live_max` | 起動後の同時接続数の最大値 |
| `limit` | 許可する同時接続数の上限 |
| `accepted` | 受け入れた接続数の累計 |
| `refused_saturated` | 接続上限によって拒否した数の累計 |

リクエストを送信していない接続も live に含まれます。live が limit に近い場合や
refused_saturated が増加する場合は、使用していないアタッチなどの持続接続を整理してください。
この拒否はリクエスト処理前に発生するため、リクエスト処理時間には現れません。
接続不足と処理遅延は同時に発生する場合もあります。

`accept_wait_bound_us_max` と `accept_wait_bound_us_mean` は、接続受け入れの待機時間の
上限を最大値・平均値で表示します。`accept_waits` は記録数で、
`accept_wait_bound_us_sum` は上限値の合計です。実際の待機時間を直接測定した値ではありません。
接続キューが最後に空だった時点から計算するため、実際の待機はこの値より短い場合があります。
空のキューを確認した後、デフォルトで 100ms 待機しますが、100ms が待機全体の厳密な上限ではありません。
この時間はリクエストキューの待機とは別で、観測が蓄積されるにつれて平均が下がる場合もあります。

### 時間分布

前述の 3 つの時間項目にのみ、`wait_us_hist` または `us_hist` があります。
`bounds_us` は 10µs から 1 秒までの 11 個の区間境界で、`counts` は区間ごとの件数です。
最後は 1 秒を超える区間なので、counts の要素数は 1 つ多くなります。区間は重複せず、合計は
観測数です。最長時間は該当項目の max 値で確認してください。p99 のような分位数は提供しません。

`queue_before_gate.waits` は待機時間を測定したコマンド数で、平均計算の分母です。
`commands` はバッチの処理が完了してから増加するため、処理中のバッチの分だけ waits より小さい場合があります。
平均と分布を併せて見ると、全体的な遅延と一部のリクエストだけに時間がかかる場合を区別できます。

### データベース設定（`db_pragmas`）

`memory_db` と `state_db` ごとに、要求した設定（requested）と実際の適用値（effective）を表示します。
DB を開くときに確認した設定で、累積カウンターではありません。

| 値 | 意味 |
|---|---|
| `degraded: true` | 設定が期待した状態ではないか、ファイル DB の代わりに一時メモリで動作中 |
| `state_db: null` | このインスタンスで状態 DB が開かれていません。headless でもこの値を使用します |
| `memory_db.init_failure` | ファイル DB を開けず、一時メモリに切り替えた原因（cause）とエラー（error）。正常時は null |

設定の不一致があっても DB は引き続き使用できます。パフォーマンスと障害後の復旧に影響する可能性があるため、
requested と effective を比較してください。一時メモリは設定がすべて適用されても degraded が true で、
その間に保存した値は再起動後に消失します。

### 画面の転送（`stream_push`）

| フィールド | 意味 |
|---|---|
| `frames_dropped` | 受信側が追いつかずに破棄したフレーム数の累計 |
| `clients_lagged_out` | 遅延が大きくなり接続を切断した受信側の数の累計 |
| `backlog` | 現在送信を待っているフレーム数。送信されると減少します |
| `sink_capacity` | 1 つの接続が保持できるフレーム数の上限 |

frames_dropped が増加した場合、アタッチが画面の一部を受信できなかった可能性があります。
Tasty のアタッチは、再接続リクエストを受け取ると再接続して画面を新たに受信します。

### リクエストキュー（`queue_admission`, `queue_dispatch`）

queue_admission は、キューに入った量と、入る前に拒否したリクエストを表示します。

| フィールド | 意味 |
|---|---|
| `queued_bytes`, `queued_commands`, `queued_injected` | 現在待機中のバイト数・コマンド数・内部コマンド数 |
| `peak_bytes` | 起動後の待機バイト数の最大値 |
| `limit_bytes`, `limit_injected_depth` | バイト数と内部コマンド数の上限 |
| `refused_bytes`, `refused_depth` | 各上限によって拒否したリクエスト数の累計 |

キューがいっぱいであるというエラーが出た場合は、この値を確認してください。キューに入る前に拒否したリクエストは、
キューの待機・実行時間に含まれません。

queue_dispatch は、キューから取り出して処理する過程を表示します。

| フィールド | 意味 |
|---|---|
| `rounds` | コマンドを取り出して処理した回数 |
| `rounds_stopped_by_count`, `rounds_stopped_by_time` | 一度に処理する個数・時間を使い切って停止した回数 |
| `expired_before_run` | キューで待機中にリクエスト元の制限時間が過ぎ、実行しなかった数 |
| `started` | 実行を開始したコマンド数 |
| `in_flight`, `in_flight_max` | 実行開始後、コマンドまたは応答待ちがまだ終わっていないリクエストの現在数と最大値 |

in_flight は減少することがあります。呼び出し元が待機をやめても、コマンドが実行中なら引き続き集計します。時間制限によって停止した回数や expired_before_run が増加する場合は、
キューの処理がリクエストに追いついているか確認してください。

分類の作成・名前変更・削除・順序変更と、ワークスペースの情報・順序変更は、同じ再試行キーでリクエストすると、アプリの再起動後も最初の結果を返します。対象が後で移動したり名前を変更されたりしても、新しい対象を選び直しません。リモート画面のローカル表示名と位置は、保存結果を再取得するときに再適用しません。他のコマンドまで、再起動後の重複防止が保証されるわけではありません。

### 重複リクエストの処理（`keyed_requests`）

冪等キー（idempotency_key）を付けたリクエストだけを数え、1 つのリクエストは 1 回だけ集計します。

| フィールド | 処理結果 |
|---|---|
| `executed` | 新しいキーのリクエストを実行 |
| `replayed` | 同じリクエストに以前の結果を返し、再実行しません |
| `conflicted` | 同じキーで異なる内容が送られたため、実行しません |
| `discarded` | 実行しましたが、応答は破棄 |
| `in_flight` | 同じリクエストが実行中のため、その結果を一緒に待機 |

replayed が executed より速く増加する場合は、再試行が繰り返されていないか確認してください。
この in_flight は、queue_dispatch の現在の実行数とは異なる集計です。

### 遅いリクエストの詳細（`slow_requests`）

キュー待ち・ホスト処理・プラグイン待ちの合計が threshold_us（100ms）以上のリクエストを、
古い順に最大 capacity（32）件表示します。超過すると、最も古い記録から破棄します。
admitted は起動後に記録した累計で、現在残っている件数との差が押し出された件数です。

| フィールド | 内容 |
|---|---|
| `request_seq` | Tasty が付与した番号。リクエストの id とは異なる値 |
| `host` | method, caller, queue_wait_us, host_us, outcome(ok/error), error_code |
| `plugin_hops` | プラグインごとの host_request_id、待機時間、ok/error/expired/cancelled の結果 |
| `total_us` | 測定時間の合計 |

まだ応答していない場合、host の outcome と error_code は null です。
plugin_hops が長い場合は、プラグインのログで host_request_id と同じリクエスト ID を探してください。
プラグインのエラー・無応答ログには、id と request_seq が併記されます。
リクエスト本文とトークンは保存せず、pressure の取得自体もこの一覧から除外します。
再起動すると記録が空になり、番号も 1 から再び始まります。

### リクエストの拒否理由（`gate_refusals`）

judged は権限などを検査したリクエスト数で、CLI リクエストとプラグイン呼び出しを含みます。
1 つのリクエストは、次の理由のうち最大 1 つに集計されます。

| フィールド | 理由とエラーコード |
|---|---|
| `permission_denied` | 権限検査で拒否、-32001 |
| `cap_blocked` | テレメトリの上限に到達、-32007 |
| `throttled` | 呼び出し頻度の制限に到達、-32010 |

権限・使用量の上限を確認するか、頻度制限が解除されるまで待ってください。
権限による拒否には、権限不足だけでなく、プラグイン・エージェントが使用できないコマンドや、
存在しないコマンドを呼び出した場合も含まれます。後の 2 つの場合は権限リクエストでは解決しないため、
コマンドを確認してください。セッショントークンのないローカル CLI の権限免除は維持されます。

すべての -32001 エラーが permission_denied に含まれるわけではありません。
不正なセッショントークンや、未登録・期限切れ・失効したセッショントークンは検査前に拒否するため、judged にも含まれません。
検査を通過した後、権限付与リクエストなどが拒否した -32001 も、このカウンターから除外します。
この累計は再起動すると 0 になります。`tasty agent rate-limit-status` の throttled_count は、
個別の制限の永続的な累計なので、異なる値です。
