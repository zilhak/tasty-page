# Claude・Codex と一緒に使う

Claude Code と Codex CLI を Tasty のターミナルで実行し、状態を確認します。両方の CLI は別途インストールする必要があります。複数のエージェントにタスクを分担させるには、フックと親の結果受信経路をあわせて設定してください。

子の応答終了とタスクの成功は異なります。親が Claude Code か Codex かによって、結果を受け取る経路が変わります。フックは状態を伝え、親の受信経路はその状態や結果への参照を会話に届けます。結果を読み、実際の変更と実行結果を照合してください。

## クイックスタート

1. フックをインストールします: `tasty claude install`、`tasty codex install`（[フックのインストール](#1-フックのインストール初回のみ)）。
2. エージェントを起動します: `tasty claude launch --workspace myproj --directory ~/proj`（[起動する](#2-起動する)）。
3. その Claude Code セッション内で、別のエージェントにタスクを任せます: `tasty claude spawn --workspace workers --cwd ~/proj --prompt "cargo test を実行して失敗の原因を報告して"`（[タスクを任せる](#3-別のエージェントにタスクを任せるspawn--tell)）。
4. 状態と結果を確認します: `tasty claude children` で子の一覧と状態を確認し、完了は[完了通知を受け取る](#4-完了通知を受け取る)の方法で受け取ります。

`tasty claude help`・`tasty codex help` の最後の「内部連携」グループはフックが呼び出すコマンドなので、直接入力しません。承認ポリシー、権限モード、セッションの再起動、セッションプロファイルについては、必要なときに後の節を参照してください。

## 1. フックのインストール（初回のみ）

Tasty がエージェントの状態（作業中 / 待機 / 入力が必要 / 終了）を把握するには、各 CLI のフック設定に Tasty の項目が必要です。

```sh
tasty claude install    # Tasty フックと完了通知 mod をインストール
tasty codex install     # ~/.codex/config.toml の [hooks] に Tasty の項目を追加
```

- すでに自分で追加したフックはそのまま保持されます。複数回実行しても重複しません。
- Claude の設定フォルダーを別の場所にリンクして使用していても、インストールと削除は同じ管理フォルダーを参照します。Tasty が管理する mod 内のファイルやフォルダーが別の場所にリンクされている場合は、インストールと削除を拒否します。
- **Tasty を更新した後は、再度実行してください。** フックのコマンド文字列は設定ファイルに保存されるため、新しい形式を反映するには再インストールが必要です。
- Claude Code が API エラー（サーバー過負荷・リクエスト上限・認証失敗など）でターンを終了した場合に待機として通知するフックも、再インストールしないと追加されません。それまでは、そのような子は「作業中」と表示され続けます。
- 子がバックグラウンドタスク（バックグラウンドシェル・バックグラウンドサブエージェント）を残したまま API エラーでターンを終了した場合は、タスクが終わり、それに続くターンが終了するまで「作業中」のままにします。この動作も再インストールしないと追加されません。
- Codex で `hook returned invalid ... JSON output` エラーが表示された場合は、更新後に `tasty codex install` を再度実行してください。Tasty の状態通知の結果が Codex のフック応答に混ざらないように設定されます。
- Tasty の外で Claude Code を実行すると、このフックは動作しません。
- Codex は、新しくインストールされたフックや変更されたフックをレビューするまで実行しません。インストール後、Codex の `/hooks` で Tasty のフックを確認して承認してください。Tasty はこのレビューを省略しません。
- 削除は `tasty claude uninstall` / `tasty codex uninstall` です。

別の Codex home や profile を使用する場合は、インストール先を指定してください。2 つの場所指定オプションは併用しません。
既存のほかのフックとモデル設定は保持します。

```sh
tasty codex install --codex-home /absolute/codex-home
# profile ファイルを直接選択する場合:
tasty codex install --config-file /absolute/codex-home/work.config.toml
```

インストールしたフックが現在のセッションで正常に実行されると、Tasty が状態とセッション情報を受け取ります。

- エージェントが応答を終えたり質問したりすると、そのサーフェスの**注意喚起の枠線**が点灯し、サイドバーのワークスペースにバッジが付きます（質問への回答待ちは黄色を優先）。
- タブを閉じてから復元したり、Tasty を再起動したりすると、同じセッションを再開します（`claude -r` / `codex resume`）。
- 子の状態・結果を親が受け取るには、[受信設定](#4-完了通知を受け取る)も必要です。完了は完了ログに 1 行ずつ蓄積され、対応する親の Claude Code は完了通知 mod で受け取ります。

`tasty codex install` 後は、Tasty の Bash・zsh ターミナルで、いつもどおり `codex` や `codex resume` を
入力しても復元情報が保存されます。セッション選択画面をそのまま使用でき、選択した会話は新しいメッセージを
送信する前でも復元対象として記録されます。承認・サンドボックス・モデルのオプションも保持されます。
起動時に指定した承認・サンドボックスのオプションは、同じ Codex 内で開始した新しい会話（`/new`）にも適用されます。
Codex 内で `/permissions` を使って権限を変更すると、それ以降の新しい会話は変更後の値に従い、復元時は起動時に指定したオプションで開き直します。
更新後はインストールコマンドを再度実行し、新しいターミナルで開始してください。ユーザー全体のシェル設定は変更しません。

Tasty はターミナルごとに専用の Codex サーバーを起動し、Codex を終了するかターミナルを閉じると、一緒に終了処理を行います。
すでに実行中の会話や共有サーバーには再接続しません。Codex CLI 0.154.0 を基準としています。
プラグインカタログや会話履歴が大きくても、応答サイズだけを理由に接続を切ることはなく、一覧を切り詰めずに渡します。
起動画面での自動復元は、Tasty の準備ができるまで最大 30 秒待ってから進みます。起動後に別途ターミナルを起こす必要はありません。

自動連携は、承認・サンドボックス・モデル、作業ディレクトリ（`-C`）、セッション選択オプションに対応しています。
`-c`、プロファイル、`fork` など、対応していないオプションは案内を表示した後、元の Codex で実行され、自動復元には登録されません。
`command codex`、明示的な `--remote`、非対話型コマンドも元のまま実行されます。
Bash・zsh 以外のシェルでは、以下の `tasty codex launch` を使用してください。

## 2. 起動する

```sh
tasty claude launch --workspace myproj --directory ~/proj --task "テストを修正する"
tasty codex launch --workspace review --directory ~/proj
```

新しいワークスペースを作成し、そのターミナルで CLI を実行します。`--workspace` を省略すると、名前は `claude` / `codex` になります。

Codex は `--approval untrusted|on-request|never`、`--sandbox read-only|workspace-write|danger-full-access`、`--full-auto` で承認・サンドボックスポリシーを指定できます（後述の「Codex の承認ポリシー」）。

Claude Code は `--permission-mode` で権限モードを指定できます（後述の「Claude の権限モード」）。

Claude Code プラグインが有効な場合、Claude Code セッション内で Tasty を実行しても、Tasty ターミナルのシェルとフックコマンドには、そのセッションを指す環境変数（`CLAUDECODE`、`CLAUDE_CODE_CHILD_SESSION`、`CLAUDE_CODE_MESSAGING_TOKEN` など）が渡されません。そのターミナルで実行した Claude Code は独立したセッションとして動作し、会話履歴も保存します。`CLAUDE_CODE_GIT_BASH_PATH` のように自分で設定した Claude Code の環境変数はそのまま渡されます。同様に、Codex プラグインが有効な場合は、Codex の会話から Tasty を実行しても、その会話を指す `CODEX_THREAD_ID` が渡されないため、そのターミナルのシェルや Claude が呼び出した `tasty` を外側の Codex からの呼び出しとは見なしません。`CODEX_HOME` はそのまま渡されます。プラグインを無効にすると、そのプラグインの変数は削除せず、そのまま渡します。

## 3. 別のエージェントにタスクを任せる（spawn / tell）

Claude Code セッションで、次のコマンドを使って別のエージェントを実行してみてください。タスクを任せる側を親、新しく実行した側を子エージェントと呼びます。新しいエージェントは指定したワークスペースのペイン内にタブとして開き、この関係が記録されます。

```sh
tasty claude spawn --workspace workers --cwd ~/proj --role tester --nickname t1 \
  --prompt "cargo test を実行して失敗の原因を報告して"
tasty codex spawn --workspace workers --cwd ~/proj --sandbox read-only \
  --prompt "直前にコミットされた diff をレビューして"
```

| オプション | 意味 |
|---|---|
| `--workspace <ID または名前>` | 必須。子を配置するワークスペース |
| `--pane <ID>` | ワークスペースの特定のペイン（デフォルト: 最初のペイン） |
| `--cwd <パス>` | 子の作業ディレクトリ |
| `--role <ラベル>` | 役割ラベル。`broadcast --role` で送信先を選ぶときに使用します |
| `--nickname <名前>` | タブに表示する名前 |
| `--prompt <テキスト>` | 起動直後に送信する最初の指示 |
| `--surface <ID>` | 親サーフェス（デフォルト: 自分自身） |

`spawn` は**即座に戻ります**。別途待機するコマンドはありません。子のフックと[受信設定](#4-完了通知を受け取る)を済ませると、子が報告した待機状態を親に届けます。待機はタスクの成功を意味しません。Claude の子のサブエージェントが終了した場合や、バックグラウンドタスクを残したまま応答が終了した場合は、待機とは見なしません。バックグラウンドタスクが終わり、それに続く応答まで終えると通知します。[Stop ゲート](#8-claude-のセッションプロファイルと-stop-ゲート)がチェックリストを送り、応答を続けさせた場合も待機とは見なさず、ゲートを通過して応答が終了すると通知します。終了しないバックグラウンドコマンド（開発サーバーなど）を残すと、待機状態にはなりません。バックグラウンドタスクを待っている間に出力がなければ、親に 1 回通知します。デフォルトの基準は 10 分で、出力ファイルが見つかったか、Monitor だけが残っているかによって異なります（[4 節の出力なし通知](#4-完了通知を受け取る)）。

親は自分のワークスペースとは**別のワークスペース**に子を配置するほうが安全です。接続したリモートワークスペースで子を実行する方法と結果を受け取る条件は、後述の「[接続したリモートワークスペースに子を作成する](#接続したリモートワークスペースに子を作成する)」節で説明します。子はリモートコンピューターのツールと設定で実行されます。

その後、子に追加の指示を送ったり、状態を確認したりします。

```sh
tasty claude tell "今度は clippy も実行して" --surface 57     # 複数行可、自動送信
tasty claude children                                       # 子の一覧 (index · surface · 状態)
tasty claude state --surface 57                             # idle / needs_input / active / exited
tasty claude broadcast "進捗を報告して\r" --role tester   # 役割ごとに一括送信 (\r で送信)
tasty claude kill --child 0                                 # index で終了
tasty claude respawn --child 0 --prompt "やり直して"          # 同じ場所で再起動
tasty claude parent --surface 57                            # この子の親
```

プロンプトなしで起動した Claude の子は、入力待ち画面が表示されると `idle` になります。この時点では完了通知は届きません。完了通知は応答を終えたときだけ届きます。`--prompt` で起動した子は、そのプロンプトを処理している間は `active` です。

`tasty codex …` にも同じサブコマンド（`tell` / `children` / `state` / `broadcast` / `kill` / `respawn` / `parent`）があります。Codex の会話で実行すると、結果を受け取る方法が異なります（[Codex の親に自動的に届ける](#codex-の親に自動的に届ける)）。

子が多くなりすぎると、spawn の応答に警告が付きます。しきい値は**設定** <!-- en: Settings --> › **プラグイン** <!-- en: Plugins --> › **Claude Code** / **Codex** の **Spawn child 警告しきい値** <!-- en: Spawn child warning threshold --> で変更します（Claude Code・Codex ともにデフォルトは 6）。

### Claude の子のモデルと effort

今回の子セッションにだけモデルと effort を指定できます。

```sh
tasty claude spawn --workspace workers --cwd ~/proj --model opus --effort high \
  --prompt "テスト失敗の原因を調査して"
```

`--model` は別名、完全なモデル ID、provider ARN などの識別子を受け付けます。`--effort` は `low`、`medium`、`high`、`xhigh`、`max`、`ultracode` を受け付け、対応状況は Claude CLI とモデルによって異なります。`ultracode` は xhigh と Ultracode を要求し、Claude Code 2.1.203 以降が必要です。

省略したオプションは既存の Claude 設定に従います。親・ほかの子・グローバル設定は変更しません。`--profile-file` や `--profile` と併用した場合は、明示したモデル・effort が優先され、プロファイルファイルはそのままにします。フックが正常に実行されると、同じセッションを復元したり reboot したりするときにも保持します。新しい respawn はこの値を引き継ぎません。

コマンドが戻ったことは、モデルが応答したことを意味しません。provider がモデルを拒否しても、Tasty は別のモデルに切り替えて再試行しません。実際のモデルと effort は Claude の画面で確認してください。

## 4. 完了通知を受け取る

親が Claude Code または通常のターミナルの場合、子が Claude か Codex かに関係なく、状態通知は親の完了ログに 1 行ずつ蓄積されます。Codex の親会話は、後述の別の結果返却経路を使用します。
同じ子に tell を複数回送っても、状態が 1 回変わると 1 行だけ記録されます。別の親が同じ子に送った tell の通知は、その親のログに別途記録されます。
入力要求・中断・エラー・プロセス終了も状態通知なので、通知をタスクの成功と断定しないでください。
Claude の子が API エラーでターンを終了した場合は、完了通知行の末尾にその事実とエラーの種類（例: `overloaded`）が付きます。バックグラウンドタスクが残っていて子が待ち続けている場合は、完了行の代わりに、その事実を記した行が 1 回記録されます。
Claude の子の出力なし通知は、デフォルトで 10 分（600 秒）を基準とします。[設定 > プラグイン > Claude Code](../plugins/index.md#プラグインが追加する設定)で 60～86400 秒に変更でき、再起動せずに反映されます。通知を無効にする値はありません。

バックグラウンドシェルやサブエージェントを待っている子は、見つかったタスク出力ファイルがすべて設定時間の間変化しないと、タスク名を記した行を 1 回の待機につき 1 回記録します。英語の行は `background work <名前> has written no output for <分> min` です。タスクの出力が見つからない場合は、画面出力が 10 分と設定値のうち大きいほうの時間にわたって変化しないと、1 回の待機につき 1 回記録します。このときの英語の行は `waiting on background work (<種類>) for <分> min, with no output meanwhile` です。実際の通知はアプリの言語に従います。

Monitor はイベントがあるときだけ出力するため、静かなのが正常です。応答を終えて Monitor タスクだけが残っている子には、出力なし通知は送られません。そのような子は Monitor が終了するまで `active` のままで、完了シグナルも送られません。Monitor とほかのタスクが一緒にある場合は、ほかのタスクだけで判定します。

この通知は完了ログに記録され、以下の mod または Monitor の受信設定を済ませた親の Claude Code で新しいターンを開始させます。Codex の親会話から作成した子には、この通知経路は適用されません。Codex の親は、後述の結果返却経路でターン結果を受け取ります。

バックグラウンドタスクの待機中ではないターンで、最後の出力にエラー文言がある場合は、基準が 30 秒に固定されます。エラー直後の 30 秒と再通知の最小間隔 5 分は設定対象ではありません。同じ無出力期間では 1 回だけ通知します。この設定は `tasty claude children` の `stale` 表示基準である 120 秒とは別なので、通知より先に `stale` が表示されることがあります。通知だけでタスクが停止したとは断定しません。

Monitor を区別する新しいフックを取得するには、`tasty claude install` を再度実行してから、新しい Claude Code プロセスを開始してください。それまでは Monitor もシェルタスクと見なして通知します。

対応する Codex の親会話には、子の応答が終了したことを知らせる結果参照が届きます。参照に記載されたイベント ID で `tasty codex result` を実行し、回答を読みます。接続条件と対応経路は、後述の [Codex の親に自動的に届ける](#codex-の親に自動的に届ける)節に従ってください。

### Claude Code で自動的に受け取る

更新後は `tasty claude install` を再度実行し、新しい Claude Code セッションを開始してください。インストールコマンドは、既存のフックとほかのプラグインのパスを保持しながら、完了通知 mod と重複防止プラグインを一緒にインストールします。Claude Code 2.1.307 の mod API を基準に作成されています。実際のモデルターンでの受信検証は別であり、使用量制限や認証エラーを成功とは見なしません。

mod が有効になると、セッション開始時から自分の完了ログを読み、Claude が作業中の場合は、そのターンが終わった後にプラグインメッセージで通知します。新しいセッションは以前のログを再送せず、mod の再読み込みは保存された位置から読み続けます。通知が待機中に mod が再読み込みされても、通常は 1 回だけ届き、2 つ目のコピーをスキップしたという短い案内が表示されることがあります。まれに、配信中に重複防止プラグイン自体が再起動すると同じ通知がもう 1 回届くことがありますが、失われることはありません。この動作は、インストール後に新しく開始した Claude セッションから適用されます。未読のログが整理されると復元できません。状態通知はタスク成功の証拠ではありません。

その Claude の Bash で、`TASTY_CLAUDE_NOTIFY_MOD` の値が自分のサーフェス番号と一致するか確認できます。mod と Monitor を一緒に有効にすると、通知が重複します。既存の個人用指示やスキルにある Monitor の手順も、この目印があるセッションでは省略してください。Tasty がそれらのファイルを自動で変更することはありません。削除は `tasty claude uninstall` です。

### Claude Code の Monitor で受け取る

mod に対応していないか、有効にできていない親の Claude Code でのみ Monitor を使用します。最初の spawn/tell の前に購読し、購読直後に子の一覧も確認してください。

```text
Monitor({ command: "tail -n0 -F \"$TASTY_PARENT_HOME/notify/$TASTY_SURFACE_ID.log\"", timeout_ms: 1800000 })
```

Monitor は最大 30 分で期限切れになります。期限切れの通知を受け取ったら、同じコマンドで再度購読し、すぐに `tasty claude children` で子の状態を 1 回確認してください。この一覧には Codex の子も一緒に表示されます（`tasty codex children` も同じ子を表示します）。購読が切れている間に終了した子を見逃さずに済みます。

ログの文言はアプリの言語に従います。Claude と Codex の子が、同じファイルに通知を 1 行ずつ記録します。**Tasty を再起動すると、前回の実行の完了ログは削除されます。** Monitor なしでファイルを直接読むだけでは、自動再開や永続保存にはなりません。

新しい行を書き込む前に、ファイルサイズが **256 KiB** 以上なら、ファイル全体を空にしてから書き込みます。末尾部分だけを残すわけではないため、まだ読んでいない通知も一緒に消えます。1 行を追加したり、複数の子が同時に書き込んだりする間に、このサイズを超えることがあります。空にするときは通常、後述の `retention_start` の累計を、消去したバイト数だけ増やします。ほかの子が同時に書き込んでいて、整理の順番を時間内に得られない場合は、累計を増やさずに空にするため、そのとき失われた通知は累計からも把握できません。期間やファイル数の制限はなく、閉じたタブのログも次の再起動まで残ります。

完了ログを直接読み続ける場合は、隣の `<番号>.log.meta` ファイルにある `retention_start` も確認してください。これまでに消去されたバイト数の合計です。保存した読み取り位置とあわせて比較し、途中で記録が失われたか確認できます。ただし、ログの整理やメタデータの記録に失敗すると、累計に反映されない損失が生じることがあるため、すべての欠落を確認できる方法ではありません。Monitor の購読では、このファイルを直接読む必要はありません。

同じデータフォルダーで tasty を**二重に起動しないでください。** 後から起動した側が起動時に完了ログの
フォルダー全体を削除するため、そのとき先に起動していた側が書き込んでいた完了ログまで消えます。2 つを
一緒に使用するには、`TASTY_HOME` で別々のデータフォルダーを指定してください。

### Codex の親に自動的に届ける

Tasty をデスクトップから起動した場合でも、Codex の会話が使用する実行経路を自動で渡し、結果を受け取ります。実行経路や受信先を `spawn`・`tell` ごとに指定する必要はありません。

Codex の会話内で `tasty codex spawn`（または `tell`・`respawn`）を実行すると、子の応答が終わるたびに
結果がその会話に自動で戻ります。別途準備するコマンドはありません。

```sh
tasty codex spawn --workspace workers --cwd ~/proj --sandbox read-only \
  --prompt "直前にコミットされた diff をレビューして"
```

親会話には、次のような短い参照メッセージが届きます。子の回答本文は含まれません。

```text
[tasty] A child agent reported a turn boundary. provider=codex status=turn_ended event=<イベント ID>. ...
```

親はメッセージに記載されたコマンドで結果を読みます。

```sh
tasty codex result <イベント ID>
```

- 結果を受け取った会話でのみ読めます。何度読んでも結果は削除されません。
- 結果は、子の Codex がそのターンを実際に終えた後、そのターンの最後の回答として記録します。ほかの Stop フックが応答を続けさせても、途中の回答ではなく最後の回答が戻ります。
- `status` は応答がどのように終わったかを示すだけで、タスクがうまくいったかは判定しません。`turn_ended`（応答終了）、`interrupted`（ユーザーが中断）、`exited`（セッション終了。子が同じ画面で `/new` により会話だけを変更した場合は終了ではありません）、`turn_failed`（エラーで終了）があります。
- 回答が 1 MiB を超えると、切り詰めて保存し、`body_truncated` で示します。
- 同じ応答が 2 回報告されても、1 回だけ届けます。
- 共有 Codex サーバーに一時的に接続できず送信できなかった結果は、間隔を延ばしながら（最大 1 分）再送します。12 回を超えて失敗すると、その会話の次の結果が届いたとき、または Tasty を再起動したときに再送します。
- 結果は配信完了後 30 日間保存し、その後は削除します。

親が結果を受け取れるのは、次の 2 つの場合です。

- 親が Tasty の起動コマンドで起動した Codex です。親の Codex が一時的に終了している場合は結果を保存し、その会話が Tasty で再び開かれたときに送信します。同じ画面で `/new` により新しい会話を開始したり、別の会話に戻ったりすると、それ以降は現在実行中の会話が結果を受け取ります。
- 親が Tasty の外の Codex で、ユーザーの共有 Codex サーバーにその会話が開かれています。

どちらでもない場合は子を作成せず、結果を受け取れない親であるというエラーを表示します。Claude Code の親は[完了ログ](#4-完了通知を受け取る)で受け取ります。

Codex の会話は、自分が作成した子だけを管理します。同じ画面で `/new` により開始した新しい会話も、以前の会話の子を一覧に表示したり閉じたりできません。別の親の子への `tell` や、`--surface` による別の親の指定は拒否します。Claude Code や通常のターミナルから同じ子に新しい指示を送ると、それ以降の結果は元の Codex の会話に戻りません。その時点でまだ終わっていない応答や、確認できていない応答の結果も戻りません。すでに戻った結果はそのまま読めます。

Codex の会話の子が複数のワークスペースに分かれている場合は、`children`・`broadcast`・`kill`・`respawn` の `--workspace` で、そのうちの 1 つを指定してください。リクエストは指定したワークスペースがあるウィンドウの子にだけ届くため、子が複数のウィンドウにいる場合は、ウィンドウごとに別々にリクエストしてください。子が 1 つのワークスペースにだけいる場合や、対象の子が決まっている場合は、指定しなくても構いません。

### Codex の会話から Claude の子を動かす

Codex の会話内で `tasty claude spawn`・`tell`・`children`・`broadcast`・`kill`・`respawn` を実行すると、親が自動で決まります。`--surface` を指定する必要はなく、別の会話のサーフェスを指定すると拒否されます。Codex プラグインがインストールされ、有効になっている必要があり、ない場合は別の親で代用せず、エラーで終了します。

```sh
tasty claude spawn --workspace workers --cwd ~/proj --prompt "テストを実行して"
tasty claude tell "今度は clippy も実行して" --surface 57   # 対象の子は指定します
```

子の Claude の応答が終わると、その回答が元の Codex の会話に戻ります。Stop ゲートが応答を続けさせた場合や、バックグラウンドタスクを待っている間は送信せず、応答が実際に終わったときに 1 回だけ送信します。同じ応答にまとめられた tell は、1 つの結果として戻ります。戻った結果は応答が終わったことを意味し、タスクが正しかったという判定ではありません。API エラーで終わった応答や、応答中に終了した子も、その状態で通知します。

子で `/clear` や `/resume` を実行しても、その後の応答は同じ Codex の会話に戻ります。Claude Code が前のセッションの終了通知を待たずに新しいセッションを開始した場合は、新しいセッションが次の応答を開始するときに引き継がれます。

子が終了した後、同じサーフェスで Claude を新しく実行した場合は、Codex の会話からその子に再度 `tell` すると、新しい実行の応答が戻ります。Codex 以外の場所（通常のシェルや Claude の親）から同じ子に `tell` や `respawn` を実行すると、その子の結果はそれ以降 Codex の会話に届かなくなります。すでに終わった応答の結果はそのまま送信します。

結果を Codex プラグインに渡せなかった場合は、破棄せず残しておきます。間隔を徐々に延ばしながら（最大 5 分）自動で再送し、1 日経っても渡せない場合は自動再試行を停止します。同じ結果を再送しても、Codex の会話には 1 回だけ届きます。

```sh
tasty claude codex-returns           # 残っている結果と本文を表示
tasty claude codex-returns --retry   # 残っている結果をすべて今すぐ送信する順番に戻す
```

`--retry` は、自動再試行を停止した結果も送信待ちに戻し、送信を待たずにすぐ終了します。そのため、一緒に出力される一覧には、今戻した結果も残っていることがあります。しばらくしてから、再度 `codex-returns` で確認してください。

1 つの Codex の会話の子が複数のワークスペースにいる場合は、`children`・`kill`・`broadcast`・`respawn` の `--workspace` で、どのワークスペースの子か指定してください。指定しないと、候補を示して拒否します。子が現在いるワークスペースを基準とするため、復元されて別のワークスペースに移動した子も、現在の場所で見つけます。

### 接続したリモートワークスペースに子を作成する

まだ接続していない場合は、`tasty remote attach --into-gui --workspace <リモート ID> --profile <名前>` で、実行中の Tasty にミラーをアタッチします。リモートに新しいワークスペースを作成してアタッチするには、`--workspace <リモート ID>` の代わりに `--new-workspace` を使用し、名前とリモートの作業パスは `--name`・`--cwd` で指定できます。プロファイルの代わりに `--ssh <対象>` も使用できます。Tasty が SSH トンネルを直接開き、フォーカスは移しません。既存のワークスペースへの接続は、受付と結果の JSON を 2 行出力し、結果を最大 90 秒待ちます。失敗した場合や時間内に結果を受け取れなかった場合は、終了コードが 1 になります。新しいワークスペースを作成する形式では、作成結果の JSON を 1 行出力します。

`tasty list workspaces` の `[mirror]` 行で、こちら側のワークスペース ID を確認し、以下の spawn の `--workspace` にその ID を指定してください。attach に指定したリモート ID をそのまま使用しないでください。セッショントークンで `tasty remote attach --into-gui` と `tasty remote refusals` を使用するのに別途権限は必要ありませんが、`tasty list workspaces` には `surface.read` 権限が必要です。CLI には接続だけを切断するコマンドがなく、ミラーの最後のサーフェスを閉じると、リモートワークスペースも一緒に閉じます。接続方法と GUI で接続だけを切断する方法は、[リモート作業を再開する](../remote/attach.md)を参照してください。

別のコンピューターの Tasty ワークスペースを接続（アタッチ）してある場合は、そのワークスペース番号を `--workspace` に指定し、`tasty claude spawn`・`tasty codex spawn` を実行できます。子はリモートコンピューターで、そのコンピューターの Claude Code・Codex のインストール、設定、ログイン情報を使って実行され、こちら側では接続したワークスペース内の子として表示されます。`tell`・`children`・`kill` も、こちら側の子と同じように使用します。

```sh
tasty claude spawn --workspace 7 --prompt "テストを実行して"    # 7 は接続したリモートワークスペース
```

- リモートコンピューターにも `tasty claude install`・`tasty codex install` でフックをインストールしておく必要があります。そうしないと完了が戻りません。Claude のフックがない場合は、spawn の結果に警告が表示されます。
- 完了通知はこちら側の親の完了ログに届き、Codex の会話が親の場合は、応答結果もその会話に戻ります。結果が遅れて届いても、その応答を指示した会話に届きます。
- Claude セッションやシェルが親の場合は、応答本文がこちら側に保存され、完了ログに結果 ID と読み取りコマンドが 1 行で届きます。状態変更の行とは別に届くため、状態の行を受け取った後、結果の行を待ってください。SSH でリモートコンピューターに入る必要はありません。

  ```sh
  tasty claude remote-results --id 0123456789abcdef   # Claude の子の結果本文 (Codex の子は tasty codex remote-results)
  tasty claude remote-results                         # 保存された結果の一覧 (本文を除く)
  ```

  結果行の文言は、Tasty の言語設定に応じて翻訳されます。たとえば、英語では `surface 12: turn result 0123456789abcdef (turn_ended) is stored. Read it with: tasty claude remote-results --id 0123456789abcdef`、韓国語では `surface 12: 턴 결과 0123456789abcdef (turn_ended)을(를) 저장했습니다. 읽기: tasty claude remote-results --id 0123456789abcdef` のように届きます。スクリプトで結果行を探すときは、`turn result` のような文言や行内の任意の 16 進数ではなく、行末の `tasty claude remote-results --id <ID>`・`tasty codex remote-results --id <ID>` というコマンド部分から、claude/codex と ID（16 桁の小文字の 16 進数）を一緒に取り出してください。例: `grep -E '(^| )tasty (claude|codex) remote-results --id ([0-9a-f]{16})$'`

  結果は子を閉じた後も 7 日間残ります。指示後に親セッションが変わった場合や親が閉じた場合は、結果を保存するだけで通知しないため、一覧から探してください。接続障害中は同じ結果行がもう 1 回届くことがありますが、同じ ID なので再度読んでも構いません。
- リモートの子に `tell` できるのは、その子を作成した親だけです。別の親（同じ画面で新しく開始した Claude の会話を含む）から送信すると、応答が誤った親に届かないよう拒否します。その親用の子を新しく作成してください。このルールができる前に作成したリモートの子など、作成した親が不明な子には誰も `tell` できないため、新しく作成してください。
- 接続が切れると、指示が実行されたか分からないと通知する場合があります。再試行する前に `children` で確認してください。自分で接続を切断して再接続すると、新しい接続と見なされ、以前の接続で送った指示の結果は引き続き受け取れません。
- `--cwd`・`--profile-file` は、リモートコンピューター上の絶対パスで指定してください。相対パスやリモートコンピューターに存在しないパスの場合は、子を作成せず拒否します。
- リモート側のユーザーは、接続中、その子に `tell`・`kill`・`respawn`・`reboot` を実行できません。接続した側だけが操作できます。
- リモートの子には `respawn`・`broadcast` を使用できません。

### API エラーで停止した Claude の自動再開

サーバー過負荷など、一時的な API エラーで Claude のターンが終わると、Tasty が少し待ってから「続けて」という文言を代わりに送り、タスクを続けさせることができます。**デフォルトでは無効です。** **設定** <!-- en: Settings --> › **プラグイン** <!-- en: Plugins --> › **Claude Code** で有効にします。

- **一時的な API エラー（サーバー過負荷）の後に自動で再開する** <!-- en: Resume automatically after a temporary API error (server overload) --> — 有効/無効。
- **再開までの待ち時間（秒）** <!-- en: Seconds to wait before resuming --> — デフォルトは 10 秒です。1 秒から 1 日（86400 秒）まで指定でき、範囲外の値は最も近い端の値に調整します。
- **諦めるまでの連続自動再開回数** <!-- en: Consecutive automatic resumes before giving up --> — デフォルトは 5 回です。連続して失敗し、この回数に達すると、それ以上送信せず、通知を 1 回表示します。
- リクエスト上限超過・認証失敗・支払いの問題など、再送しても同じエラーになる場合は再開しません。
- 待機中に自分で入力すると送信しません。そのターンが始まった後、そのサーフェスで一度でもキーを押したり、何かを貼り付けたりしていた場合は（入力欄に書きかけの文章があるかもしれないため）、再開しません。
- 自動で送信した回数は、サーフェスメタ `claude-auto-resume-count` で確認できます。
- この機能には、`tasty claude install` でインストールしたフックが必要です。Tasty を更新した後は、再度インストールしてください。

## 5. Codex の承認ポリシー

`tasty codex spawn/launch/respawn/reboot` は、Codex の承認・サンドボックスポリシーをフラグで受け付けます。

`launch`/`spawn`/`respawn`/`reboot` は、シェルの `codex` の別名や関数を経由せず、`PATH` にインストールされた Codex を実行します。別名に設定した承認・サンドボックスのオプションは、以下のフラグかグローバル設定で指定してください。起動コマンドは sh/bash/zsh と Windows Git Bash の構文を使用します。

- **承認**: `--approval untrusted|on-request|never`。呼び出しオプションがなければ、プラグインのグローバルデフォルト値を使用します。その設定もないか、**引き継ぐ**の場合は、**`never`** で実行します。自動化が承認への返答を待って停止しないように定めたデフォルト値です。人がそばで承認できる場合にだけ、`untrusted` / `on-request` を明示してください。
- **サンドボックス**: `--sandbox read-only|workspace-write|danger-full-access`。呼び出しオプションがなければ、プラグインのグローバルデフォルト値を使用し、その設定もないか、引き継ぐの場合は、Codex のデフォルト値を使用します。レビュー・相互検証用の子には `read-only` が適しています。
- `--full-auto`: 承認とサンドボックスの両方を回避します。`--approval`/`--sandbox` とは併用できません。
- グローバルデフォルト値は、**設定** › **プラグイン** › **Codex** の**デフォルト承認ポリシー** <!-- en: Default approval policy --> / **デフォルトサンドボックスモード** <!-- en: Default sandbox mode --> です。呼び出しごとのフラグが優先されます。
- 既存の会話を開き直す `reboot` とタブの復元にも、同じポリシーが適用されます。ポリシーを適用できない場合は、Codex を起動せず、ターミナルに理由を表示します。

コンテナーなど、サンドボックスを入れ子にできない環境で、`--sandbox` の指定が `RTM_NEWADDR: Operation not permitted` などのエラーで失敗する場合は、`--full-auto` を使用します。完了通知にもこのヒントが付きます。

### 子ごとのモデルと推論レベル

`tasty codex spawn --workspace workers --model gpt-6.1-sol --effort medium --prompt "テストを実行して"` のように、子ごとにモデルと推論レベルを指定できます。どちらのオプションも任意で、省略すると既存の Codex 設定を使用します。グローバル設定や、親・ほかの子のモデルは変わりません。同じ会話のタブを復元したり、`reboot` したりしても、明示した値は保持されます。

`--effort` は `none|minimal|low|medium|high|xhigh|max|ultra` を受け付けます。モデル識別子は、Codex が提供する値を使用してください。モデルと推論レベルの対応状況は Codex が判断し、拒否された場合はエラーを表示して、別のモデルに自動で切り替えることはありません。


## 6. Claude の権限モード

`tasty claude launch/spawn/respawn/reboot/child-profile` は、子の Claude の権限モードをフラグで受け付けます。

- `--permission-mode acceptEdits|auto|bypassPermissions|manual|dontAsk|plan` — Claude Code にそのまま渡されます。
- **呼び出しオプションがなければ、プラグインのグローバルデフォルト値を使用します。** その設定もないか、**引き継ぐ**の場合は、権限モードのフラグを付けず、既存の Claude Code 設定に従います。Tasty が自動で承認を省略するモードに切り替えることはありません。
- 自動化中に子が承認待ちで停止すると困る場合は、その呼び出しにだけ希望のモードを明示してください。停止した子の状態も、[受信設定](#4-完了通知を受け取る)に従って届けられます。
- グローバルデフォルト値は、**設定** › **プラグイン** › **Claude Code** の**子セッションの既定パーミッションモード** <!-- en: Default permission mode for child sessions --> です。デフォルト値は**引き継ぐ**（フラグなし）で、呼び出しごとのフラグが優先されます。
- `--profile` / `--profile-file` で付与する設定 JSON が `permissions.defaultMode` を設定している場合は、`--permission-mode` と併用できません — 両方が同じものを設定するため、どちらか一方を選ぶようエラーが表示されます。
- `reboot` / `child-profile` で指定したモードは、**その再起動にだけ**適用されます。タブの復元で再び起動するときには引き継がれません。

<a id="6-セッションの再起動-reboot"></a>

## 7. セッションの再起動（reboot）

フックや設定を変更した後、エージェントを同じセッションで起動し直します。

```sh
tasty claude reboot --surface 57 --delay 5
tasty codex reboot --surface 58
```

指定した時間の後にプロセスを停止し、同じセッションを再開します。エージェントが**自分自身**に対して呼び出すときは、ターンの最後の操作として呼び出します — それ以降の応答は、プロセスの終了により中断されます。子エージェントだけを再起動するときは、タスクを依頼したエージェントの応答は中断されません。

`tasty codex reboot` の成功応答は、再起動を予約したことを意味します。再起動が完了したかは、プラグインログ（`tasty plugin logs com.tasty.codex`）で確認します。待機中に同じターミナルで Codex を新しく起動すると、再起動はその Codex に入力せず停止します。

<a id="7-claude-のセッションプロファイルと-stop-ゲート"></a>

## 8. Claude のセッションプロファイルと Stop ゲート

Claude Code は起動時に一度だけフックを読み込みます。特定のセッションにだけ追加のフック・権限を付与するには、プロファイルを登録し、起動時に `--profile` で指定します。

```sh
tasty claude profile-register strict --file ./strict.json   # settings JSON を名前で登録
tasty claude profile-list
tasty claude spawn --workspace w --profile strict           # この子にだけ適用
tasty claude reboot --profile strict                        # 以降の再起動にも引き継ぐ
tasty claude child-profile --child 0 --profile strict       # 子に継続的に付与
```

**Stop ゲート**を使用すると、エージェントが応答を終える前に、チェックリストでタスクを再確認するようにできます。標準のゲートである `continue-checklist` を有効にして、セッションに接続してください。

```sh
tasty claude checklist-enable                               # ゲートを有効にする (checklist-disable で無効にする)
tasty claude checklist-status                               # 現在有効か確認
tasty claude spawn --workspace w --profile continue-checklist
```

`checklist-enable`・`checklist-disable`・`checklist-status` は、`--gate <名前>` で別の登録済みゲートを指定できます（デフォルトは `continue-checklist`）。すべてのゲートの有効状態は、`tasty claude gate-list` でまとめて確認します。

- エージェントが応答の末尾に `[[TASTY-CHECKLIST-DONE]]` を入れると通過し、そうでなければチェックリストを再度受け取ります。ラウンド上限（デフォルトは 3）に達すると、自動で通過します。
- 上限は、**設定** › **プラグイン** › **Claude Code** の**ゲートのデフォルトラウンド上限** <!-- en: Default gate round limit --> です。
- 独自のゲートを作成するには、`tasty claude gate-register <名前> --body-file <ファイル> [--sentinel <文字列>] [--rounds N]` を使用します。本文にはセンチネル文字列が含まれている必要があります。`gate-list` / `gate-show` で確認してください。

## トラブルシューティング

Windows と macOS で、Tasty ターミナルの Codex セッションが接続直後に切断される問題を修正しました。

- **完了通知が届きません** — 子の CLI のフックのインストール・実行と、[受信設定](#4-完了通知を受け取る)を確認してください。親が Claude Code の場合は、完了通知 mod が有効になっているか確認してください。mod がない場合は、Monitor の購読を確認してください。フックの通知失敗は `~/.tasty/hook-failures.log` に記録されます。プラグインログは `tasty plugin logs com.tasty.claude --follow` です。
- **`reboot` が「claude-session-id meta not set」で失敗します** — セッション開始フックがセッション ID を記録できなかった状態です。`tasty surface-meta set --key claude-session-id --value <セッション ID>` で直接設定します。
- **子が spawn されず「occupied」エラーになります** — 対象のワークスペースがリモートからアタッチされているか、ミラーです。別のワークスペースを使用します。
- **`kill` が「hard-occupied」エラーで拒否されます** — その子がいるワークスペースを、リモートユーザーがアタッチして使用中です。子との関係とタブはそのまま残ります。リモート側が接続を切断するか、強制切断で占有を解除した後、再度 `kill` を実行します。
- **Codex が「app-server could not start」で起動しません** — Tasty が、そのターミナル専用の Codex サーバーを起動できなかった状態です。同じターミナルで `codex app-server --help` が実行できるか確認してください。この機能は Codex CLI 0.154.0 を基準に確認しました。
- **Codex の親に結果が届きません** — Codex の `/hooks` で Tasty のフックが承認されているか、子を Codex の会話内で spawn したか確認してください。親の Codex を直接入力した `codex` で起動した場合は、共有 Codex サーバーにその会話が開かれている必要があります。
- **macOS でアプリアイコンから起動すると通知が届きません** — Tasty は通知を書き込むときに `tasty` を再度呼び出しますが、自分の実行ファイルのパスを自動で PATH に追加するため、通常は問題ありません。それでも届かない場合は、`hook-failures.log` を確認します。
