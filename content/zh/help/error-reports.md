# 崩溃、无响应报告与日志

Tasty 意外退出或无响应时，可以收集报告和日志来报告问题。

1. 记录发生时间和之前正在进行的操作。如果仍处于无响应状态，也可以在退出前收集下文介绍的堆栈样本。
2. **重新启动 Tasty 前，将数据文件夹中的 `debug.log` 复制到其他文件夹。新实例打开此日志时会清空之前的内容。** 相关插件的日志也应在重新启动插件前复制。
3. 收集同一时间的 `crash-*.log` 或 `hang-*.log`，以及下文列出的诊断信息。没有报告时，发送现有日志并描述症状。
4. 隐去附件副本中的令牌和个人信息，再到 [GitHub Issues](https://github.com/zilhak/tasty/issues) 报告问题。

## 查找数据文件夹

如果指定了 `TASTY_HOME`，在该文件夹中查找。去掉值前后的空白后如果为空，则使用默认文件夹。

| OS | 默认数据文件夹 |
|---|---|
| Windows | `%USERPROFILE%\.tasty\` |
| macOS · Linux | `~/.tasty/` |

以下路径均相对于此数据文件夹。

## 收集哪些文件

| 文件 | 内容和保存时机 |
|---|---|
| `crash-reports/crash-*.log` | 包含崩溃时间、Tasty 版本、OS 和架构、错误位置和消息以及回溯。附上与问题发生时间对应的文件 |
| `crash-reports/hang-*.log` | 带图形界面的 Tasty（GUI）检测到进度停止超过约 5 秒时会留下记录。并非每次无响应都会产生记录。附上与问题发生时间对应的文件 |
| `debug.log` | 默认记录警告及以上级别日志。记录运行中的 Tasty，退出后仍保留。下一个实例打开此文件时会清空其内容。**重新启动前复制** |
| `plugins-logs/<id>.log` | 各插件的日志。**重新启动插件前复制相关文件** |
| `hook-failures.log` · `hook-failures.log.1` | Claude Code、Codex CLI 钩子未能连接 Tasty 的记录。钩子问题应一并附上。超过 256 KiB 后，会在下次记录前将原文件移至 `.1` |

崩溃报告不会自动删除。报告问题时，选择对应发生时间的文件。`debug.log` 可能不包含打开日志文件之前的早期输出。仅运行 `tasty --version` 等 CLI 命令不会清空此文件。

仅在运行带图形界面的 Tasty（GUI）时自动检测无响应并记录报告。无响应报告包含停止时长、最后记录的处理和渲染状态，以及窗口焦点和遮挡状态。在 Linux 上，还包含系统负载、Tasty 的 CPU 使用时间以及运行、等待和调度信息。Linux 的负载、CPU 和调度信息中，无法收集的项目会显示原因。窗口焦点和遮挡状态可能显示为未知。仅凭最后的渲染状态无法确定无响应的原因。

Linux、Windows 发行版的崩溃报告回溯中会显示 Tasty 函数名称，不包含 Tasty 函数的行号。Windows ZIP、无界面 ZIP 和 MSI 安装文件夹中，`tasty.exe` 旁均附带 `tasty.pdb`，无需单独下载。**不要删除 `tasty.pdb`，也不要单独移动 `tasty.exe`。** 同一位置缺少 `tasty.pdb` 时，回溯可能显示错误的函数名称。即使有 `tasty.pdb`，部分帧的函数名称也可能不准确。

## 收集更详细的日志

默认日志无法说明原因时，可以通过 `TASTY_LOG` 提高日志级别后再次复现。**先复制之前的日志。**

在 macOS、Linux 上，从 Tasty 外部的终端运行以下命令，将标准错误输出（stderr）保存到 `tasty.log`。如果 Tasty 正在运行，先复制日志并退出，再运行命令。

```sh
TASTY_LOG=debug tasty 2> tasty.log
```

标准错误输出包含日志、崩溃消息和回溯。Windows GUI 构建不会显示控制台输出，从 macOS 应用包启动时也难以查看控制台输出。此时同样收集数据文件夹中的日志和报告。

## 诊断命令

使用以下命令查看版本。

```sh
tasty --version
```

如果 Tasty 正在运行且能响应，也收集以下输出。

```sh
tasty list info
tasty list pressure
```

`tasty list pressure` 显示本次运行的连接、请求处理状态和诊断累计值。重新启动会重置累计值。遇到 GPU 问题或反复无响应时，`tasty list gpu-stats`、`tasty list timers` 的输出也有帮助。命令无响应时，不要反复运行，参阅 [CLI 响应延迟和连接诊断](cli-diagnostics.md)。

## 无响应时的堆栈样本

Tasty 仍在运行但无响应时，可以使用 OS 工具收集堆栈样本。退出后便无法获取该状态的样本。

在 Linux 上，如果已安装 GDB 且有权限连接目标进程，从 Tasty 外部的终端运行 `gdb -p <PID>`。将 `<PID>` 替换为无响应的 Tasty 进程 ID。在 GDB 中运行以下命令并保存输出。

```text
thread apply all bt
detach
quit
```

Linux 发行版的 GDB 堆栈样本也会显示 Tasty 函数名称，不包含 Tasty 函数的行号。

如果已有在 macOS、Windows 上收集的进程样本或转储，注明所用工具和收集时间后一并附上。

## OS 自身的崩溃记录

如果已有 OS 崩溃记录，确认时间与问题发生时间一致，并注明所用工具和收集时间后一并附上。

## 附件内容与隐去的信息

报告中应包含以下信息。

- 之前进行的操作、复现步骤、发生时间、是否重复发生
- `tasty --version` 的输出、OS 版本和架构
- 对应时间的崩溃或无响应报告、重新启动前复制的 `debug.log`、相关插件日志
- 能够收集到的诊断命令输出、堆栈样本或 OS 崩溃记录

**隐去附件副本和截图中的以下信息。**

- `TASTY_SESSION_TOKEN` 的值：64 个十六进制字符，可能出现在终端画面、环境变量转储或 `ps` 输出中。
- 主目录路径中的用户名和工作文件夹路径
- 远程 attach 主机名和 SSH 用户名

检查所有附件文件（包括日志）中是否包含令牌和个人信息，并将其隐去。插件日志可能留下文件路径，因此也需隐去主目录路径。转储和 OS 记录也按同样标准检查。
