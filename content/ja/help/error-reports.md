# クラッシュ・フリーズのレポートとログ

Tasty が突然終了したり応答しなくなったりした場合は、レポートとログを集めて問題を報告できます。

1. 発生時刻と直前に行っていた作業を記録してください。まだフリーズしている場合は、終了する前に下記のスタックサンプルも収集できます。
2. **Tasty を再び起動する前に、データフォルダーの `debug.log` を別のフォルダーにコピーしてください。再び起動すると以前の内容は消去されます。** 関連するプラグインのログも、プラグインを再び起動する前にコピーしてください。
3. 同じ時刻の `crash-*.log` または `hang-*.log` と、下記の診断情報を集めてください。レポートがない場合は、残っているログと症状を送ってください。
4. 添付するコピーからトークンと個人情報を伏せて、[GitHub Issues](https://github.com/zilhak/tasty/issues) に報告してください。

## データフォルダーを探す

`TASTY_HOME` を指定している場合は、そのフォルダーを確認してください。値の前後の空白を除いて空になる場合は、デフォルトのフォルダーを使います。

| OS | デフォルトのデータフォルダー |
|---|---|
| Windows | `%USERPROFILE%\.tasty\` |
| macOS · Linux | `~/.tasty/` |

以下のパスはすべて、このデータフォルダーを基準にしています。

## 収集するファイル

| ファイル | 内容と保存するタイミング |
|---|---|
| `crash-reports/crash-*.log` | クラッシュ時刻、Tasty のバージョン、OS・アーキテクチャ、エラーの場所・メッセージ、backtrace を記録します。問題の発生時刻に対応するファイルを添付してください |
| `crash-reports/hang-*.log` | 約 5 秒を超えて処理が進まなくなったと検出すると、記録を残します。すべてのフリーズで記録が残るわけではありません。問題の発生時刻に対応するファイルを添付してください |
| `debug.log` | デフォルトでは警告以上を記録します。実行中の Tasty のログで、終了後も残りますが、再び起動すると空になります。**再起動前にコピーしてください** |
| `plugins-logs/<id>.log` | プラグインごとのログです。関連するファイルを**プラグインの再起動前にコピーしてください** |
| `hook-failures.log` · `hook-failures.log.1` | Claude Code・Codex CLI のフックが Tasty に届かなかった記録です。フックの問題では、これらも添付してください。256 KiB を超えると、次の記録の前に以前のファイルを `.1` に移します |

クラッシュレポートは自動では削除されません。報告時は問題の発生時刻に対応するファイルを選んでください。`debug.log` には、ログファイルを開く前の初期出力が残らない場合があります。`tasty --version` などの CLI コマンドを実行するだけでは、このファイルは空になりません。

## さらに詳しいログを収集する

デフォルトのログで原因がわからない場合は、`TASTY_LOG` でログレベルを上げて再現できます。**先に以前のログをコピーしてください。**

macOS・Linux では、Tasty 外部のターミナルで次のように実行すると、標準エラー出力（stderr）を `tasty.log` に保存します。Tasty が実行中の場合は、ログをコピーして終了してから実行してください。

```sh
TASTY_LOG=debug tasty 2> tasty.log
```

標準エラー出力にはログ、クラッシュのメッセージ、backtrace が出ます。Windows の GUI ビルドではコンソール出力が見えず、macOS のアプリバンドルから起動した場合もコンソール出力を確認しにくくなります。この場合もデータフォルダーのログとレポートを集めてください。

## 診断コマンド

次のコマンドでバージョンを確認します。

```sh
tasty --version
```

Tasty が実行中で応答する場合は、次の出力も集めてください。

```sh
tasty list info
tasty list pressure
```

`tasty list pressure` は、今回の実行の接続・要求処理の状態と診断の累計を表示します。再起動すると累計は初期化されます。GPU や繰り返すフリーズの問題では、`tasty list gpu-stats`、`tasty list timers` の出力も役立ちます。コマンドが応答しない場合は繰り返し実行せず、[CLI の応答遅延と接続診断](cli-diagnostics.md) を参照してください。

## フリーズ中のスタックサンプル

Tasty がまだ実行中でフリーズしている場合は、OS のツールでスタックサンプルを収集できます。終了後は、その状態のサンプルを取得できません。

Linux で GDB がインストールされ、対象プロセスに接続する権限がある場合は、Tasty 外部のターミナルで `gdb -p <PID>` を実行してください。`<PID>` はフリーズした Tasty のプロセス ID に置き換えます。GDB で次を実行して、出力を保存してください。

```text
thread apply all bt
detach
quit
```

macOS・Windows ですでに収集したプロセスのサンプルやダンプがある場合は、使用したツールと収集時刻を記載して添付してください。

## OS 自体のクラッシュ記録

すでに収集した OS のクラッシュ記録がある場合は、問題の発生時刻と一致するか確認し、使用したツールと収集時刻を記載して添付してください。

## 添付する情報と伏せる情報

報告には次の情報を含めてください。

- 直前の作業、再現手順、発生時刻、繰り返し発生するか
- `tasty --version` の出力、OS のバージョンとアーキテクチャ
- 該当時刻のクラッシュ・フリーズのレポート、再起動前にコピーした `debug.log`、関連するプラグインのログ
- 収集できた診断コマンドの出力、スタックサンプル、OS のクラッシュ記録

**添付するコピーとスクリーンショットでは、次の情報を伏せてください。**

- `TASTY_SESSION_TOKEN` の値: 64 桁の 16 進数で、ターミナル画面、環境変数のダンプ、`ps` の出力に含まれる場合があります。
- ホームパスに含まれるユーザー名と作業フォルダーのパス
- リモート attach のホスト名と SSH ユーザー名

添付するすべてのファイルは、ログも含めてトークンや個人情報が含まれていないか確認し、伏せてください。プラグインのログにはファイルパスが残る場合があるため、ホームパスも伏せてください。ダンプや OS の記録も同じ基準で確認してください。
